# Technical roadmap

## The core question

The MX450's Tensor Core throughput is only 5–10% of the theoretical value (measured 0.60 vs 6–12 TFLOPS),
and `cuBLAS` is 6.4× **slower** than FP32 after requesting the `TENSOR_OP` algorithm.

**What exactly is this "throttling"?**

| Possibility | Characteristic | Solvable? |
|---|---|---|
| A. OTP eFuse physically blown | one-time programmable, irreversible | ❌ not solvable |
| B. firmware / register-level throttle | each SKU generation writes different config values | ⚠️ possibly modifiable |
| C. devinit table configuration (inside vBIOS) | writes registers per board type at init | ⚠️ requires modifying the system BIOS |
| D. hardware designed with a narrow datapath | the datapath itself is narrow | ❌ not solvable |

**The first step of the whole project is to distinguish A/B/C/D.** Acting without distinguishing them means
blindly modifying registers, which is extremely high-risk.

## Existing evidence

1. `NV_PMC_BOOT_0 = 0x167000a1` → chipset 0x167 = TU117, hardware identity confirmed.
2. After compiling `mma.m16n8k8` with `ptxas -arch=sm_75`, the `.text` section is the same 896 B / 56 instructions
   as an equivalent FFMA kernel, but the opcode fingerprints differ (FFMA version `2595×32`; MMA version
   `572×8 + 2375×6 + 2328×6 + 1060×5…`)
   → **real tensor instructions are generated, not FMA unrolling**.
3. Stress test with 8 independent accumulators + 8 warps + 2048 blocks: throughput stays at **0.60 TFLOPS**,
   zero jitter across three runs
   → rules out latency-bound and insufficient-parallelism explanations.
4. `cuBLAS` log shows `algo: CUBLAS_GEMM_DEFAULT_TENSOR_OP(99)`, measured **0.32 TFLOPS**
   → rules out "my kernel is just badly written".
5. **NVIDIA's official developer forum (2018)**: the "lowest-end Turing SKU" of cc 7.5 also supports tensor
   operations, but "at a very much throttled throughput"
   → throttling **is by design**, not a defect.
6. VRAM allocation ceiling **1620 MiB** (err 2 from 1640 MiB); `cuMemAllocManaged(4GB)` allocates but delivers
   only 3.30 GB/s (1/21).

## Phased plan

### Phase 0 · Establish baselines (completed)
- [x] chip identity
- [x] TC instruction existence (SASS level)
- [x] TC throughput quantification (two independent paths)
- [x] VRAM boundary
- [x] reproducible toolchain

### Phase 1 · Determine the nature of the lock ← **current phase**

Goal: confirm whether the throttling is a writable register configuration or physically fixed.

**Method 1-A: read devinit / fuse-related registers**
- scan the PMC region via BAR0 mmap, looking for registers related to "capability bits"
- known obstacle: after unloading the driver, many PMC registers return the sentinel `0xbadf5040`,
  meaning devinit must run first; other channels (NVML / ioctl) are needed while the driver is loaded

**Method 1-B: analyse NVIDIA's open kernel modules**
- `open-gpu-kernel-modules` covers Turing+, including HAL and devinit
- search it for throttle / SS / PLM definitions, to see whether TU117 uses the same throttling mechanism
- this is **the lowest-cost, highest-information step**, do it first

**Method 1-C: compare register values across SKUs**
- if a register snapshot from another SKU of the same generation (e.g. GTX 1650) were available, the differing
  bits could be identified
- practical constraint: only one MX450 on hand, no cross-comparison possible

**Decision criteria**
- if "throttle configuration written per device id" is found in open-gpu-kernel-modules
  → it is class B/C, **there is room to rewrite**
- if the capability turns out to be controlled by read-only bits in `NV_PMC_BOOT_42` / fuse
  → it is class A, **stop here and record honestly**

### Phase 2 · Locate the specific registers (only if phase 1 judges B/C)
- locate the throttle write point in TU117's devinit path
- consult the `SS0/SS1` semantics of the CMP 170HX and look for equivalents in the Turing namespace
- sample read-only across power states / loads, watching for value changes

### Phase 3 · Attempt runtime rewriting
- first choice: write via BAR0 before driver initialisation (following cmpunlocker's timing)
- second choice: patch `nvidia-open` (Turing supports the open kernel module from 570 onward)
- **every step needs a rollback plan**; this machine has no separate vBIOS Flash, so a bad write may be
  unrecoverable

### Phase 4 · Verify and record
- re-measure with `tools/tc_bench.py` and compare against the 0.60 TFLOPS baseline
- stability testing: sustained load, temperature, error rate
- regardless of outcome, write the full data and conclusions into `findings/`

## Known hard constraints (will not change through any unlock)

1. **The 2048 MiB of VRAM is two physically soldered GDDR6 packages**, not a register limitation.
   The CMP 170HX can reach 64 GB because five 16 GB HBM2e stacks **are really on the board**.
   The MX450 has no spare packages; no unlock can conjure VRAM out of nothing.
2. **Even with TCs fully unlocked (+10–20× compute), 7B QLoRA still needs 7 GB of VRAM**, which still does not
   fit. This project's output is knowledge about the "compute" dimension and possibly a real gain — not
   "the ability to train bigger models".

## Reference projects and what can be borrowed

| Project | Borrowable | Not applicable |
|---|---|---|
| `cmpunlocker` | the exploitation pattern for the Falcon BootROM load-before-verify bug; the four-register PLM open order; `SS0/SS1` throttle semantics; the systemd daemon replay mechanism | targets GA100; register addresses differ from Turing |
| `envytools` | `nva` BAR0 peek/poke, `envydis` disassembly, `nvbios` parsing | the rnndb register database only covers Maxwell and earlier |
| `nouveau` / `NVK` | partial reverse engineering of Turing command streams and ISA | does not address compute unlocking |
| `open-gpu-kernel-modules` | Turing+ HAL, devinit, register definitions (**the main target of phase 1**) | does not contain closed-source microcode |
