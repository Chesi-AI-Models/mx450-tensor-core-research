# 技术路线图

## 核心问题

MX450 的 Tensor Core 吞吐只有理论值的 5–10%（实测 0.60 vs 6–12 TFLOPS），
且 `cuBLAS` 请求 `TENSOR_OP` 算法后比 FP32 还慢 6.4 倍。

**这个「限速」究竟是：**

| 可能 | 特征 | 可解性 |
|---|---|---|
| A. OTP eFuse 物理熔断 | 一次性可编程，烧断不可逆 | ❌ 不可解 |
| B. 固件 / 寄存器级 throttle | 每代 SKU 用不同配置值写入 | ⚠️ 可能可改 |
| C. devinit 表配置（vBIOS 内） | 初始化时按板型写寄存器 | ⚠️ 需改系统 BIOS |
| D. 硬件设计上就按低速率布线 | 数据通路本身窄 | ❌ 不可解 |

**整个项目的第一步，是先分清 A/B/C/D。** 分不清就动手，等于盲改寄存器，风险极高。

## 已有证据

1. `NV_PMC_BOOT_0 = 0x167000a1` → chipset 0x167 = TU117，硬件身份确认。
2. `ptxas -arch=sm_75` 编译 `mma.m16n8k8` 后，`.text` 与等量 FFMA 内核同为 896 B / 56 条指令，
   但 opcode 指纹不同（FFMA 版 `2595×32`；MMA 版 `572×8 + 2375×6 + 2328×6 + 1060×5…`）
   → **生成的是真张量指令，不是 FMA 展开**。
3. 8 路独立累加器 + 8 warp + 2048 blocks 压测，吞吐恒为 **0.60 TFLOPS**，三次运行零抖动
   → 排除延迟受限与并行度不足。
4. `cuBLAS` 日志 `algo: CUBLAS_GEMM_DEFAULT_TENSOR_OP(99)`，实测 **0.32 TFLOPS**
   → 排除「我的 kernel 写得差」。
5. **NVIDIA 官方开发者论坛（2018）**：cc 7.5 的「最低端 Turing SKU」
   也支持 Tensor 运算，但「以极低的吞吐（a very much throttled throughput）」
   → 限速**是设计意图**，不是缺陷。
6. 显存分配上限 **1620 MiB**（1640 MiB 起 err 2）；`cuMemAllocManaged(4GB)` 可分配但带宽仅 3.30 GB/s（1/21）。

## 分阶段计划

### 阶段 0 · 建立基线（已完成）
- [x] 芯片身份
- [x] TC 指令存在性（SASS 层）
- [x] TC 吞吐量化（两条独立路径）
- [x] 显存边界
- [x] 建立可复现工具链

### 阶段 1 · 判定锁的性质 ← **当前所处阶段**

目标：确认限速是寄存器可写配置，还是物理固定。

**方法 1-A：读 devinit / 熔丝相关寄存器**
- 通过 BAR0 mmap 扫描 PMC 区域，寻找与「能力位」相关的寄存器
- 已知障碍：驱动卸载后大量 PMC 寄存器返回哨兵值 `0xbadf5040`，
  说明需要先做 devinit 才能读；需要在驱动加载态下用其他通道（NVML / ioctl）获取

**方法 1-B：分析 NVIDIA 开源内核模块**
- `open-gpu-kernel-modules` 覆盖 Turing+，含 HAL 与 devinit
- 检索其中的 throttle / SS / PLM 类定义，看 TU117 是否走同一套限速机制
- 这是**成本最低、信息量最大**的一步，优先做

**方法 1-C：对比不同 SKU 的寄存器值**
- 若能拿到同代不同 SKU（如 GTX 1650）的寄存器快照，可对比出差异位
- 现实约束：手上只有一块 MX450，无法横向对比

**判定标准**
- 若在 open-gpu-kernel-modules 中找到「按 device id 分支写入的限速配置」
  → 属 B/C 类，**存在改写空间**
- 若发现该能力由 `NV_PMC_BOOT_42` / fuse 只读位控制
  → 属 A 类，**到此为止，如实记录**

### 阶段 2 · 定位具体寄存器（阶段 1 判定为 B/C 才进入）
- 在 TU117 的 devinit 路径中定位 throttle 写点
- 参考 CMP 170HX 的 `SS0/SS1` 语义，在 Turing 命名空间中寻找等价物
- 用只读方式在不同电源状态 / 负载下采样，观察是否有值变化

### 阶段 3 · 尝试运行时改写
- 首选：通过 BAR0 在驱动初始化前写入（参考 cmpunlocker 时序）
- 次选：给 `nvidia-open` 打补丁（Turing 自 570 起支持开源内核模块）
- **每一步都要有回滚方案**；本机无独立 vBIOS Flash，写错即可能无法恢复

### 阶段 4 · 验证与记录
- 用 `tools/tc_bench.py` 复测，与 0.60 TFLOPS 基线对比
- 稳定性测试：连续负载、温度、错误率
- 无论成败，把完整数据与结论写入 `findings/`

## 已知硬约束（不会因破解而改变）

1. **显存 2048 MiB 是物理焊接的 2 颗 GDDR6**，不是寄存器限制。
   CMP 170HX 能扩到 64GB，是因为 5 颗 16GB 的 HBM2e **真的焊在板上**。
   MX450 没有多余颗粒，任何解锁都变不出显存。
2. **即使 TC 完全解锁（+10~20× 算力），7B QLoRA 仍需 7GB 显存**，依然装不下。
   本项目的产出是「算力」维度的认知与可能的提升，不是「能训更大模型」。

## 参考项目与可借鉴点

| 项目 | 可借鉴 | 不适用之处 |
|---|---|---|
| `cmpunlocker` | Falcon BootROM 签名段加载 bug 的利用范式；PLM 四寄存器打开顺序；`SS0/SS1` throttle 语义；systemd 守护重放机制 | 目标 GA100，寄存器地址与 Turing 不同 |
| `envytools` | `nva` 的 BAR0 peek/poke、`envydis` 反汇编、`nvbios` 解析 | rnndb 寄存器库只覆盖 Maxwell 及更早 |
| `nouveau` / `NVK` | Turing 命令流与 ISA 的部分逆向成果 | 不涉及算力解锁 |
| `open-gpu-kernel-modules` | Turing+ 的 HAL、devinit、寄存器定义（**阶段 1 主攻方向**） | 不含闭源微码 |
