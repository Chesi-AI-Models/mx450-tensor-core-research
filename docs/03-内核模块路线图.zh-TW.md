## 二、已發現的障礙

### 障礙 1 · NVIDIA 內部符號未匯出

```
ffffffffc2c13bb0 t __pfx_os_map_kernel_space   [nvidia]
```

符號類型 `t`（小寫）= **local，未匯出**。`[nvidia]` 模組內共 46294 個符號，絕大多數為 local。

**直接影響**：無法透過 `EXPORT_SYMBOL` 直接呼叫 NVIDIA 的記憶體對映介面。

### 障礙 2 · `kallsyms_lookup_name` 不再匯出

Linux 5.7 起該符號從匯出表移除，模組內直接呼叫會連結失敗。

**繞過方式**（業界通用）：
1. **kprobe 法**：註冊一個 kprobe，在其 handler 中取得 `kallsyms_lookup_name` 的位址
2. **符號掃描法**：解析 `/proc/kallsyms`（但核心模組無法直接讀檔案，需借助 `kernel_read`）
3. **已知偏移法**：從同一核心版本的 `vmlinux` 取偏移（需 vmlinux，`Skipping BTF generation due to unavailability of vmlinux` 說明本機沒有）

**推薦 kprobe 法**，成功率高且不依賴 vmlinux。

### 障礙 3 · 模組崩潰會導致狀態異常

本輪一次測試中，因參數類型寫錯（`'fnOS'` 多字元常數被當作 `char*` 解引用，存取 `0x666e4f53`），
導致核心 oops。雖未重啟系統，但模組引用計數異常，`rmmod` 與 `rmmod -f` 均失敗。

**教訓**：
- 核心模組裡任何指標錯誤都是致命的
- 每次載入前先在 `qemu` 或可棄置環境驗證
- 崩潰後模組可能無法卸載，需重啟清理

### P1 · 繞過 kallsyms_lookup_name 限制 ✅ **已完成，方案修正**

**嘗試 1（kprobe）**：QEMU 內成功（`kallsyms_lookup_name @ 0xffffffffb37e9404`），
宿主機上**呼叫時 oops**（`mx450_p1_init+0x92`，大符號表 46294 項）。
推測該函式走遍大表時依賴 kallsyms_lock/RCU，模組 init 上下文呼叫不安全。

**方案修正**：`/proc/kallsyms` 對 root 完全可讀，符號位址本來就在：

```bash
$ grep -E "os_map_kernel_space" /proc/kallsyms
ffffffffc2c13bb0 t __pfx_os_map_kernel_space	[nvidia]
```

→ **改為「使用者態讀 kallsyms 取位址 + module_param 傳入」**，全程不碰 `kallsyms_lookup_name`。
位址來源透明可稽核（能看到 `[nvidia]` 歸屬），風險大幅降低。

詳見 `findings/2026-10-18-阶段3-P1-kprobe.md`。
