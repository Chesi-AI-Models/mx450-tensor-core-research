## 二、已发现的障碍

### 障碍 1 · NVIDIA 内部符号未导出

```
ffffffffc2c13bb0 t __pfx_os_map_kernel_space   [nvidia]
```

符号类型 `t`（小写）= **local，未导出**。`[nvidia]` 模块内共 46294 个符号，绝大多数为 local。

**直接影响**：无法通过 `EXPORT_SYMBOL` 直接调用 NVIDIA 的内存映射接口。

### 障碍 2 · `kallsyms_lookup_name` 不再导出

Linux 5.7 起该符号从导出表中移除，模块内直接调用会链接失败。

**绕过方式**（业界通用）：
1. **kprobe 法**：注册一个 kprobe，在其 handler 中取得 `kallsyms_lookup_name` 的地址
2. **符号扫描法**：解析 `/proc/kallsyms`（但内核模块无法直接读文件，需借助 `kernel_read`）
3. **已知偏移法**：从同一内核版本的 `vmlinux` 取偏移（需 vmlinux，`Skipping BTF generation due to unavailability of vmlinux` 说明本机没有）

**推荐 kprobe 法**，成功率高且不依赖 vmlinux。

### 障碍 3 · 模块崩溃会导致状态异常

本轮一次测试中，因参数类型写错（`'fnOS'` 多字符常量被当作 `char*` 解引用，访问 `0x666e4f53`），
导致内核 oops。虽未重启系统，但模块引用计数异常，`rmmod` 与 `rmmod -f` 均失败。

**教训**：
- 内核模块里任何指针错误都是致命的
- 每次加载前先在 `qemu` 或可弃置环境验证
- 崩溃后模块可能无法卸载，需重启清理

### P1 · 绕过 kallsyms_lookup_name 限制 ✅ **已完成，方案修正**

**尝试 1（kprobe）**：QEMU 内成功（`kallsyms_lookup_name @ 0xffffffffb37e9404`），
宿主机上**调用时 oops**（`mx450_p1_init+0x92`，大符号表 46294 项）。
推测该函数遍历大表时依赖 kallsyms_lock/RCU，模块 init 上下文调用不安全。

**方案修正**：`/proc/kallsyms` 对 root 完全可读，符号地址本来就在：

```bash
$ grep -E "os_map_kernel_space" /proc/kallsyms
ffffffffc2c13bb0 t __pfx_os_map_kernel_space	[nvidia]
```

→ **改为「用户态读 kallsyms 取地址 + module_param 传入」**，全程不碰 `kallsyms_lookup_name`。
地址来源透明可审计（能看到 `[nvidia]` 归属），风险大幅降低。

详见 `findings/2026-10-18-阶段3-P1-kprobe.md`。
