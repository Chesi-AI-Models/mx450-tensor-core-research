# 技術路線圖

## 核心問題

MX450 的 Tensor Core 吞吐只有理論值的 5–10%（實測 0.60 vs 6–12 TFLOPS），
且 `cuBLAS` 請求 `TENSOR_OP` 演算法後比 FP32 還慢 6.4 倍。

**這個「限速」究竟是：**

| 可能 | 特徵 | 可解性 |
|---|---|---|
| A. OTP eFuse 物理熔斷 | 一次性可程式化，燒斷不可逆 | ❌ 不可解 |
| B. 韌體 / 暫存器級 throttle | 每代 SKU 用不同配置值寫入 | ⚠️ 可能可改 |
| C. devinit 表配置（vBIOS 內） | 初始化時按板型寫暫存器 | ⚠️ 需改系統 BIOS |
| D. 硬體設計上就按低速率佈線 | 資料通路本身窄 | ❌ 不可解 |

**整個專案的第一步，是先分清 A/B/C/D。** 分不清就動手，等於盲改暫存器，風險極高。

## 已有證據

1. `NV_PMC_BOOT_0 = 0x167000a1` → chipset 0x167 = TU117，硬體身份確認。
2. `ptxas -arch=sm_75` 編譯 `mma.m16n8k8` 後，`.text` 與等量 FFMA 核心同為 896 B / 56 條指令，
   但 opcode 指紋不同（FFMA 版 `2595×32`；MMA 版 `572×8 + 2375×6 + 2328×6 + 1060×5…`）
   → **產生的是真張量指令，不是 FMA 展開**。
3. 8 路獨立累加器 + 8 warp + 2048 blocks 壓測，吞吐恆為 **0.60 TFLOPS**，三次執行零抖動
   → 排除延遲受限與平行度不足。
4. `cuBLAS` 日誌 `algo: CUBLAS_GEMM_DEFAULT_TENSOR_OP(99)`，實測 **0.32 TFLOPS**
   → 排除「我的 kernel 寫得差」。
5. **NVIDIA 官方開發者論壇（2018）**：cc 7.5 的「最低階 Turing SKU」
   也支援 Tensor 運算，但「以極低的吞吐（a very much throttled throughput）」
   → 限速**是設計意圖**，不是缺陷。
6. 顯示記憶體分配上限 **1620 MiB**（1640 MiB 起 err 2）；`cuMemAllocManaged(4GB)` 可分配但頻寬僅 3.30 GB/s（1/21）。

## 分階段計畫

### 階段 0 · 建立基線（已完成）
- [x] 晶片身份
- [x] TC 指令存在性（SASS 層）
- [x] TC 吞吐量化（兩條獨立路徑）
- [x] 顯示記憶體邊界
- [x] 建立可重現工具鏈

### 階段 1 · 判定鎖的性質 ← **目前所處階段**

目標：確認限速是暫存器可寫配置，還是物理固定。

**方法 1-A：讀 devinit / 熔絲相關暫存器**
- 透過 BAR0 mmap 掃描 PMC 區域，尋找與「能力位」相關的暫存器
- 已知障礙：驅動卸載後大量 PMC 暫存器回傳哨兵值 `0xbadf5040`，
  說明需要先做 devinit 才能讀；需在驅動載入態下用其他通道（NVML / ioctl）取得

**方法 1-B：分析 NVIDIA 開源核心模組**
- `open-gpu-kernel-modules` 涵蓋 Turing+，含 HAL 與 devinit
- 檢索其中的 throttle / SS / PLM 類定義，看 TU117 是否走同一套限速機制
- 這是**成本最低、資訊量最大**的一步，優先做

**方法 1-C：對比不同 SKU 的暫存器值**
- 若能拿到同代不同 SKU（如 GTX 1650）的暫存器快照，可對比出差異位
- 現實限制：手上只有一塊 MX450，無法橫向對比

**判定標準**
- 若在 open-gpu-kernel-modules 中找到「按 device id 分支寫入的限速配置」
  → 屬 B/C 類，**存在改寫空間**
- 若發現該能力由 `NV_PMC_BOOT_42` / fuse 唯讀位控制
  → 屬 A 類，**到此為止，如實記錄**

### 階段 2 · 定位具體暫存器（階段 1 判定為 B/C 才進入）
- 在 TU117 的 devinit 路徑中定位 throttle 寫點
- 參考 CMP 170HX 的 `SS0/SS1` 語意，在 Turing 命名空間中尋找等價物
- 用唯讀方式在不同電源狀態 / 負載下取樣，觀察是否有值變化

### 階段 3 · 嘗試執行時改寫
- 首選：透過 BAR0 在驅動初始化前寫入（參考 cmpunlocker 時序）
- 次選：給 `nvidia-open` 打補丁（Turing 自 570 起支援開源核心模組）
- **每一步都要有回滾方案**；本機無獨立 vBIOS Flash，寫錯即可能無法恢復

### 階段 4 · 驗證與記錄
- 用 `tools/tc_bench.py` 複測，與 0.60 TFLOPS 基線對比
- 穩定性測試：連續負載、溫度、錯誤率
- 無論成敗，把完整資料與結論寫入 `findings/`

## 已知硬限制（不會因破解而改變）

1. **顯示記憶體 2048 MiB 是物理焊接的 2 顆 GDDR6**，不是暫存器限制。
   CMP 170HX 能擴到 64GB，是因為 5 顆 16GB 的 HBM2e **真的焊在板上**。
   MX450 沒有多餘顆粒，任何解鎖都變不出顯示記憶體。
2. **即使 TC 完全解鎖（+10~20× 算力），7B QLoRA 仍需 7GB 顯示記憶體**，依然裝不下。
   本專案的產出是「算力」維度的認知與可能的提升，不是「能訓更大模型」。

## 參考專案與可借鑑點

| 專案 | 可借鑑 | 不適用之處 |
|---|---|---|
| `cmpunlocker` | Falcon BootROM 簽章段載入 bug 的利用範式；PLM 四暫存器打開順序；`SS0/SS1` throttle 語意；systemd 守護重放機制 | 目標 GA100，暫存器位址與 Turing 不同 |
| `envytools` | `nva` 的 BAR0 peek/poke、`envydis` 反組譯、`nvbios` 解析 | rnndb 暫存器庫只涵蓋 Maxwell 及更早 |
| `nouveau` / `NVK` | Turing 命令流與 ISA 的部分逆向成果 | 不涉及算力解鎖 |
| `open-gpu-kernel-modules` | Turing+ 的 HAL、devinit、暫存器定義（**階段 1 主攻方向**） | 不含閉源微碼 |
