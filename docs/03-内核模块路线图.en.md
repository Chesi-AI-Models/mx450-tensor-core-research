## 2. Obstacles found

### Obstacle 1 · NVIDIA internal symbols are not exported

```
ffffffffc2c13bb0 t __pfx_os_map_kernel_space   [nvidia]
```

Symbol type `t` (lowercase) = **local, not exported**. The `[nvidia]` module has 46,294 symbols, the vast
majority local.

**Direct impact**: NVIDIA's memory-mapping interface cannot be called directly via `EXPORT_SYMBOL`.

### Obstacle 2 · `kallsyms_lookup_name` is no longer exported

Since Linux 5.7 this symbol was removed from the export table; calling it from a module fails to link.

**Workarounds** (industry-standard):
1. **kprobe method**: register a kprobe and obtain the address of `kallsyms_lookup_name` from its handler
2. **symbol-scan method**: parse `/proc/kallsyms` (but a kernel module cannot read files directly; needs `kernel_read`)
3. **known-offset method**: take the offset from `vmlinux` of the same kernel version (needs vmlinux; `Skipping BTF generation due to unavailability of vmlinux` shows this machine has none)

**The kprobe method is recommended**: high success rate and no vmlinux dependency.

### Obstacle 3 · a module crash leaves broken state

In one test this round a parameter type mistake (`'fnOS'` multi-character constant dereferenced as `char*`,
touching `0x666e4f53`) caused a kernel oops. The system did not reboot, but the module's refcount went bad and
both `rmmod` and `rmmod -f` failed.

**Lessons**:
- any pointer error in a kernel module is fatal
- verify in `qemu` or a disposable environment before every load
- after a crash the module may be un-unloadable and needs a reboot to clean up

```

```

**Measured result**:

- the module loads successfully inside the VM
- **a crash only kills the VM; zero impact on the host**
- reproduction script: `scripts/p0_qemu_test.sh`

**Key confirmation**: `module verification failed` only taints the kernel (`Tainted: G`), it **does not block
loading**. So unsigned modules can be tested freely later.

**Not done (optional)**: kdump / crashkernel — requires changing GRUB and rebooting the host; QEMU isolation
already meets the safety need, deferred until vmcore capture is actually required.

### P1 · Bypass the kallsyms_lookup_name restriction ✅ **completed, approach revised**

**Attempt 1 (kprobe)**: succeeded in QEMU (`kallsyms_lookup_name @ 0xffffffffb37e9404`),
but **oops on the host at call time** (`mx450_p1_init+0x92`, with the 46,294-entry symbol table).
Presumably that function relies on kallsyms_lock/RCU while traversing the large table, making a call from module
init context unsafe.

**Approach revised**: `/proc/kallsyms` is fully readable by root, and the symbol address is already there:

```bash
$ grep -E "os_map_kernel_space" /proc/kallsyms
ffffffffc2c13bb0 t __pfx_os_map_kernel_space	[nvidia]
```

→ **switched to "read kallsyms in user space, pass the address via module_param"**, never touching
`kallsyms_lookup_name`. The address provenance is transparent and auditable (the `[nvidia]` attribution is
visible), greatly reducing risk.

See `findings/2026-10-18-阶段3-P1-kprobe.md`.

## 5. Payoff boundary (must be accepted before starting)

Even if P1–P4 all succeed:

- ✅ can see how Tensor Cores are configured at the microcode level
- ✅ can confirm whether the throttling is a fuse or a configuration
- ❌ **cannot replace the microcode** (FWSEC signature verification)
- ❌ **cannot change the 1.68 GB of VRAM**
- ❌ **therefore still cannot train a 7B model**

**This is a path of understanding, not a path of capability.**
