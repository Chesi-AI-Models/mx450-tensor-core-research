# 2026-10-19 · Stage 4 addendum: ownership of the iowr address space — five hypotheses eliminated one by one

## 1. This round corrected a methodological error

**The earlier address statistics (`findings/阶段4-FECS微码反汇编.md`) contained a systematic bias.**

The original analysis script `analyze_iowr.py` tracked only `mov` instructions, not `add`/`sub`. But the microcode
contains many cases like:

```asm
00002c2d: mov $r9 0x20600       ; $r9 = 0x20600
00002c31: iowr I[$r9] $r1       ; writes 0x20600  ✓
00002c39: add b32 $r9 $r9 0xc00 ; $r9 = 0x21200  ← the script missed this step
00002c3e: iowr I[$r9] $r15      ; actually writes 0x21200, recorded as 0x20600  ✗
```

**The new script `tools/analyze_iowr_v3.py`** tracks `mov(imm/reg) / add / sub / shl / shr / and / or`,
and first strips the "address + bytecode" prefix at the start of each disassembly line
(v2 got 0% resolution because of a `^` anchor).

### Corrected statistics

```
iowr total: 449   resolved: 442 (98.4%)   unresolved: 7
iord total: 0

instruction counts: mov_i 4446, lcall 932, add 286, sub 61, and 81, shl 43, shr 50, or 3
```

**The address distribution is broadly consistent with v1 (85% still in the 0x20000 segment), so the main conclusion
is unaffected, but the specific figures are now corrected.**

## 2. Key breakthrough: the Falcon IO address mapping rule

envytools `docs/hw/falcon/io.rst` gives the host/Falcon dual-view mapping table:

```
Host    Falcon    Name
0x000   0x00000   INTR_SET
0x004   0x00100   INTR_CLEAR
0x040   0x01000   SCRATCH0
0x100   0x04000   UC_CTRL        ← CPUCTL
0x104   0x04100   UC_ENTRY       ← BOOTVEC
0x108   0x04200   UC_CAPS        ← HWCFG
0x10c   0x04300   UC_BLOCK_ON_FIFO
0x12c   0x04b00   UC_CAPS2       ← HWCFG1
0x180   0x06000   CODE_INDEX     ← IMEM window address
0x184   0x06100   CODE           ← IMEM window data
0x1c0   0x07000   DATA_INDEX[0]
0x1c4   0x07100   DATA[0]
```

**Mapping rule: `Falcon = Host × 0x40`**

**Verification**: we measured `BAR0 0x409000 + 0x12c = 0x80104126`, and `0x12c` is exactly `UC_CAPS2`.
`0x409184 = 0x002000D0`, and `0x184` is exactly `CODE` (the IMEM window) — and what it returns is IMEM[0].
**Two independent verifications; the mapping is confirmed.**

## 3. The five hypotheses, eliminated one by one

### Hypothesis 1 · the `0x20000` segment is a BAR0 absolute address

**Test**: read the BAR0 `0x20000` segment both with the driver unloaded and with the driver running (GPU at 100%).

```
driver unloaded:  0x020000 = 0xBADF5040
driver running:   0x020000 = 0xBADF5040   ← still BAD
                  0x0247FC = 0xBADF1100
                  0x010100 = 0xBAD00100
```

**`0xBADF5040` / `0xBADF1100` / `0xBAD00100` are three classes of NVIDIA "unimplemented address" sentinel value**
(for comparison: `0x001000` also returns `0xBADF5040`, while `0x001700` — the PRAMIN window — returns a valid
`0x00007FF0`).

**Conclusion: eliminated. Not a BAR0 address.**

### Hypothesis 2 · `iowr address = FECS base (0x409000) + offset`

**Test**: read BAR0 `0x409000 + 0x20000 = 0x429000` etc.

**Result**: everything from `0x420000` to `0x43F000` returns BAD.

Also scanning the valid region of the GR segment:

```
0x404000: 0x80000000    ← valid
0x408000: 0x08800800    ← valid
0x409000: 0             ← FECS
0x410000: 0x32080A00    ← valid
0x418000: 0x8700029F    ← valid
0x419000: 0x10210780    ← valid
0x41A000 / 0x41B000: 0  ← valid but empty
0x420000+: all BAD
```

**Conclusion: eliminated. The GR register region ends near 0x41B000.**

### Hypothesis 3 · the `0x20000` segment is UAS (Unified Address Space)

**Test**: read FECS's UAS register group with the GPU at full load.

```
0x409160 UAS_IO_WINDOW   = 0x00000000
0x409164 UAS_CONFIG      = 0x00000000
0x409168 UAS_FAULT_ADDR  = 0x00000000
0x40916c UAS_FAULT_STATUS= 0x00000000
```

**All zero, and `UAS_FAULT_STATUS = 0` means no UAS access fault has ever occurred.**

**Conclusion: eliminated. This Falcon instance's UAS is not enabled (or does not exist).**

> Footnote: envytools' `docs/hw/falcon/data.rst` line 9 says `.. todo:: document UAS`
> — **even envytools itself has not documented UAS.**

### Hypothesis 4 · the `0x20000` segment is XFER external space (VRAM)

**Test**: sample `XFER_EXT_BASE` eight consecutive times with the GPU at full load.

```
0x409110 XFER_EXT_BASE = 0x00772600   (all 8 samples identical, stable)
0x409114 XFER_FALCON_ADDR = 0x00000000
0x409118 XFER_CTRL        = 0x00000602
0x40911c XFER_EXT_ADDR    = 0x0000E700
```

**If `iowr address = XFER_EXT_BASE + offset`, then `0x20000 → VRAM 0x792600`.**
**We dumped VRAM `0x760000-0x860000` (1 MB) and the 64 bytes at `0x792600` are all zero.**

**Conclusion: eliminated. Not XFER external space.**

### Hypothesis 5 · the `0x20000` segment is Falcon DMEM

**HWCFG = 0x40204080**, field decoding:
- bits 8:0 = 0x080 = 128 → IMEM = 128 × 256 B = **32 KB** (matching the measured dump length)
- DMEM is conventionally 1/4 to 1/2 of IMEM in NVIDIA designs, i.e. **8–16 KB**

**`0x20000 = 128 KB`, far beyond DMEM capacity.**

**Conclusion: eliminated.**

## 4. Address structure analysis: it is "4 KB blocks + registers within blocks"

Grouping the 72 unique addresses into 4 KB blocks:

| Block | Addresses | Offsets within block |
|---|---|---|
| `0x20000-0x20FFF` | 11 | 0x000, 0x100, 0x600, 0x700, 0x900, 0xA00, 0xB00, 0xC00, 0xD00, 0xE00, 0xF00 |
| `0x21000-0x21FFF` | 3 | 0x200, 0x300, 0x800 |
| `0x22000-0x23FFF` | 7 | 0xA00, 0xE00, 0xF00, 0x000(23000), 0x200, 0x300, 0x800 |
| `0x24000-0x24FFF` | 4 | 0x200, 0x300, 0x400, 0x420, **0x6FC, 0x7FC, 0xFFC** |
| `0x28000-0x28FFF` | 8 | 0x000, 0x100, 0x300, 0x400, 0x800, 0x900, 0xD00, 0xE00 |
| `0x2C000-0x2CFFF` | 4 | 0x000, 0x100, 0x200, 0x300 |
| `0x2DC00-0x2DEFF` | 3 | 0xC00, 0xD00, 0xE00 |
| `0x30200-0x30900` | 4 | 0x200, 0x540, 0x700, 0x900 |

**Two key features:**

1. **offsets within blocks step in units of 0x100** — the classic "one register group per instance, instances 0x100
   apart"
2. **`0x246FC / 0x247FC / 0x24FFC`, the three addresses ending in `0xFFC`** — the tail offset within a 4 KB block,
   the classic "block end marker / block-level control register"

**This matches the layout of GR internal hardware register groups exactly, not a memory buffer.**

## 5. Final verdict

**The `0x20000` segment is the high-address extension of the Falcon IO space in v6, mapping to GR engine internal
hardware registers — not to BAR0.**

Basis:

| Evidence | Note |
|---|---|
| all five hypotheses empirically eliminated | BAR0 / FECS+off / UAS / XFER / DMEM |
| address structure is 4 KB blocks + 0x100 stepping | hardware register group signature, not memory |
| `iord` count is 0 | the microcode only writes, never reads — classic "configuration register" writes |
| no overlap with the valid GR region (ends at 0x41B000) | not inside host-visible BAR0 space |

**This is the final confirmation that "public material cannot solve it", not "not found yet":**

- envytools rnndb: stops at Maxwell; the `0x20000` segment's upper bound `0x227FF` < `0x30900`, the microcode's
  actual maximum access
- `turing/tu102/` headers: no `dev_gpc.h` / `dev_tpc.h`
- open-source HAL: zero definitions for `NV_PGRAPH_GPC` / `NV_PGRAPH_TPC`
- envytools falcon docs: `.. todo:: document UAS` (the authors have not written it either)

## 6. Incidental discovery this round: the GPU MMU page table in VRAM

While dumping VRAM `0x760000-0x860000`, a regular structure was found at `0x788000-0x791000`:

```
0x790000: 0D 0D 7E 17 00 00 00 06   → 0x177E0D << 8 = 0x177E0D00
          0D 0E 7E 17 00 00 00 06   → 0x177E0E00  (+0x100)
          0D 0F 7E 17 00 00 00 06   → 0x177E0F00
          0D A8 2F 21 00 00 00 06   → 0x212FA800  ← jumps to another segment
```

each entry 8 bytes, `[flags:8][addr:24][reserved:32]`, with addresses incrementing contiguously within the 2 GB VRAM
range.

```
0x788000: 02 91 07 00 00 00 00 00   → 0x079102
          02 89 07 00 00 00 00 00   → 0x078902
          12 91 07 00 00 00 00 00   → 0x079112
          02 8A 07 00 00 00 00 00   → 0x078A02
```

appearing in pairs, stepping by `0x10` and `0x100` — the classic structure of a **page table / address mapping table**.

**Verdict: this is the GPU's memory-management structure (MMU page table / allocator metadata), not FECS private data.**

**But it is the first time this project has located a GPU-internal data structure inside VRAM**, which is valuable
for later research.

## 8. What this round means

**Eliminating five possibilities is itself progress.**

In reverse engineering, "establishing what something is not" is as valuable as "establishing what it is" — it narrows
the search space and prevents those who follow from repeating the same detours.

**The conclusion is now clear:**

```
FECS microcode (dumped, disassembled)
    ↓ accesses through iowr
Falcon IO space (v6 extension, 0x20000 segment)
    ↓ maps to
GR internal hardware registers (NVIDIA has never published the mapping table)
    ↓ controls
runtime configuration of GPC / TPC / SM
```

**The mapping table in the final link is the one part NVIDIA never leaked.**

To obtain it there are only two routes:
1. reverse the closed-source `nv-kernel.o_binary` (symbols stripped; effort measured in months)
2. write tests on the real machine (**high risk, may hang the GPU**; not recommended)

**At the software level, this chain has been probed as deep as it can go.**
