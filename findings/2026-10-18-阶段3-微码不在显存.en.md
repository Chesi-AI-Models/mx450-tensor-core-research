# Stage 3 · Analysis of the 32 MB VRAM dump: the Falcon microcode is not there

## 1. Analysis method

Signatures were extracted using the gk20a (Kepler) microcode as a reference:

```
fecs_inst.bin : d0 00 10 00 00 fe 04 00 bd a4 7e 2f 3a 00 f8 02
gpccs_inst.bin: d0 00 08 00 00 fe 04 00 bd a4 7e d9 1e 00 f8 02
                    ↑     ↑^^^^^^^^^^^^^^^^^
              stack top   shared 12-byte prefix
```

The cracker community's reverse-engineering notes on AD102 (Ada) FECS also confirm that entry 0x0 is
"stack top + `lcall main`", disassembled with `envydis -m falcon -V fuc6`.

## 2. Scan results

| Check | Result |
|---|---|
| Strong signature `00 fe 04 00 bd a4 7e` (8 bytes) | **0 hits** |
| Relaxed `d0 00 ?? 00` | 215 hits, but every context is a data table (e.g. `d0 00 d1 00 d2 00 d3 00`) |
| High-entropy 4 KB blocks (non-zero ratio > 80%) | 6457 / 8192 |

**Conclusion: the 32 MB dump contains no Kepler-style Falcon microcode.**

## 3. Why (with clear documentary basis)

> "Falcons have **separate instruction and data memories (IMEM/DMEM)** and provide a small
> DMA engine (via the FBIF - 'Frame Buffer Interface') to load code from system memory."
> — kernel.org `gpu/nova/core/falcon.html`

**Falcon microcode is loaded into the Falcon's own IMEM (internal SRAM), not into VRAM.**

The 32 MB we dumped is **the GSP's runtime data region** (containing firmware copies, heaps, table structures),
not a microcode storage area.

## 4. Obstacles to reading IMEM

> "**Heavy Secure (HS)**: In this mode, the microprocessor is a **black box** — it's not
> possible to read or write any Falcon internal state or Falcon registers from outside
> the Falcon (for example, from the host system)."
> — NVIDIA `Falcon-Security` public documentation

Security mode levels:

| Mode | Who may load | Can the host read/write internal state |
|---|---|---|
| NS (PL0) | no signature required | yes (with limited capability) |
| LS (PL2) | requires HS ucode to load | partially visible (for debugging) |
| **HS (PL3)** | **requires an NVIDIA signature** | **completely invisible** |

Boot chain (isomorphic on Ampere/Turing):

```
hardware BROM → HS ucode (Booter, on SEC2) → LS ucode (GSP-RM, on GSP)
```

FECS/GPCCS are loaded by **the HS FWSEC / devinit**, and very likely run in LS or HS mode.
If HS, then IMEM is completely unreadable from the host.

## 6. Next step (the only remaining direction)

**Attempt to reach IMEM through the Falcon registers:**

1. Locate the Falcon register base of FECS / GPCCS within BAR0
   (envytools documents the Falcon register layout, but Turing instance offsets must be confirmed)
2. Read the Falcon's `CPUCTL` / `HWCFG` registers to determine the current security mode
3. If NS/LS → attempt to read IMEM (via `FALCON_IMEMC/IMEMD` or `DMEMC/DMEMD`)
4. If HS → this path is closed; only NVIDIA disclosure or hardware-level means remain

**Pre-check**: reading the `SECURITY_MODE` field of `NV_PFALCON_..._HWCFG` settles it, at very low cost.
