# 🔴 Stage 3 · FECS security mode confirmed: LIGHT SECURE (LS)

## 1. Register read results

After unloading the driver, BAR0 was mmap'd directly and the FECS Falcon instance read (base `0x409000`):

```
CPUCTL  (0x100) = 0x00000010   started=0  halted=1
HWCFG   (0x108) = 0x40204080   IMEM_SIZE field = 128
DMACTL  (0x10c) = 0x00000005   secure_stat=0
HWCFG1  (0x12c) = 0x80104126
```

## 2. HWCFG1 decoding (the key)

`0x80104126`, low byte `0x26 = 0b0010_0110`:

| Field | bits | Value | Meaning |
|---|---|---|---|
| `core_rev` | 3:0 | `0b0110` = 6 | **Falcon v6 (fuc6)** |
| `security_model` | 5:4 | `0b10` = **2** | **LIGHT (LS)** |
| `core_rev_subversion` | 7:6 | `0b00` = 0 | subversion 0 |

## 3. Triple cross-confirmation

1. **`security_model = 2`** → per `dev_falcon_v4.h` and nova-core's `FalconSecurityModel` enum,
   `2 = Light` (0 = None/NS, 2 = Light/LS, 3 = Heavy/HS)
2. **`core_rev = 6`** → consistent with cracker-community reverse-engineering notes on AD102 FECS
   (those notes use `envydis -m falcon -V fuc6`, with all 9797 instructions annotated)
3. **`secure_stat = 0`** (DMACTL bit 7) → not currently in a secure DMA transfer state

**Conclusion: the MX450's FECS Falcon runs in Light Secure mode, not Heavy Secure.**

## 4. What this means

NVIDIA's official description of LS:

> "**Light Secure (LS)**: In this mode, the microprocessor has more privileges than NS but
> fewer than HS. **Some of the microprocessor state is visible to host software to ease
> debugging.** The only way to enable this mode is by HS microcode enabling LS mode."

Contrast with HS:

> "**Heavy Secure (HS)**: the microprocessor is a **black box** — it's **not possible to read
> or write any Falcon internal state or Falcon registers from outside the Falcon**."

**This is the most important judgement reversal of the night**:

- If HS → IMEM is completely unreadable, and this path ends immediately
- **Actually LS → part of the internal state is visible to the host, so IMEM may be readable**

## 5. Current obstacle: unloading the driver resets the Falcon

```
IMEM ports 0-3:  IMEMC=0  IMEMD=0  IMEMT=0
DMEM ports 0-3:  DMEMC=0  DMEMD=0
CPUCTL: halted=1, started=0
```

**Unloading the driver resets the Falcon and the microcode is cleared from IMEM.**

So to read IMEM, BAR0 must be accessed **while the driver is running** — the same contradiction as stage P3,
with the same clear resolution: **use a kernel module and `ioremap`**.

## 6. Next step (the only action)

Write `mx450_p4.c` to, while the driver runs:

1. `ioremap(BAR0 + 0x409000, 0x1000)`
2. Read `HWCFG1 (0x12c)` to confirm it is still LS (it may differ while the driver runs)
3. Read the current `IMEMC (0x180)` value and inspect the `secure` bit (bit 28)
4. If `secure=0`:
   - set `IMEMC = offs` (low 16 bits are the block/word offset)
   - read `IMEMD (0x184)` to obtain the instruction word
   - dump IMEM block by block
5. If `secure=1`: secure IMEM is unreadable in LS mode, another route is needed

**Risk**: writing `IMEMC` changes the Falcon's access-port state. Mitigations:
- read the current value first
- save the original value and restore it after reading
- prefer port 3 (usually unused by the driver)
