# 2026-10-18 · Stage 3: PRAMIN channel discovered and first validated

## 1. Web-search verification (the result of searching at every step)

### Check 1 · Why BAR1 reads all zero (the real reason)

> "The GPU's internal page tables only have **~16 MiB of BAR1 mapped (just the display
> framebuffer)**. Reads from the rest return zeros."
> — analysis from the nbd-vram project

**It is not D3cold; the GPU's internal page tables map only the 16 MB framebuffer.** The earlier hypothesis of "wake the GPU and read again" does not hold.

### Check 2 · The P2P channel is closed on consumer cards

> "`nvidia_p2p_get_pages_persistent`... **the NVIDIA driver returns EINVAL on consumer
> GeForce GPUs**. Both persistent and non-persistent variants, both flag values.
> It's gated at the RM level for Quadro/datacenter SKUs only, regardless of driver version."

### Check 3 · The PRAMIN channel exists and is used by NVIDIA itself

In NVIDIA's new Rust driver **nova-core**:

```rust
const PRAMIN_BASE: usize = 0x700000; // PRAMIN is always at BAR0 + 0x700000
const PRAMIN_SIZE: usize = 0x100000; // 1MB aperture
```

Official documentation ([PATCH 09/12] docs: gpu: nova-core):

```
PRAMIN Window Operation
=======================
1 MiB sliding aperture, repositioned over the entire VRAM address space
using NV_PBUS_BAR0_WINDOW register (0x1700):

 31:26 | 25:24  | 23:0
 RSVD  | TARGET | BASE_ADDR (bits 39:16 of VRAM address)

TARGET: 0x0 = VRAM, 0x1 = SYS_MEM_COH, 0x2 = SYS_MEM_NONCOH

actual_vram_addr = (BASE_ADDR << 16) + pramin_offset
```

The local `open-gpu-kernel-modules` headers confirm the same:
`NV_PRAMIN 0x007FFFFF:0x00700000 /* RW--M */` (present from Maxwell through Blackwell).

## 2. Local measurement 1 · the window is readable

```
[NV_PBUS_BAR0_WINDOW @0x1700] = 0x00007FF0
  TARGET    = 0  (VRAM)
  BASE_ADDR = 0x007FF0
  => the window currently covers VRAM 0x007FF00000 (the tail of 2 GB of VRAM)
```

**The PRAMIN mechanism is confirmed present on this machine, and the register is readable.**

## 3. Local measurement 2 · the window is writable, but reads come back all zero

Scanning the first 256 MB (sampling 4 KB per 1 MB):

```
regions with data: 0 / 256
WINDOW restored to 0x00007FF0
```

- Writing `0x1700` produced no error (the window moved successfully)
- But every window read returned all zeros
- The original window value was restored afterwards, and the driver reloaded normally

## 4. Key judgement: the all-zeros result was caused by the test conditions

**This test unloaded the nvidia driver** (otherwise BAR0 is occupied and cannot be mmap'd).

When the driver unloads, NVIDIA scrubs VRAM (a security policy), so the whole VRAM is zero anyway —
this has nothing to do with whether the PRAMIN mechanism works.

**This also explains a second reason for BAR1 reading zero**: not only do the page tables map just 16 MB,
but after unloading the driver the VRAM content itself has already been cleared.

## 5. Conclusion: access must happen while the driver runs

| Condition | BAR0 mmap (user space) | Kernel-module ioremap |
|---|---|---|
| driver running | ❌ occupied, EBUSY | ✅ mappable |
| driver unloaded | ✅ mappable | ✅ mappable |
| VRAM contents | ❌ already scrubbed | ✅ preserved |

**The only viable path: write a kernel module that `ioremap`s the 0x700000 region of BAR0 while the driver runs,
then read VRAM through the PRAMIN window.**

## 6. Next steps

1. The module receives the BAR0 physical address via `module_param` (read from `/sys/bus/pci/devices/*/resource`)
2. Inside the module, `ioremap(BAR0 + 0x700000, 0x100000)` maps the PRAMIN window
3. Also `ioremap(BAR0 + 0x1700, 4)` to read/write the window register
4. Keep the nvidia driver loaded (GPU powered, VRAM holds content)
5. Move the window to scan VRAM, searching for FECS/GPCCS microcode signatures

**Risk**: concurrent access to BAR0 registers alongside the driver may conflict. Requirements:
- read-only as the primary mode
- restore the original window value after each read
- avoid accessing while the driver is manipulating PFB/PBUS

## 7. Environment state after this round

- Driver restored, `nvidia-smi` normal
- WINDOW register restored to its original value `0x00007FF0`
- No other GPU state was modified
- Every operation is rollback-capable
