# 2026-10-18 · 階段 1 補記 5：GSP 韌體的 vBIOS 憑證驗證鏈（決定性證據）

## 發現

在 `/lib/firmware/nvidia/580.142/gsp_tu10x.bin`（30 MB，Turing GSP 韌體）中，
檢索到一組 **vBIOS 驗證錯誤碼**，來自 `FWSECLIC`（Firmware Security License）模組：

```
vbios
vbios000
NV_UDE_ERR_VBIOS_VERIF_COMPLETED_AND_FAILED
NV_FWSECLIC_ERR_CODE_CMD_VBIOS_VERIFY_DEVID_FAIL
NV_FWSECLIC_ERR_CODE_CMD_VBIOS_VERIFY_CERT_NOT_FOUND
NV_FWSECLIC_ERR_CODE_CMD_VBIOS_VERIFY_CERT_PARSE_FAIL
NV_FWSECLIC_ERR_CODE_CMD_VBIOS_VERIFY_CERT_VERIFY_FAIL
NV_FWSECLIC_ERR_CODE_CMD_VBIOS_VERIFY_HAT_FAIL
NV_FWSECLIC_ERR_CODE_CMD_VBIOS_VERIFY_BIOS_SIG_FAIL
NV_FWSECLIC_ERR_CODE_CMD_VBIOS_VERIFY_HULK_INIT_FAIL
```

## 這條證據說明什麼

這不是「某處可能校驗」的推測，而是**韌體裡現成的錯誤碼列舉** —— 每一條都對應一個校驗環節：

| 錯誤碼 | 校驗環節 |
|---|---|
| `VERIFY_DEVID_FAIL` | 裝置 ID 與 vBIOS 宣告是否一致 |
| `VERIFY_CERT_NOT_FOUND` | 是否攜帶簽章憑證 |
| `VERIFY_CERT_PARSE_FAIL` | 憑證格式是否合法 |
| `VERIFY_CERT_VERIFY_FAIL` | **憑證鏈是否可驗通** |
| `VERIFY_BIOS_SIG_FAIL` | **vBIOS 映像簽章是否匹配** |
| `VERIFY_HAT_FAIL` | 雜湊樹 / Hash-and-Trim 校驗 |
| `VERIFY_HULK_INIT_FAIL` | 安全初始化階段失敗 |
| `VERIF_COMPLETED_AND_FAILED` | 整個驗證流程失敗 |

**結論：vBIOS 在載入前要過完整的憑證鏈 + 映像簽章 + 雜湊樹驗證。**

## 這直接解釋了三個此前的實測現象

1. **為什麼改 vBIOS 不可能** —— 不是「難」，是簽章校驗會把任何改動判為 `BIOS_SIG_FAIL`。
   沒有 NVIDIA 私鑰，改出來的映像無法被 GSP 接受。
2. **為什麼 `cmpunlocker` 必須走 Falcon 漏洞** —— 因為它繞過的正是「載入器在驗簽之前先拷貝資料」
   這個時序缺陷，而不是嘗試偽造簽章。
3. **為什麼 `nvidia-smi` 能報 VBIOS 版本而 PCI ROM BAR 讀不到** —— vBIOS 由 GSP／韌體側持有並驗證，
   不透過 PCI Option ROM 機制向系統暴露。

## 至此，完整的四層防線

```
┌─ ① 硬體層 ───────────────────────────────────────────┐
│ GPU 無獨立 SPI Flash                                  │
│   卸載驅動後 PCI ROM BAR 回傳 EIO（0 位元組）          │
├─ ② 韌體層（系統）───────────────────────────────────┤
│ Intel Boot Guard：BIOS 關鍵區域簽章 + 加密            │
│ 24 MB dump 中無 VFCT 表、無 _ROM 方法、無明文 PCIR     │
├─ ③ 韌體層（GPU）────────────────────────────────────┤
│ GSP FWSECLIC：vBIOS 憑證鏈 + 映像簽章 + 雜湊樹驗證    │
│   ← 本輪新發現，是最直接的一條                        │
├─ ④ 驅動層 ───────────────────────────────────────────┤
│ NVML 不暴露 TC 計數                                    │
│ CUPTI metric 列舉 rc=38                                │
│ 私有 ioctl 物件級隔離（佔位句柄 0xcaf0xxxx）           │
└──────────────────────────────────────────────────────┘
```

**四層，四個不同的技術手段，每一層單獨就足以封死一條路徑。**

## 對解鎖可能性的最終判斷

| 要改的東西 | 攔路的那一層 | 可否繞過 |
|---|---|---|
| vBIOS 映像（devinit / 限速配置） | ③ GSP 憑證驗證 | 僅可能透過載入器時序漏洞（Falcon 類），需自研 |
| 系統 BIOS 中的 VGA 模組 | ② Boot Guard | 需要 Intel／聯想私鑰，**不可能** |
| 執行時暫存器（SS/PLM 類） | ④ 驅動物件模型 + ③ PLM 權限 | 需先知道 Turing 的暫存器位址（**未知**） |
| 顯示記憶體容量 | 硬體（顆粒焊死） | **不可能** |

**四條路徑，兩條物理不可能，兩條需要目前不存在的信息／漏洞。**

## 尚未嘗試的一條

`vbios000` 這個字串暗示韌體內可能存在一個名為 `vbios000` 的句柄／分區。
若能在 GSP 啟動後透過 mailbox 查詢該物件，或許能取到**已解密的 vBIOS 映像**用於靜態分析
（注意：拿到映像也不等於能改，見上表）。

這需要解析 GSP 的 RPC 協定，工作量較大，且不改變「改不了」的結論。
