# P2 第三阶段：尾调用确认与完整函数集

## 一、联网核查结果（本节修正此前两项推断）

### 核查 1 · 函数原型（已确认）

DeepWiki 对 `os-interface.c` 的解读：

```
Kernel Space Mapping — os_map_kernel_space() 按 cache 属性映射物理内存
  Cached         NV_MEMORY_CACHED          nv_ioremap_cache()
  Write-Combined NV_MEMORY_WRITECOMBINED   nv_ioremap_wc() / nv_ioremap_nocache()
  Uncached       NV_MEMORY_UNCACHED        nv_ioremap_nocache()
  Default        NV_MEMORY_DEFAULT         nv_ioremap_nocache()
```

### 核查 2 · **此前的参数数量推断有误：实际是 4 个参数**

`src/nvidia/arch/nvalloc/unix/src/osapi.c` 中的真实调用：

```c
reg_mapping = osMapKernelSpace(nv->regs->cpu_address,   /* 物理地址 */
                               os_page_size,             /* 大小 */
                               NV_MEMORY_UNCACHED,       /* cache_type */
                               NV_PROTECT_READABLE);     /* protect */
```

**四个参数**。而我反汇编的 `os_map_kernel_space` 只看到 `rdi`/`rsi`/`edx` 三个
（未见 `ecx` 的使用），说明：

- `osMapKernelSpace`（4 参数）是 public API 层
- `os_map_kernel_space`（3 参数）是其下层内核实现
- 我读的是后者，**签名需按 3 参数理解，protect 在更上层处理**

## 二、尾调用目标已确认

`os_map_kernel_space` 中 `cache_type == 0` 分支尾调用 `0xffffffffb04a4730`：

```
$ grep -E "^ffffffffb04a47" /proc/kallsyms
ffffffffb04a4700 T ioremap_encrypted
ffffffffb04a4720 T __pfx_ioremap_cache
ffffffffb04a4730 T ioremap_cache          ← 目标
ffffffffb04a4750 T __pfx_ioremap_prot
ffffffffb04a4760 T ioremap_prot
```

**结论：`os_map_kernel_space` 是对内核 `ioremap` 系列的薄封装。**
这与 NVIDIA 开源代码的结构完全吻合。

## 三、⚠ 未解的矛盾（调用前必须澄清）

反汇编显示 **`cache_type == 0` → `ioremap_cache`**。

但 NVIDIA 惯例是 `NV_MEMORY_UNCACHED = 0`，若如此则应调用 `ioremap_uc` / `ioremap_nocache`。

**二者必有一错**，可能原因：

| 假设 | 说明 | 验证方法 |
|---|---|---|
| A. 枚举值并非 UNCACHED=0 | 该版本 `NV_MEMORY_*` 数值与我记忆不同 | 从 580.142 的 `nvtypes.h` 读取真实枚举 |
| B. 读取起点偏移 | 0x...bc0 可能是某个 thunk 而非真入口 | 对比 `__pfx_`（+0x10）与本体 |
| C. `ioremap_cache` 语义差异 | 6.x 内核中该函数行为改变 | 查内核源码 `arch/x86/mm/ioremap.c` |
| D. 该分支不是 cache_type 分派 | 我误读了 edx 的用途 | 逐条核对指令语义 |

**在澄清之前不得调用该函数** —— 用错 cache 属性映射 GPU 内存可能导致一致性错误、
数据损坏，甚至 GPU 挂起。

## 五、`nv_al_*` 系列不存在

`grep -oE "nv_al_[a-z_]+" /proc/kallsyms` → **零结果**。

说明 `nv_al_add_mapping` 这类函数名不正确，或被内联/改名为其他形式。
地址空间管理走的是 `os_*` 抽象层，不是 `nv_al_*`。
