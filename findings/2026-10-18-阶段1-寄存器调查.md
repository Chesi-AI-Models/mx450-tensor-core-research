# 2026-10-18 · 阶段 1 首轮：Turing 寄存器调查

> 环境：LYLNAS / fnOS (Debian 12) / kernel 6.18.18 / 驱动 580.142 / MX450 `10de:1f97`

## 一、本轮动作

1. `gh` 检索 `NVIDIA/open-gpu-kernel-modules`（Turing+ 开源内核模块）
2. 拉取 `src/common/inc/swref/published/turing/tu102/` 下的寄存器头文件
3. 逐个检索 fuse / FBPA / GSP / PLM / TENSOR 相关定义

## 二、拉取的文件

| 文件 | 行数 | 内容 |
|---|---|---|
| `dev_fuse.h` | 35 | 熔丝寄存器（仅 2 个） |
| `dev_fbpa.h` | 29 | FBPA（仅 ECC 计数） |
| `dev_gsp.h` | 68 | GSP Falcon mailbox / queue / EMEM |

留档于 `refs/nvidia-swref/`。

## 三、关键发现

### 发现 1 · `dev_fuse.h` 里没有任何 Tensor Core 相关熔丝

全文只有两条：

```c
#define NV_FUSE_OPT_SECURE_GSP_DEBUG_DIS   0x0002174C  /* RW-4R */
#define NV_FUSE_OPT_NVDEC_DISABLE          0x00021378  /* RW-4R */
```

- 权限标记 `RW-4R` = 读/写、32 位 —— **熔丝寄存器在驱动层是可访问的**，不是完全黑箱
- **但没有 TC 能力位**。如果 TC 是被 OTP 熔断，理论上应有一条类似 `NV_FUSE_OPT_TENSOR_DISABLE` 的定义

**推论**：TU117 的 TC 限速**很可能不通过 fuse 实现**。这削弱了「A 类（物理熔断）」假设，
但同时也没有给出「B 类（寄存器可改）」的地址。

### 发现 2 · Turing 的 FBPA 头文件里没有 CFG1

`cmpunlocker` 在 GA100 上改的是：

```
FBPA_CFG1 (0x009A0204) = 0x02779000   # 64GB HBM2e 几何
```

而 `tu102/dev_fbpa.h` 全文只有：

```c
#define NV_PFB_FBPA_0_ECC_DED_COUNT(i)  (0x00900488+(i)*4)  /* RW-4A */
```

- 地址前缀 `0x00900xxx` 与 GA100 的 `0x009A0xxx` 不同段
- **没有 CFG1 / PLM 定义**

**推论**：显存几何配置不在开源头文件的公开范围内。对 MX450 而言这无关紧要
（显存是物理焊死的 2GB），但它说明**「按 CMPUnlocker 的地址表直接照搬」在 Turing 上不成立**。

### 发现 3 · Turing 目录下检索不到 PLM

`gh search code "PLM" --repo NVIDIA/open-gpu-kernel-modules` 在 Turing 路径下**零命中**。

CMPUnlocker 的核心是打开 4 个 PLM 寄存器（`FEAT_PLM` / `FBPA_PLM` / `WPR_PLM` / `WPR_CFG`），
而 Turing 的开源代码里没有这套东西。

**推论**：要么 Turing 用别的机制做权限隔离，要么这部分完全在闭源 GSP 微码里。两种情况下，
**CMPUnlocker 的注入目标地址在 Turing 上都不可用**。

### 发现 4 · `dev_gsp.h` 暴露了 Falcon 通信接口

```c
#define NV_PGSP                         0x113fff:0x110000
#define NV_PGSP_FALCON_MAILBOX0         0x110040   /* RW-4R */
#define NV_PGSP_FALCON_MAILBOX1         0x110044   /* RW-4R */
#define NV_PGSP_QUEUE_HEAD(i)           (0x110c00+(i)*8)
#define NV_PGSP_QUEUE_TAIL(i)           (0x110c04+(i)*8)
#define NV_PGSP_EMEMC(i)                (0x110ac0+(i)*8)
#define NV_PGSP_EMEMD(i)                (0x110ac4+(i)*8)
```

**这是本轮最有价值的收获。** Turing 是 NVIDIA 第一个引入 GSP 的世代，
GSP 固件通过这组 mailbox/queue 与 host 通信，并且有直接访问 EMEM（外部内存）的通道。

`cmpunlocker` 的原理就是**在 GSP-RM 启动之前**篡改其签名段，从而劫持执行流。
MX450 上同样存在 `PGSP` 这组接口 —— **注入入口在物理上是存在的**。

### 发现 5 · 驱动有查询 TC 数量的控制命令（未使用）

```c
#define NV0080_CTRL_GR_INFO_INDEX_TENSOR_CORE_COUNT   (0x00000023)
// "This index is used to return the number of Tensor Cores"
```

说明 GR 引擎知道这块芯片有多少 TC。若能把该值读出来：

- 报 56（14 SM × 4）→ TC 被硬件承认，只是限速 → **B 类假设成立**
- 报 0 → TC 在驱动层就被判定为不可用 → **接近 A/D 类**

读取需要走 `NV2080_CTRL` ioctl（NVML 私有接口），本轮未实现。
**这是下一轮优先级最高的动作** —— 它是判定锁性质的直接证据。

## 四、本轮结论

| 假设 | 本轮证据 | 判断 |
|---|---|---|
| A. OTP eFuse 熔断 | fuse 头文件无 TC 位 | **减弱**（但可能未公开） |
| B. 寄存器级 throttle | 未找到 Turing 的 SS/PLM 定义 | **待验证**（需 TC 计数） |
| C. devinit 表配置 | 需 dump 系统 BIOS | 未开始 |
| D. 硬件设计低速率 | NVIDIA 论坛称「throttled throughput」 | **仍可能** |

**净收获**：确认 CMPUnlocker 的寄存器地址表**不能照搬**（Turing 命名空间不同），
但确认了 **GSP Falcon 注入通道存在**（`NV_PGSP`），这为后续提供了唯一的可行入口。

## 五、下一轮计划

1. **读取 TC 数量**（`NV2080_CTRL_GR_INFO_INDEX_TENSOR_CORE_COUNT`）
   → 直接判定 B 类是否成立
2. 若 B 成立：在 Turing 命名空间中定位 SM 级 throttle 寄存器
3. 若 B 不成立：转向 dump 系统 BIOS，解析 devinit 表
4. 同时补：`dev_ltc.h`（L2）、`dev_sec_pri.h`（SEC2）的完整审查
