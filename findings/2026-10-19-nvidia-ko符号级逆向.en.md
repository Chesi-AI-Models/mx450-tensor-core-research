## 5. Discovery: the Falcon / RISC-V dispatch logic

```asm
655b1a: mov  0x640(%r13),%eax     ; read the architecture identifier field
655b21: sub  $0x2,%eax
655b24: cmp  $0x1,%eax
655b27: jbe  657c32               ; value ∈ {2,3} → take the RISC-V microcode path
655b2d: movq $0x0,0x40(%rbp)      ; otherwise → take the Falcon microcode path
655b35: mov  $0x0,%rsi            ; ← relocation placeholder: GRCTX_UCODE_DATA_FECS
```

**This directly corroborates the project's measured conclusions:**

| Architecture | Microcode type | Basis |
|---|---|---|
| Turing (TU117) | **Falcon fuc6** | the 32 KB / 16 KB we dumped are both fuc6 instructions |
| Ampere+ | **RISC-V** | the `arch ∈ {2,3}` branch loads RISCV ucode |

**`0x640(%r13)` is the architecture enum field; `{2,3}` corresponds to the RISC-V generations.**

## 7. Empirical verification: `0x40A600` is a GPC-level status register

Reading BAR0 with the GPU at full load:

```
0x40a600 = 0x1F801FC2   ← GPC0
0x40a604 = 0x1F801000
0x40a608 = 0x1F801000
0x40a60c = 0x1F801000
0x40a610 = 0x1F801FC2   ← GPC1 (identical to GPC0)
0x40a614 = 0x1F801000
0x40a618 = 0x1F801000
0x40a61c = 0x1F801000
0x40a620 - 0x40a66c = 0x00000000   ← the remaining 5 groups are all zero
```

**Structure interpretation:**

- the array is allocated for a **maximum of 7 GPCs** (matching larger dies such as GA102)
- **TU117 has only 2 GPCs**, so only the first 2 groups hold data
- 4 registers per group, stepping `0x10`
- within a group the 0th is status (`0x1F801FC2`) and the 1st–3rd are configuration (`0x1F801000`)

**This is a GPC-level status register, not Tensor Core configuration.**

## 8. The fundamental conclusion of this round

### What is now confirmed

| # | Conclusion | Evidence |
|---|---|---|
| 1 | nvidia.ko's symbol table is complete (46,614) | `readelf -s`; exact match with kallsyms addresses |
| 2 | the GR context layout is constructed by `_nv033210rm` | all 186 GRCTX strings located to that function |
| 3 | **Turing uses Falcon microcode, Ampere+ uses RISC-V** | the `0x640(%r13) ∈ {2,3}` branch |
| 4 | **the `0x20000` segment has no address table on the host side** | full `.rodata` scan; only numeric tables found |
| 5 | the `0x400000` segment has 18 genuine address tables | including `0x409C18` (FECS↔GPCCS handshake) |
| 6 | `0x40A600` is GPC-level status, 7 groups sized for the max GPC count | BAR0 measurement; first 2 groups valid |

### Final judgement (consistent with earlier, but now backed by closed-source HAL evidence)

**The `0x20000` segment is Falcon IO space, not a host-visible GR register.**

Three pieces of evidence:

1. **`.rodata` contains no address table for the `0x20000` segment** (only numeric tables such as geometric sequences)
2. **the GR context's register lists contain only the `0x400000` segment** (18 tables, all in that segment)
3. **the microcode accesses the `0x20000` segment with `bit31=0` `iowr`, and the `0x400000` segment with `bit31=1`**
   (GPCCS's `0x201` subroutine)

**Three independent lines of evidence point to the same conclusion: not even NVIDIA's own driver treats the
`0x20000` segment as a host-accessible register range.**
