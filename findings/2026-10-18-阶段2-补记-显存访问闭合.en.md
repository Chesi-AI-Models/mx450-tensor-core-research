# 2026-10-18 · Stage 2 addendum: VRAM access attempts (all three channels closed)

## Goal

Capture the FECS / GPCCS microcode from a running GPU's memory, disassemble it, and look for Tensor Core
control logic. This was the last untried direction at the software layer.

## Channel 1 · `/dev/mem`

```
crw-r----- 1 root kmem 1, 1 /dev/mem
kernel config: CONFIG_STRICT_DEVMEM=y
        CONFIG_IO_STRICT_DEVMEM=y
```

- `dd if=/dev/mem bs=1M skip=393216 count=16` → **0 bytes copied**
- `os.lseek(fd, 0x6020000000); os.read(fd, 1MB)` → **EFAULT (Bad address, errno 14)**

**Verdict**: with `STRICT_DEVMEM=y`, `/dev/mem` only permits access to the legacy IO region; PCI MMIO ranges are denied.

## Channel 2 · `mmap` BAR1

BAR resource layout:

```
BAR0: 0x000000005f000000 - 0x000000005fffffff   (256 MB, control registers)
BAR1: 0x0000006020000000 - 0x000000602fffffff   (256 MB, VRAM window)
```

`mmap /sys/bus/pci/devices/0000:2c:00.0/resource1` **succeeded**; the segment-by-segment scan gave:

```
offset          non-zero bytes    ratio
(all 64 × 4MB segments empty)

segments with data: 0 / 64
```

**Verdict**: the 256 MB window is **all zeros**.

Cause analysis:
1. **The MX450 is an Optimus discrete GPU**; `nvidia-smi` shows 0% utilization and no processes → the GPU is in
   **D3cold**, VRAM is fully powered down and its contents are not visible
2. NVIDIA's BAR1 is not a "linearly readable VRAM window"; access must go through the PRAMIN / paged-window
   mechanism rather than a linear mmap

## Channel 3 · kernel module (not implemented)

To actually read the GPU's internal SRAM (Falcon IMEM/DMEM) or an arbitrary VRAM region you need:

- to compile a kernel module
- to establish a mapping through NVIDIA's kernel API (`os_alloc_mem` / `nv_al_add_mapping` etc.)
- or to operate the GPU's PRAMIN window directly

**This is no longer "user-space reverse engineering" but driver-level kernel development. The effort is measured
in months, and requires kernel headers plus a kernel debugging environment.**

## Final state of the three channels

| Channel | Result | Obstacle |
|---|---|---|
| `/dev/mem` | ❌ EFAULT | `CONFIG_STRICT_DEVMEM=y` |
| BAR1 mmap | ❌ all zeros | GPU in D3cold + BAR1 is not a linear VRAM window |
| kernel module | not implemented | requires driver-level kernel development |

## The end of the software layer

At this point **every** path starting from user space has been exhausted:

| # | Layer | Means | Result |
|---|---|---|---|
| 1 | user-space API | NVML | does not expose TC fields |
| 2 | user-space API | CUPTI metric | `rc=38`, zero metrics (even with permissions opened) |
| 3 | user-space API | private ioctl | ROOT_CLIENT works, DEVICE_0 returns a placeholder handle |
| 4 | system firmware | BIOS dump | Boot Guard encrypted, no VFCT / no `_ROM` |
| 5 | GPU firmware | vBIOS extraction | GSP FWSECLIC certificate-chain verification |
| 6 | GPU firmware | GSP disassembly | fully parsed, but **contains no TC control logic** |
| 7 | VRAM | /dev/mem | rejected by STRICT_DEVMEM |
| 8 | VRAM | BAR1 mmap | all zeros |
| 9 | SM microcode | filesystem | Turing microcode is not on disk (only Kepler's is) |

**Nine paths, nine closures.**

## Conclusion

The Tensor Core throttling control point lies in **FECS/GPCCS microcode + hardware configuration**, and both:

- the microcode is **baked into the GPU** (not provided through the filesystem)
- accessing it requires a **driver-level kernel module**, and even when read, the microcode is protected by
  **FWSEC signature verification** and cannot be replaced

**This is not "no method has been found yet" — it is "the method requires capabilities beyond the software layer,
and even with them, nothing can be rewritten".**
