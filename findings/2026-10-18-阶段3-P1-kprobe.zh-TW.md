# 2026-10-18 · 階段 3 · P1：kprobe 繞過（部分成功 + 方案修正）

## 目標

繞過 `kallsyms_lookup_name` 自 Linux 5.7 起不再匯出的限制，用它查詢 NVIDIA 核心模組的內部符號位址。

## 實作

`kernel/mx450_p1.c`：

```c
struct kprobe kp = { .symbol_name = "kallsyms_lookup_name" };
register_kprobe(&kp);
kln_addr = (unsigned long)kp.addr;      /* 取得真實位址 */
unregister_kprobe(&kp);
kln = (kln_t)kln_addr;                  /* 轉型後呼叫 */
kln("os_map_kernel_space");              /* 查目標符號 */
```

## 結果 1 · QEMU 隔離環境：完全成功

```
kernel: 6.18.18.c1126-trim
mx450_p1: kallsyms_lookup_name resolved @ 0xffffffffb37e9404
mx450_p1: os_map_kernel_space = (not present)
mx450_p1: nv_al_add_mapping   = (not present)
mx450_p1: probe complete
rc=0
```

- **kprobe 技術在 fnOS 6.18 核心上有效**
- `kallsyms_lookup_name` 位址成功取得並可呼叫
- nvidia 符號「not present」是預期（虛擬機內未載入 nvidia 模組）

## 結果 2 · 宿主機：核心 oops

```
Segmentation fault (rc=139)
mx450_p1: kallsyms_lookup_name resolved @ 0xffffffffa65e9404
 mx450_p1_init+0x92/0xff0 [mx450_p1]
```

**位址取到了，但呼叫 `kallsyms_lookup_name` 時崩潰（+0x92）。**

### 差異分析

| 環境 | 符號表規模 | 結果 |
|---|---|---|
| QEMU（無 nvidia） | 小 | ✅ 成功 |
| 宿主機（含 nvidia，46294 個符號） | 大 | ❌ oops |

**推測原因**：`kallsyms_lookup_name` 走訪大符號表時，可能依賴 `kallsyms_lock` / RCU 保護，
在模組 init 上下文中直接呼叫不安全；或該函式的內部實作在 6.18 有變化。

### 系統狀態

- **宿主未重啟**（uptime 2 天 22 小時）
- `nvidia-smi` 正常（MX450, 57°C, 1395MHz）
- `nvidia` / `nvidia_uvm` / `nvidia_drm` 模組狀態正常
- 遺留：`mx450_p1` 與 `mx450_probe` 各 12 KB，標記 `in use`，`rmmod` 與 `rmmod -f` 均失敗，
  **僅重啟可清除**

## 關鍵修正：根本不需要 kallsyms_lookup_name

排查時發現：**`/proc/kallsyms` 對 root 完全可讀**，符號位址本來就擺在那裡。

```bash
# 本機實測（無需任何模組）
$ grep -E "os_map_kernel_space|nv_al_add_mapping" /proc/kallsyms
ffffffffc2c13bb0 t __pfx_os_map_kernel_space	[nvidia]
```

**所以正確方案是**：

1. 使用者態讀 `/proc/kallsyms` 取得目標符號位址
2. 透過模組參數把位址傳進去（`module_param`）
3. 模組直接用該位址轉型呼叫，**全程不碰 `kallsyms_lookup_name`**

**好處**：
- 避開了導致 oops 的函式
- 位址來源透明可稽核（能直接看到 `[nvidia]` 歸屬）
- 可以先用 `cat /proc/kallsyms` 確認符號存在，再決定是否載入模組

## P1 結論

| 項目 | 狀態 |
|---|---|
| kprobe 技術可行性 | ✅ 已驗證（QEMU） |
| 宿主機呼叫 `kallsyms_lookup_name` | ❌ oops，不可用 |
| **符號位址取得** | ✅ **改用 `/proc/kallsyms`，已實測可行** |
| P1 目標（拿到 nvidia 符號位址） | ✅ **實質達成**（位址已在 `/proc/kallsyms`） |

**P1 判定：完成，但方案從「kprobe 動態解析」修正為「使用者態讀 kallsyms + 參數傳入」。**

## 教訓

1. **QEMU 與宿主行為可能不同** —— 符號表規模差異導致同一份程式碼一邊成功一邊崩潰
2. **核心模組崩潰後無法卸載** —— 兩次測試各留一個 12 KB 殭屍模組，只能重啟清除
3. **先找最簡單的辦法** —— 花時間寫 kprobe，而 `/proc/kallsyms` 直接就能讀
4. **移植前先在隔離環境驗證，但隔離驗證通過 ≠ 宿主安全**

## 下一步（P2）

1. 使用者態腳本：從 `/proc/kallsyms` 提取 `os_map_kernel_space` / `nv_al_add_mapping` 等位址
2. 模組透過 `module_param` 接收位址，先做**唯讀驗證**（列印符號附近的記憶體內容，確認位址有效）
3. 確認有效後，再研究函式簽章，嘗試建立 GPU 記憶體對映
