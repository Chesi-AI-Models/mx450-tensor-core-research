# 2026-10-18 · Stage 2: GSP firmware reverse engineering (step one of systematic unsealing)

> This is the first round of deep work after "formal commitment".
> Goal: find the Tensor Core throttling control point inside the GPU firmware.

## 1. Complete parse of the firmware structure

`/lib/firmware/nvidia/580.142/gsp_tu10x.bin` (30 MB) is a **double-layer ELF**:

```
outer: ELF64 relocatable, UCB RISC-V, not stripped (effectively symbol-less)
      ├── .fwimage        29 MB   ← contains a complete nested ELF
      ├── .fwversion      8 B
      └── .fwsignature[*] 3 × 4 KB  ← signature sections (exactly the kind CMPUnlocker exploits)
```

Extracting the inner ELF from `.fwimage` (offset `0x40`):

```
inner: ELF64 executable, UCB RISC-V, RVC, statically linked, stripped
      Entry point: 0x4009000
```

**The inner sections are split by GPU architecture** — this is the key:

| Section | Address | Size | Purpose |
|---|---|---|---|
| `.ga100_data` / `.ga100_text` | 0x4001000 / 0x4005000 | 0x1170 / 0x1414 | Ampere branch |
| `.tu10x_data` / `.tu10x_text` | 0x4003000 / 0x4007000 | 0x1170 / 0x1414 | **Turing branch (this machine takes it)** |
| `.bootstrap` | 0x4009000 | 0x74 | entry |
| `.tu10x_resident_text` | 0x400e000 | 0x3000 | Turing resident code |
| `.manifest` | 0x4012168 | 0xe98 | configuration manifest |
| `.acl` | 0x4012000 | 0x161 | access control list |

## 2. The chip dispatch logic found (`.bootstrap`)

```asm
4009014: lw   t0, 0(t0)          # read PMC_BOOT_0
4009018: srl  t0, t0, 0x14       # >> 20 → chipset field
400901c: and  t0, t0, 511        # take the low 9 bits
4009020: li   t1, 354            # 0x162 TU102
4009024: beq  t0, t1, 0x4009058
         ...
4009040: li   t1, 359            # 0x167 = TU117  ← this machine
4009044: beq  t0, t1, 0x4009058
         ...
4009058: jalr 0x4007000          # jump into .tu10x_text
```

**Perfectly consistent with measurement**: `NV_PMC_BOOT_0 = 0x167000a1`, `>> 20 = 0x167 = 359`.
**This proves the firmware really dispatches by chip ID, and that TU117 takes `.tu10x_text`.**

## 3. Discovery of the GSP's private CSR mechanism

`.tu10x_text` starts with five consecutive non-standard CSR writes:

```asm
csrw 0x7c8, t0    # index / selector
csrw 0x7c9, s0    # enable / status
csrw 0x7ca, s1    # base address
csrw 0x7cb, s2    # length / mask
csrw 0x7cc, t1    # attribute / target address
```

Target addresses appearing alongside: `0xc0a04`, `0xc0600`, `0xc0e00`, `0x4005000`, `0x4000000`.

**This is the channel through which the GSP configures its own address-mapping windows.**

> **⚠ 2026-10-18 21:45 correction (after a web check)**
> The earlier wording "NVIDIA private CSR" was not accurate enough. Third-party analysis of GSP firmware shows that
> GSP runs NVIDIA's own microkernel **LibOS** and uses **PMP (Physical Memory Protection)** for partition isolation —
> a standard RISC-V memory protection mechanism.
> So `0x7c8–0x7cc` is more likely **NVIDIA's wrapper/extension around the PMP configuration CSRs**,
> i.e. "which physical address range is opened to which partition".
> Reference: zerohour.day's analysis of `gsp-535.113.01.bin` (which also confirms Ampere firmware contains four 4 KB
> RSA signature sections, and that Turing's GSP is likewise RISC-V).

## 4. Decisive negative result: Ampere's unlock mechanism does not exist on Turing

Taking the 8 GA100 register addresses used by CMPUnlocker and doing a little-endian search for each in the 29 MB
firmware:

| Register | Address | Result |
|---|---|---|
| SS0 | `0x0082381C` | **absent** |
| SS1 | `0x00823820` | **absent** |
| FEAT_PLM | `0x00823804` | **absent** |
| FBPA_PLM | `0x009A0148` | **absent** |
| FBPA_CFG1 | `0x009A0204` | **absent** |
| MMU_LMR | `0x00100CE0` | **absent** |
| WPR_PLM | `0x001FA7C4` | **absent** |
| WPR_CFG | `0x001FA7CC` | **absent** |

**This is not "the addresses differ" — it is "the mechanism does not exist".**

CMPUnlocker's four-register PLM unlock plus SS0/SS1 throttle release is an **Ampere (GA100)-specific architecture**.
Turing's GSP firmware does not even reference those addresses, showing that generation has no such Platform Lock
Manager mechanism.

## 5. One last key fact: Turing's SM microcode is not on disk

The GSP firmware contains only FECS / GPCCS **error strings** (`FECS & GPCCS FALCONS HAVE…`, `UCODE RESET`),
**not their microcode data**.

The only microcode on the filesystem is from the Kepler generation:

```
/lib/firmware/nvidia/gk20a/fecs_inst.bin     ← Kepler
/lib/firmware/nvidia/gk20a/gpccs_inst.bin    ← Kepler
```

**Turing's FECS/GPCCS microcode is baked into the GPU (ROM / secure region) and is not provided through the filesystem.**

And Tensor Cores sit inside the SM; their scheduling and throttling are controlled by **FECS/GPCCS microcode +
hardware configuration** — **not in the GSP firmware, and not in any readable file.**

## 6. Architectural conclusion

The GPU software stack divides as follows:

```
┌─ GSP firmware (readable, parsed) ──────────────┐
│ manages: GPU global init, scheduling, power, error handling │
│ does NOT manage: configuration of SM-internal units (incl. Tensor Cores) │
├─ FECS / GPCCS microcode (baked into the GPU, unreadable) ─┤
│ manages: microcode scheduling of the SM front end / compute pipeline │
│ Tensor Core behaviour lives here                │
├─ hardware fuses / die wiring ──────────────────┤
│ decides: SM count (14/16), whether TCs are usable │
└────────────────────────────────────────────────┘
```

**Key judgement: the Tensor Core throttling control point is not in any layer we can read or write.**

- not in the GSP firmware (confirmed by search)
- FECS/GPCCS microcode unreadable (baked in)
- hardware fuses unmodifiable

## 7. What this means for "full unlock"

**The software path is closed here.** Not "difficult" — the control point is outside the reach of software:

| Direction attempted | Result |
|---|---|
| user-space APIs (NVML / CUPTI / ioctl) | all three layers clipped/isolated |
| system BIOS (devinit) | Boot Guard encrypted |
| vBIOS modification | GSP certificate-chain verification |
| GSP firmware modification | signature verification; and it **contains no TC control logic** |
| SM microcode modification | **unreadable, unwritable** |
| hardware fuses | **physically irreversible** |

## 8. If one insists on continuing, only these three remain (all outside software)

1. **hardware-level measurement**: use a logic analyser on the SM↔GPC bus to observe the actual execution path of
   HMMA instructions — you can "see" it, but not change it
2. **die decapping + microscopy**: confirm whether the transistors in the TC area were laser-cut
   — establishes "physical removal versus fuse disable", at the cost of destroying a chip
3. **wait for public material**: NVIDIA has never published Turing's GSP/microcode register map; progress would
   require future security research disclosure

## 8.5 Web-check supplement (same round, 21:45)

Three external sources corroborate this round's findings:

1. **RSA signature section count matches**: third-party analysis of `gsp-535.113.01.bin` finds "four 4 KB RSA
   signature sections", while this machine's `gsp_tu10x.bin` has **three 4096-byte `.fwsignature` sections**
   (version difference). Same structural origin.
2. **PMP mechanism**: the GSP microkernel LibOS uses PMP for partition isolation → the `csrw 0x7c8–0x7cc` in
   `.tu10x_text` is PMP configuration, not "mysterious private registers". This further implies that writing to that
   location incorrectly would directly break the GSP's memory isolation.
3. **NVIDIA's public statement**: RISC-V was chosen partly *because* "its isolation and memory protection features
   make this kind of locking easier to implement".
   → the conclusion shifts from "vendor oversight" to "**deliberate design**".
