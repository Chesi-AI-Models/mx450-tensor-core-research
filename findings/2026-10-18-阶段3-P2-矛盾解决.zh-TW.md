# P2 第四階段：NV_MEMORY 列舉確認，cache_type 矛盾解決

## 一、矛盾回顧

反組譯顯示 `os_map_kernel_space` 中 `cache_type == 0` 分支尾呼叫 `ioremap_cache`，
但我此前按記憶認為 `NV_MEMORY_UNCACHED = 0`，二者不符，故暫停呼叫。

## 二、原始碼實證

`gh search code "NV_MEMORY_UNCACHED" --repo NVIDIA/open-gpu-kernel-modules` 定位到：

```
src/nvidia/inc/kernel/os/nv_memory_type.h
kernel-open/common/inc/os/nv_memory_type.h
```

完整列舉（41 行檔案，原樣引用）：

```c
#define NV_MEMORY_NONCONTIGUOUS      0
#define NV_MEMORY_CONTIGUOUS         1
#define NV_MEMORY_CACHED             0
#define NV_MEMORY_UNCACHED           1
#define NV_MEMORY_WRITECOMBINED      2
#define NV_MEMORY_WRITEBACK          5
#define NV_MEMORY_DEFAULT            6
#define NV_MEMORY_UNCACHED_WEAK      7
```

**關鍵：`NV_MEMORY_CACHED = 0`，`NV_MEMORY_UNCACHED = 1`。**

## 三、三方交叉驗證

| edx 值 | 列舉常數 | 反組譯分支行為 | 一致性 |
|---|---|---|---|
| **0** | `NV_MEMORY_CACHED` | 尾呼叫 `ioremap_cache` | ✅ 完全吻合 |
| **2** | `NV_MEMORY_WRITECOMBINED` | `je 0xffffffffc2c13c33` | ✅ |
| **6** | `NV_MEMORY_DEFAULT` | `je 0xffffffffc2c13c4e` | ✅ |
| 其他 | — | 記錄日誌、回傳 NULL | ✅ 與原始碼 default 分支一致 |

**結論：反組譯分析準確無誤；此前的錯誤在於把 0 記成了 UNCACHED。**

## 四、函式入口偏移確認

```
ffffffffc2c13bb0  t __pfx_os_map_kernel_space   ← 16 位元組 CET 前綴
ffffffffc2c13bc0  t os_map_kernel_space         ← 真入口（+0x10）
```

dump 起始位元組為 `0f 1f 40 d6`（多位元組 NOP，GCC 對齊用），而非 `endbr64`
（`f3 0f 1e fa`）—— 說明 endbr64 位於 `__pfx_` 區域內，真函式體從 NOP 對齊開始。

**`0xffffffffc2c13bc0` 確認為函式本體，不是 thunk。**

## 五、最終確認的函式原型

```c
void *os_map_kernel_space(void *phys_addr,   /* rdi */
                          NvU64 size,        /* rsi */
                          NvU32 cache_type); /* edx: 0=CACHED 1=UNCACHED 2=WC 6=DEFAULT */
```

行為：
1. `phys_addr == NULL && cache_type == 0` → 回傳某全域物件（`mov -0x11191531(%rip),%rax`）
2. `phys_addr != NULL`：
   - 檢查 IF 旗標與 `preempt_count()`（**不允許在中斷／原子上下文呼叫**）
   - 按 `cache_type` 分派：0 → `ioremap_cache`；2 → WC 路徑；6 → DEFAULT 路徑
   - 預設：`log(4, ...)` 並回傳 NULL

**註**：4 參數版本 `osMapKernelSpace(addr, size, cache_type, protect)` 是其上層封裝，
`protect` 在更上層處理，不進入該函式。

## 七、目前可否呼叫

**技術上已具備呼叫條件**（位址、簽章、列舉、行為全部確認）。但：

| 風險項 | 說明 |
|---|---|
| 真實操作 GPU 位址空間 | 不是唯讀，會在 ioremap 層建立對映 |
| 參數語意仍有殘餘不確定 | `size` 的對齊要求、`phys_addr` 是否必須頁對齊未驗證 |
| 無法在 QEMU 預演 | 虛擬機無 NVIDIA 模組 |
| 失敗後果 | 可能回傳 NULL（無害），也可能建立錯誤對映導致後續存取異常 |

**建議**：首次呼叫選擇最保守的參數——`cache_type = NV_MEMORY_UNCACHED (1)`
（暫存器存取的標準選擇）、頁對齊位址、`size = PAGE_SIZE`，並立即 `os_unmap_kernel_space` 釋放。
