# 2026-10-18 · 階段 2：GSP 韌體逆向（系統性解封的第一步）

> 這是「正式投入」後的第一輪深度工作。
> 目標：從 GPU 韌體內找 Tensor Core 限速的控制點。

## 一、韌體結構完全解析

`/lib/firmware/nvidia/580.142/gsp_tu10x.bin`（30 MB）是**雙層 ELF**：

```
外層：ELF64 relocatable, UCB RISC-V, not stripped（實為無符號）
      ├── .fwimage        29 MB   ← 內嵌一個完整的 ELF
      ├── .fwversion      8 B
      └── .fwsignature[*] 3 × 4 KB  ← 簽章段（CMPUnlocker 利用的正是這類段）
```

從 `.fwimage` 抽出內層 ELF（偏移 `0x40`）：

```
內層：ELF64 executable, UCB RISC-V, RVC, statically linked, stripped
      Entry point: 0x4009000
```

**內層節區按 GPU 架構分家**——這是關鍵：

| 節區 | 位址 | 大小 | 用途 |
|---|---|---|---|
| `.ga100_data` / `.ga100_text` | 0x4001000 / 0x4005000 | 0x1170 / 0x1414 | Ampere 分支 |
| `.tu10x_data` / `.tu10x_text` | 0x4003000 / 0x4007000 | 0x1170 / 0x1414 | **Turing 分支（本機走這條）** |
| `.bootstrap` | 0x4009000 | 0x74 | 入口 |
| `.tu10x_resident_text` | 0x400e000 | 0x3000 | Turing 常駐程式碼 |
| `.manifest` | 0x4012168 | 0xe98 | 配置清單 |
| `.acl` | 0x4012000 | 0x161 | 存取控制表 |

## 二、找到晶片分派邏輯（`.bootstrap`）

```asm
4009014: lw   t0, 0(t0)          # 讀 PMC_BOOT_0
4009018: srl  t0, t0, 0x14       # >> 20 → chipset 欄位
400901c: and  t0, t0, 511        # 取低 9 位
4009020: li   t1, 354            # 0x162 TU102
4009024: beq  t0, t1, 0x4009058
         ...
4009040: li   t1, 359            # 0x167 = TU117  ← 本機
4009044: beq  t0, t1, 0x4009058
         ...
4009058: jalr 0x4007000          # 跳入 .tu10x_text
```

**與實測完全吻合**：`NV_PMC_BOOT_0 = 0x167000a1`，`>> 20 = 0x167 = 359`。
**證明韌體確實是按晶片 ID 分派，TU117 走 `.tu10x_text`。**

## 三、發現 GSP 的私有 CSR 機制

`.tu10x_text` 開頭是連續 5 條非標準 CSR 寫入：

```asm
csrw 0x7c8, t0    # 索引 / 選擇子
csrw 0x7c9, s0    # 啟用 / 狀態
csrw 0x7ca, s1    # 基底
csrw 0x7cb, s2    # 長度 / 遮罩
csrw 0x7cc, t1    # 屬性 / 目標位址
```

配合出現的目標位址：`0xc0a04`、`0xc0600`、`0xc0e00`、`0x4005000`、`0x4000000`。

**這是 GSP 配置自身位址對映視窗的通道。**

> **⚠ 2026-10-18 21:45 修正（連網核查後）**
> 此前表述為「NVIDIA 私有 CSR」，不夠準確。第三方對 GSP 韌體的分析指出：
> GSP 執行的是 NVIDIA 自研微內核 **LibOS**，並用 **PMP（Physical Memory Protection）**
> 做分區隔離 —— 這是 RISC-V 的標準記憶體保護機制。
> 因此 `0x7c8–0x7cc` 更可能是 **NVIDIA 對 PMP 配置 CSR 的封裝／擴展**，
> 即「把哪段實體位址開放給哪個 partition」。
> 參考：zerohour.day 對 `gsp-535.113.01.bin` 的分析
> （該文同時確認 Ampere 韌體含 4 個 4KB RSA 簽章段，Turing 的 GSP 同為 RISC-V）。

## 四、決定性負結果：Ampere 的解鎖機制在 Turing 上不存在

把 CMPUnlocker 用到的 8 個 GA100 暫存器位址，逐一在 29 MB 韌體裡做小端搜尋：

| 暫存器 | 位址 | 結果 |
|---|---|---|
| SS0 | `0x0082381C` | **未出現** |
| SS1 | `0x00823820` | **未出現** |
| FEAT_PLM | `0x00823804` | **未出現** |
| FBPA_PLM | `0x009A0148` | **未出現** |
| FBPA_CFG1 | `0x009A0204` | **未出現** |
| MMU_LMR | `0x00100CE0` | **未出現** |
| WPR_PLM | `0x001FA7C4` | **未出現** |
| WPR_CFG | `0x001FA7CC` | **未出現** |

**這不是「位址不同」，是「機制不存在」。**

CMPUnlocker 的四暫存器 PLM 打開 + SS0/SS1 限速解除，是 **Ampere（GA100）專屬架構**。
Turing 的 GSP 韌體裡連這些位址都不引用，說明該世代沒有這套 Platform Lock Manager 機制。

## 五、最後一個關鍵事實：Turing 的 SM 微碼不在磁碟上

GSP 韌體內只出現 FECS / GPCCS 的**錯誤字串**（`FECS & GPCCS FALCONS HAVE…`、`UCODE RESET`），
**不包含它們的微碼資料**。

檔案系統裡的微碼只有 Kepler 世代的：

```
/lib/firmware/nvidia/gk20a/fecs_inst.bin     ← Kepler
/lib/firmware/nvidia/gk20a/gpccs_inst.bin    ← Kepler
```

**Turing 的 FECS/GPCCS 微碼固化在 GPU 內部（ROM / 安全區），不透過檔案系統提供。**

而 Tensor Core 位於 SM 內部，其排程與限速由 **FECS/GPCCS 微碼 + 硬體配置** 控制 ——
**不在 GSP 韌體裡，也不在任何可讀檔案中。**

## 六、架構層面的結論

GPU 的軟體堆疊分工是這樣的：

```
┌─ GSP 韌體（可讀、已解析）──────────────────────┐
│ 管：GPU 全域初始化、排程、電力、錯誤處理       │
│ 不管：SM 內部單元（含 Tensor Core）的配置      │
├─ FECS / GPCCS 微碼（固化在 GPU 內部，不可讀）──┤
│ 管：SM 前端 / 運算管線的微碼排程              │
│ Tensor Core 的行為在這裡                       │
├─ 硬體熔絲 / 晶片佈線 ──────────────────────────┤
│ 決定：SM 數量（14/16）、TC 是否可用            │
└────────────────────────────────────────────────┘
```

**關鍵判斷：Tensor Core 的限速控制點，不在我們能夠讀寫的任何一層。**

- GSP 韌體裡沒有（已搜尋證實）
- FECS/GPCCS 微碼不可讀（固化）
- 硬體熔絲不可改

## 七、這對「全面解鎖」意味著什麼

**軟體路徑到這裡已經閉合。** 不是「難」，是控制點不在軟體可及範圍內：

| 嘗試方向 | 結果 |
|---|---|
| 使用者態 API（NVML / CUPTI / ioctl） | 三層均被裁剪／隔離 |
| 系統 BIOS（devinit） | Boot Guard 加密 |
| vBIOS 修改 | GSP 憑證鏈驗證 |
| GSP 韌體修改 | 簽章驗證；且**不包含 TC 控制邏輯** |
| SM 微碼修改 | **不可讀、不可寫** |
| 硬體熔絲 | **物理不可逆** |

## 八、如果仍要繼續，只剩這三條（都不在軟體範圍）

3. **等待公開資料**：NVIDIA 從未公開 Turing 的 GSP／微碼暫存器對映；若未來有安全研究公開，才可能推進

## 八點五、連網核查補充（同一輪，21:45）

三條外部資訊與本輪發現互相印證：

1. **RSA 簽章段數量吻合**：第三方分析 `gsp-535.113.01.bin` 得到「4 個 4KB RSA 簽章段」，
   本機 `gsp_tu10x.bin` 為 **3 個 4096 位元組 `.fwsignature` 段**（版本差異）。結構同源。
2. **PMP 機制**：GSP 微內核 LibOS 用 PMP 做分區隔離 → `.tu10x_text` 裡的 `csrw 0x7c8–0x7cc`
   是 PMP 配置，不是「神祕私有暫存器」。這進一步說明寫錯該處會直接破壞 GSP 的記憶體隔離。
3. **NVIDIA 的公開表述**：RISC-V 被選中，部分原因正是「其隔離與記憶體保護特性讓這類鎖定更容易實作」。
   → 結論從「廠商疏忽」修正為「**刻意設計**」。
