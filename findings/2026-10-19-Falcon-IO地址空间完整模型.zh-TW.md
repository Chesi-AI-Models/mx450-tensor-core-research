# 🔴🔴🔴 2026-10-19 · Falcon IO 位址空間完整模型（架構級發現）

## 一、核心文件（envytools `docs/hw/falcon/io.rst` 第 24-40 行，原樣引用）

```
The addresses are different between falcon and host. From falcon POV, the IO space
is word-addressable 0x40000-byte space. However, most registers are duplicated
64 times: bits 2-7 of the address are ignored. The few registers that don't
ignore these bits are called "indexed" registers. From host POV, the falcon IO
space is a 0x1000-byte window in BAR0. Its base address is engine-dependent.
First 0xf00 bytes of this window are tied to the falcon IO space, while last 0x100
bytes contain several host-only registers. On G98:GF119, host mmio address
falcon_base + X is directed to falcon IO space address X << 6 | HOST_IO_INDEX << 2.
On GF119+, some engines stopped using the indexed accesses. On those, host mmio
address falcon_base + X is directed to falcon IO space address X.

HOST_IO_INDEX is specified in the host-only MMIO register falcon_base + 0xffc:

MMIO 0xffc: HOST_IO_INDEX
  bits 0-5: selects bits 2-7 of the falcon IO space when accessed from host.

Unaligned accesses to the IO space are unsupported, both from host and falcon.
Low 2 bits of addresses should be 0 at all times.
```

## 二、由此建立的完整模型

### Falcon 側

| 項 | 值 |
|---|---|
| IO 空間總大小 | **0x40000 位元組（256 KB）** |
| 位址範圍 | `0x00000 - 0x3FFFF` |
| 對齊要求 | 低 2 位必須為 0（4 位元組對齊） |
| 暫存器複製 | 大多數暫存器複製 64 份，`bits 2-7` 被忽略 |
| 例外 | "indexed" 暫存器不忽略 `bits 2-7`，用它們做索引 |

### Host 側

| 項 | 值 |
|---|---|
| 可見視窗 | **0x1000 位元組（4 KB）**，位於 `falcon_base + 0x000` |
| 視窗內劃分 | `0x000-0xEFF` → Falcon IO 空間；`0xF00-0xFFF` → host-only 暫存器 |
| `HOST_IO_INDEX` | `falcon_base + 0xFFC`，`bits 0-5` 選擇 Falcon IO 的 `bits 2-7` |
| 老式對映（G98:GF119） | `falcon_addr = (host_offset << 6) \| (HOST_IO_INDEX << 2)` |
| 新式對映（GF119+ 部分引擎） | `falcon_addr = host_offset` |

### 關鍵結論

**`HOST_IO_INDEX` 的 6 個 bit 只能選擇 `bits 2-7`，即「第幾個副本」。**

**它無法選擇 `bits 8+`——而 `bits 8+` 才是「哪個暫存器」。**

**因此 host 最多只能存取 Falcon IO 空間的最低 4 KB（`0x0000-0x0FFF`）。**

**`0x20000` 段（`bits 17:8` 非零）對 host 永久不可見。**

## 三、這解釋了此前所有的矛盾

| 現象 | 解釋 |
|---|---|
| 微碼 iowr `0x20000` 段 376 次（85%） | 合法的 Falcon IO 位址，在 256 KB 空間內 |
| BAR0 `0x020000` 讀回 `0xBADF5040` | host 視窗只有 4 KB，`0x20000` 遠超視窗 |
| `HOST_IO_INDEX` 無法幫上忙 | 只能選 `bits 2-7`，選不到 `bits 17:8` |
| `0x409818` 在 BAR0 裡有效 | **不是** Falcon IO 位址，而是外部 BAR0 位址（見下節） |
| 五種假設全部失敗 | 因為前提錯了——它不是 BAR0 位址，也不是 UAS/XFER/DMEM |

## 四、GPCCS 微碼揭示的兩套位址機制

### 機制 A · 直接 iowr（Falcon IO 空間）

```asm
00002f28: mov $r9 0x23200
00002f2c: iowr I[$r9] $r15        ; bit31=0 → Falcon IO 空間
```

**位址 `0x00000-0x3FFFF`，存取 Falcon 控制的引擎內部暫存器。**

### 機制 B · 帶 bit31 的外部存取（BAR0）

```asm
; 0x201 副程式：建構帶旗標的位址
00000201: mov $r9 0x3fffffc       ; 26 位位址遮罩
00000209: and $r10 $r9            ; 位址只保留低 26 位
0000020f: mov $r9 0x80000000      ; bit 31
00000214: shl b32 $r12 0x1a       ; bit26 = 讀/寫方向
00000217: or  $r10 $r9            ; 設定 bit31
0000021a: or  $r10 $r11           ; 合併參數
0000021d: or  $r11 $r10 $r12      ; 合併方向位
00000220: mov $r10 0x1ca00        ; 命令佇列位址
00000224: lcall 0x1d8             ; 提交命令
```

**`iowr I[0x80000000 | (addr & 0x3FFFFFC)]` → 存取 BAR0 絕對位址 `addr`。**

**GPCCS 用它存取 FECS 的暫存器：**

```asm
00000276: mov $r10 0x409818       ; FECS 段內的 BAR0 位址
0000027c: lcall 0x337             ; → 0x2a1 → 0x201 → 打包 bit31
00000282: mov $r10 0x409c1c
0000028a: lcall 0x337
0000028e: mov $r10 0x409c18
00000294: lcall 0x26a             ; 讀
0000029b: bra b32 $r10 0x1 e 0x28e ; 迴圈輪詢！
```

**這是 GPCCS 等待 FECS 的握手迴圈。**

### 機制 B 的驗證

**BAR0 實測（GPU 滿載）：**

```
0x409800 = 0x00000004
0x409808 = 0x00000001
0x409810 = 0x00042790   ← 非零
0x409818 = 0x00000000
0x409830 = 0x03030000   ← 非零
0x409838 = 0x00001F97   ← 非零
0x409C00 = 0x00000002
```

**這些是真實暫存器（不是 BAD），證明機制 B 存取的確實是 BAR0 位址空間。**

**而 GPCCS 輪詢的 `0x409818` / `0x409C18` / `0x409C1C` 目前值均為 0——**
**說明握手處於「閒置/已完成」狀態（GPU 在跑 GEMM，但不需要 context switch）。**

## 六、這對「Tensor Core 限速」的最終意義

### 已經確定的事

1. **TC 硬體存在**（SASS 可編譯執行 HMMA，實測 0.60 TFLOPS）
2. **TC 被限速到理論值的 5%**（理論 6-12 TFLOPS）
3. **控制點不在任何 host 可讀寫的層**：
   - GSP 韌體：已完整反組譯，不含 TC 邏輯
   - vBIOS：受 FWSEC 憑證鏈保護
   - 系統 BIOS：Boot Guard 加密
   - **FECS/GPCCS 微碼：已完整反組譯，只管排程與同步**
   - **Falcon IO 空間 `0x20000` 段：host 永久不可見**
   - SM 微碼：不存在（純硬體）
   - 硬體熔絲：物理不可逆

### 新增的一條硬邊界

**即使知道 `0x20000` 段是 GR 內部暫存器，host 也永遠讀不到它——**
**這是 `HOST_IO_INDEX` 只有 6 位（只能選 `bits 2-7`）決定的硬體設計。**

**要讀它，只有兩條路：**
1. **修改微碼**，讓它把 `0x20000` 段的值搬到 host 可見的地方
   → 但微碼受 **FWSEC 簽章驗證**，改一個位元組即拒絕載入
2. **物理層探測**（邏輯分析儀抓 Falcon 的 IO 匯流排）
   → 超出軟體研究範疇

**第一條路被簽章擋住，第二條路需要拆機。**
