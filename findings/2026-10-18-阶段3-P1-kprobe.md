# 2026-10-18 · 阶段 3 · P1：kprobe 绕过（部分成功 + 方案修正）

## 目标

绕过 `kallsyms_lookup_name` 自 Linux 5.7 起不再导出的限制，用它查询 NVIDIA 内核模块的内部符号地址。

## 实现

`kernel/mx450_p1.c`：

```c
struct kprobe kp = { .symbol_name = "kallsyms_lookup_name" };
register_kprobe(&kp);
kln_addr = (unsigned long)kp.addr;      /* 拿到真实地址 */
unregister_kprobe(&kp);
kln = (kln_t)kln_addr;                  /* 转型后调用 */
kln("os_map_kernel_space");              /* 查目标符号 */
```

## 结果 1 · QEMU 隔离环境：完全成功

```
kernel: 6.18.18.c1126-trim
mx450_p1: kallsyms_lookup_name resolved @ 0xffffffffb37e9404
mx450_p1: os_map_kernel_space = (not present)
mx450_p1: nv_al_add_mapping   = (not present)
mx450_p1: probe complete
rc=0
```

- **kprobe 技术在 fnOS 6.18 内核上有效**
- `kallsyms_lookup_name` 地址成功取得并可调用
- nvidia 符号"not present"是预期（虚拟机内未加载 nvidia 模块）

## 结果 2 · 宿主机：内核 oops

```
Segmentation fault (rc=139)
mx450_p1: kallsyms_lookup_name resolved @ 0xffffffffa65e9404
 mx450_p1_init+0x92/0xff0 [mx450_p1]
```

**地址取到了，但调用 `kallsyms_lookup_name` 时崩溃（+0x92）。**

### 差异分析

| 环境 | 符号表规模 | 结果 |
|---|---|---|
| QEMU（无 nvidia） | 小 | ✅ 成功 |
| 宿主机（含 nvidia，46294 个符号） | 大 | ❌ oops |

**推测原因**：`kallsyms_lookup_name` 遍历大符号表时，可能依赖 `kallsyms_lock` / RCU 保护，
在模块 init 上下文中直接调用不安全；或该函数的内部实现在 6.18 有变化。

### 系统状态

- **宿主未重启**（uptime 2 天 22 小时）
- `nvidia-smi` 正常（MX450, 57°C, 1395MHz）
- `nvidia` / `nvidia_uvm` / `nvidia_drm` 模块状态正常
- 遗留：`mx450_p1` 与 `mx450_probe` 各 12 KB，标记 `in use`，`rmmod` 与 `rmmod -f` 均失败，
  **仅重启可清除**

## 关键修正：根本不需要 kallsyms_lookup_name

排查时发现：**`/proc/kallsyms` 对 root 完全可读**，符号地址本来就摆在那里。

```bash
# 本机实测（无需任何模块）
$ grep -E "os_map_kernel_space|nv_al_add_mapping" /proc/kallsyms
ffffffffc2c13bb0 t __pfx_os_map_kernel_space	[nvidia]
```

**所以正确方案是**：

1. 用户态读 `/proc/kallsyms` 取得目标符号地址
2. 通过模块参数把地址传进去（`module_param`）
3. 模块直接用该地址转型调用，**全程不碰 `kallsyms_lookup_name`**

**好处**：
- 避开了导致 oops 的函数
- 地址来源透明可审计（能直接看到 `[nvidia]` 归属）
- 可以先用 `cat /proc/kallsyms` 确认符号存在，再决定是否加载模块

## P1 结论

| 项目 | 状态 |
|---|---|
| kprobe 技术可行性 | ✅ 已验证（QEMU） |
| 宿主机调用 `kallsyms_lookup_name` | ❌ oops，不可用 |
| **符号地址获取** | ✅ **改用 `/proc/kallsyms`，已实测可行** |
| P1 目标（拿到 nvidia 符号地址） | ✅ **实质达成**（地址已在 `/proc/kallsyms`） |

**P1 判定：完成，但方案从"kprobe 动态解析"修正为"用户态读 kallsyms + 参数传入"。**

## 教训

1. **QEMU 与宿主行为可能不同** —— 符号表规模差异导致同一代码一边成功一边崩溃
2. **内核模块崩溃后无法卸载** —— 两次测试各留一个 12 KB 僵尸模块，只能重启清除
3. **先找最简单的办法** —— 花时间写 kprobe，而 `/proc/kallsyms` 直接就能读
4. **移植前先在隔离环境验证，但隔离验证通过 ≠ 宿主安全**
