## 五、發現：Falcon / RISC-V 的分派邏輯

```asm
655b1a: mov  0x640(%r13),%eax     ; 讀架構標識欄位
655b21: sub  $0x2,%eax
655b24: cmp  $0x1,%eax
655b27: jbe  657c32               ; 值 ∈ {2,3} → 走 RISC-V 微碼路徑
655b2d: movq $0x0,0x40(%rbp)      ; 否則 → 走 Falcon 微碼路徑
655b35: mov  $0x0,%rsi            ; ← 重定位佔位：GRCTX_UCODE_DATA_FECS
```

**這直接印證了本專案的實測結論：**

| 架構 | 微碼類型 | 依據 |
|---|---|---|
| Turing (TU117) | **Falcon fuc6** | 我們 dump 的 32KB/16KB 都是 fuc6 指令 |
| Ampere+ | **RISC-V** | 程式碼裡 `arch ∈ {2,3}` 分支載入 RISCV ucode |

**`0x640(%r13)` 是架構列舉欄位，`{2,3}` 對應 RISC-V 世代。**

## 七、實測驗證：`0x40A600` 是 GPC 級狀態暫存器

GPU 滿載時讀 BAR0：

```
0x40a600 = 0x1F801FC2   ← GPC0
0x40a604 = 0x1F801000
0x40a608 = 0x1F801000
0x40a60c = 0x1F801000
0x40a610 = 0x1F801FC2   ← GPC1（與 GPC0 完全相同）
0x40a614 = 0x1F801000
0x40a618 = 0x1F801000
0x40a61c = 0x1F801000
0x40a620 - 0x40a66c = 0x00000000   ← 剩餘 5 組全零
```

**結構解讀：**

- 陣列按**最大 GPC 數 7** 分配（對應 GA102 等大晶片）
- **TU117 只有 2 個 GPC**，所以只有前 2 組有資料
- 每組 4 個暫存器，步長 `0x10`
- 組內第 0 個是狀態（`0x1F801FC2`），第 1-3 個是配置（`0x1F801000`）

**這是 GPC 級狀態暫存器，不是 Tensor Core 配置。**

## 八、這一輪的根本結論

### 已經確認的

| # | 結論 | 證據 |
|---|---|---|
| 1 | nvidia.ko 符號表完整（46614 條） | `readelf -s`，與 kallsyms 位址精確對應 |
| 2 | GR context 佈局由 `_nv033210rm` 建構 | 186 個 GRCTX 字串全部定位到該函式 |
| 3 | **Turing 用 Falcon 微碼，Ampere+ 用 RISC-V** | `0x640(%r13) ∈ {2,3}` 分支 |
| 4 | **`0x20000` 段在 host 側無任何位址表** | `.rodata` 全量掃描，僅找到數值表 |
| 5 | `0x400000` 段有 18 張真實位址表 | 含 `0x409C18`（FECS↔GPCCS 握手） |
| 6 | `0x40A600` 是 GPC 級狀態，7 組按最大 GPC 分配 | BAR0 實測，前 2 組有效 |

### 最終判斷（與之前一致，但現在有閉源 HAL 的證據）

**`0x20000` 段是 Falcon IO 空間，不是 host 可見的 GR 暫存器。**

三重證據：

1. **`.rodata` 裡沒有 `0x20000` 段的位址表**（只有等比數列等數值表）
2. **GR context 的暫存器清單只包含 `0x400000` 段**（18 張表，全部在該段）
3. **微碼用 `bit31=0` 的 `iowr` 存取 `0x20000` 段，用 `bit31=1` 存取 `0x400000` 段**（GPCCS 的 `0x201` 副程式）

**三條獨立證據指向同一結論：NVIDIA 自己的驅動都不把 `0x20000` 段當作 host 可存取的暫存器。**
