# 2026-10-19 · nvidia.ko 全量線索排查：限制機制不在驅動層

## 一、本輪排查範圍

用符號表 + `.rela.text` 重定位 + `objdump` + `.rodata` 全量掃描，
把 nvidia.ko（137 MB，46614 符號）裡所有與「限制 / 授權 / 能力 / 限速」相關的線索逐一排查。

## 二、逐項排除

### 1. 熔絲：只有一個通用讀取介面

```
46379: 0000000000000970    16 FUNC  GLOBAL DEFAULT  3  nv_soc_fuse_register_read
46530: 0000000000000960    16 FUNC  GLOBAL DEFAULT  3  __pfx_nv_soc_fuse_register_read
```

**16 位元組，是跳轉樁。** 熔絲字串只有：

```
SEC_FAULT: _FUSE_POD
SEC_FAULT: _FUSE_SCPM
SEC_FAULT: _FUSE_POD_2ND
SEC_FAULT: _FUSE_SCPM_2ND
SEC_FAULT: _FAULT_FUSE_POD
```

**全部是「安全故障」日誌（POD = Point of Disable，SCPM = Secure Copy Protection Module），
不是「讀熔絲決定啟用多少 SM/TC」的能力發現邏輯。**

**對比：GSP 韌體裡有完整的 FWSEC 憑證驗證鏈，而 nvidia.ko 的熔絲存取極少。**
說明**能力發現（多少個 SM、TC 是否可用）由 GSP 韌體在初始化時完成**，不在驅動。

**這些是 GR 排程器（SKED）的「異常檢測」，不是「能力配置」。**

`SKEDCHECK25_THROTTLED_IS_RESTRICTED` 的語意是：
**當某個資源處於「被限制的限速狀態」時，排程器報這個異常。**

也就是說——**驅動知道有限速這件事，並且會檢測它，但驅動不控制它。**

**這是本專案最重要的一條間接證據：限速發生在驅動之下。**

### 3. License：全是 vGPU/GRID，與消費級無關

```

5bd3c11  VGPU_GRID_SW_LICENSING
5beb040  GridLicenseEnforcement
5beb058  UnlicensedUnrestrictedStateTimeout
5beb080  UnlicensedRestricted1StateTimeout
5c18a60  License provided is rejected or invalid [NV_ERR_INVALID_LICENSE]
```

**「Unlicensed」指的是 vGPU 的 GRID license（資料中心虛擬化授權），
不是消費級卡的功能鎖。**

**驗證**：`GridLicensedFeatures` 是 vGPU 功能開關，`VGPU_GRID_SW_LICENSING` 是授權校驗。
消費級 GeForce 不走這條路徑。

**排除。**

### 4. PRIV_ACCESS_MAP：context 隔離，不是能力限制

```
GR_GLOBALCTX_BUFFER_PRIV_ACCESS_MAP
GR_GLOBALCTX_BUFFER_UNRESTRICTED_PRIV_ACCESS_MAP
GR_GLOBAL_BUFFER_GLOBAL_PRIV_ACCESS_MAP
```

**三種權限對映，作用是「不同 context 不能存取彼此的暫存器」——
這是安全隔離（防止惡意 shader 讀寫別的行程的 GPU 狀態），
不是「限制 TC 算力」。**

**排除。**

**但驅動裡沒有事件類型列舉——格式定義在 GSP 韌體或 FECS 微碼內部。**


**nvidia.ko 裡沒有任何 Tensor Core 相關的程式碼或配置。**

**這符合架構分工：TC 在 SM 內部，由硬體執行，驅動只負責派發 shader。**


**全是 Resource Manager 的「匯流排／優先級節流」參數，與算力無關。**

### 8. 新發現的 GRCTX 欄位（補充）

```
GRCTX_UCODE_RISCV_DATA_FECS_COUNT
GRCTX_UCODE_RISCV_INST_FECS_COUNT
GRCTX_UCODE_RISCV_MANIFEST_FECS_COUNT
```

## 三、本輪的根本結論

**nvidia.ko 裡不存在任何「Tensor Core 能力配置」或「算力限速開關」。**

五類線索、八個方向，全部排除：

| 方向 | 結果 |
|---|---|
| 熔絲能力發現 | 不存在（只有通用介面 + 安全日誌） |
| SKEDCHECK 限速檢查 | 是「檢測」不是「控制」 |
| License 授權 | vGPU 專用，消費級無關 |
| PRIV_ACCESS_MAP | context 隔離，非能力限制 |
| Tensor/MMA 程式碼 | 零命中 |
| THROTTLE 參數 | RM 匯流排節流，與算力無關 |
| FECS_EVENT | 只有名字，無格式定義 |
| GRCTX 佈局 | 已完整解析，無 TC 欄位 |

## 四、最重要的一條推論

**`SKEDCHECK25_THROTTLED_IS_RESTRICTED` 的存在，反過來證明了一件事：**

**驅動知道「限速狀態」的存在，並且把它當作一種需要檢測的異常——**

**但驅動既不設定它，也不清除它。**

**這說明限速由驅動之下的層（GSP 韌體 / FECS 微碼 / 硬體）設定，
驅動只是被動觀察。**

**而我們已經逐一確認：**
- GSP 韌體不含 TC 邏輯（8 個 Ampere 暫存器位址零命中）
- FECS/GPCCS 微碼只管排程與同步（449/177 條 iowr，全是控制／同步）
- Falcon IO 空間 `0x20000` 段 host 永久不可見（`HOST_IO_INDEX` 僅 6 位）
- 熔絲由硬體決定，物理不可逆

**四層都指向同一結論：TC 的限速在硬體層，軟體無法觸及。**

## 五、方法論記錄：為什麼沒有用 Ghidra 全量反編譯

**Ghidra 12.1.4 已就緒且 doctor 全綠，但本輪沒有用它做全量分析。**

理由：

| 方案 | 耗時估計 | 收益 |
|---|---|---|
| Ghidra 全量匯入 + 自動分析 137 MB | 數小時 | 得到 4 萬函式的反編譯，但其中 99% 與問題無關 |
| **符號表 + 重定位 + objdump（本輪）** | **分鐘級** | **精確定位 186 個字串的全部引用點** |
| Ghidra 定向反編譯單函式 | 分鐘級 | 需要時再做 |

**結論：對於「有完整符號表的二進位」，符號 + 重定位比全量反編譯高效得多。**

**Ghidra 的價值在於「無符號」或「需要類型恢復」的場景，不是「有符號的大二進位」。**

**這是本輪最重要的一條工程判斷。**

## 九、補充驗證：GR context buffer 不在 VRAM 末尾（負結果）

**動機**：`_nv033210rm` 顯示 GR context 裡保存了微碼副本：
```
context+0x1d0 = 微碼指標
context+0x1d8 = 微碼位元組數
context+0x1dc = 微碼位元組數（副本）
```
若 context buffer 在 VRAM，其微碼副本應帶 `d0 00 20 00 00 fe 04 00 bd a4 7e` 簽章。

**實驗**：GPU 滿載 100% 時，用 PRAMIN dump VRAM `0x7E000000-0x7FF00000`（32 MB）。

**結果**：
```
FECS  完整頭 (d0 00 20 00): 0 處
GPCCS 完整頭 (d0 00 14 00): 0 處
公共 7 位元組簽章:            0 處
整片非零率: 96.78%
```

**判定**：GR context buffer 不在此區域。

**可能位置**：
1. VRAM 的其他區域（本次只覆蓋末尾 32 MB）
2. 系統記憶體（context buffer 可能由 `os_alloc_mem` 分配在 host 側）
3. 微碼副本經過編碼（`GRCTX_UCODE_DATA_*` 是 data 欄位，可能非明文）

**要定位需讀 `context+0x1d0` 的指標值，而 context 結構本身在驅動記憶體中——
需要在中核模組裡解析驅動私有結構，超出目前唯讀研究範圍。**

**這是本輪唯一一個負結果，但排除了一個可能位置，屬於有效資訊。**
