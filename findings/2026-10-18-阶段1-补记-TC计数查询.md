# 2026-10-18 · 阶段 1 补记：TC 计数查询尝试（未成功）

**简体中文** | [繁體中文](2026-10-18-阶段1-补记-TC计数查询.zh-TW.md) | [English](2026-10-18-阶段1-补记-TC计数查询.en.md)

## 目标

读取 `NV2080_CTRL_GR_INFO_INDEX_TENSOR_CORE_COUNT (0x23)`，
判定驱动是否承认这块芯片存在 Tensor Core。

- 返回 56（14 SM × 4）→ TC 被硬件承认，只是限速 → **B 类假设成立**
- 返回 0 → 驱动层即判定不可用 → 接近 A/D 类

## 已获取的定义（全部来自 NVIDIA MIT 许可源）

| 常量 | 值 | 来源 |
|---|---|---|
| `NV_ESC_RM_CONTROL` | `0x2A` | `nv_escape.h` |
| `NV_ESC_RM_ALLOC` | `0x2B` | `nv_escape.h` |
| `NV01_ROOT_CLIENT` | `0x41` | `g_allclasses.h` |
| `NV01_DEVICE_0` | `0x80` | nvos.h |
| `NV20_SUBDEVICE_0` | `0x2080` | `cl2080.h` |
| `NV2080_CTRL_CMD_GR_GET_INFO` | `0x20801201` | `ctrl2080gr.h` |
| `NV2080_CTRL_GR_INFO_INDEX_TENSOR_CORE_COUNT` | `0x23` | `ctrl2080gr.h` |

结构体 `NVOS64_PARAMETERS` / `NVOS54_PARAMETERS` / `NV0080_ALLOC_PARAMETERS` /
`NV2080_ALLOC_PARAMETERS` / `NV2080_CTRL_GR_INFO` 均已从 `nvos.h` 提取，
实现见 `tools/read_tc_count.py`。

## 执行结果

```
打开 /dev/nvidiactl OK (fd=3)
[1] 分配 ROOT_CLIENT
  ALLOC class=0x41 失败: [Errno 22] Invalid argument (status=0)
```

**第一步 alloc 即被拒，`EINVAL`。**

## 失败原因分析

1. **无编译器。** NAS 上 `which gcc` → not found（只有 `/usr/bin/make`），
   无法编译官方示例（`nvidia-3d-init.c`），只能用 ctypes 手工构造结构体。
2. **结构与驱动期望不匹配。** 驱动在 `escape.c` 里用
   `_RM_ESC_IOCTL_ENTRY(cmd, type)` 严格校验 `size == sizeof(type)`。
   通用 Turing 结构在 580 驱动的实际打包方式（对齐/padding）若与 ctypes 推算差一个字节即返回 EINVAL。
3. **RM 初始化时序。** 现代驱动（470+）对 `/dev/nvidiactl` 的 RM 通道有额外前置要求，
   直接 alloc root client 不一定被接受。

## 结论

**这是工具链问题，不是原理问题。** 该诊断手段在当前环境不可用，需要：

- 方案 A：给 NAS 装 `build-essential`（`apt install gcc make linux-headers-$(uname -r)`），
  然后编译基于官方 headers 的 C 工具 —— 最可靠
- 方案 B：改用 `nvidia-push` 库的 `rmApiControl`（与 `nvidia-3d-init.c` 同路径）
- 方案 C：放弃该指标，改用 CUPTI 采集 `sm__pipe_tensor_cycles_active` 类计数器，
  直接观察张量管线是否被激活 —— **信息量更大，且不依赖私有 ioctl**

## 影响评估

**不阻塞主线。** 已有证据足以支撑「TC 存在但被限速」的判断：

1. `ptxas -arch=sm_75` 对 `mma.m16n8k8` 生成真 HMMA 指令（opcode 指纹与 FFMA 版完全不同）
2. 执行不报错（若 TC 完全缺失，HMMA 应触发非法指令）
3. 吞吐恒为 0.60 TFLOPS，低于纯 FFMA 的 3.06 —— 说明走了一条**比软件模拟还慢**的路径
4. `cuBLAS` 请求 `TENSOR_OP` 算法后同样只有 0.32 TFLOPS

TC 计数只是一个"驱动怎么看这块硅片"的旁证，不改变上述四条实测事实。

## 下一步（按信息量排序）

1. **CUPTI 计数器**（方案 C）—— 直接看张量管线活跃周期，判定 TC 是否被物理激活
2. **装 build-essential 走方案 A** —— 拿到 TC 计数这个硬指标
3. **dump 系统 BIOS** —— 解析 VGA 模块里的 devinit 表，看是否有 TC 相关配置项
