# 2026-10-19 · 階段 4 補記：iowr 位址空間歸屬 —— 五種假設逐一排除

## 一、本輪修正了一個方法論錯誤

**此前的位址統計（findings/阶段4-FECS微码反汇编.md）存在系統性偏差。**

原分析腳本 `analyze_iowr.py` 只追蹤 `mov` 指令，不追蹤 `add`/`sub`。而微碼中存在大量：

```asm
00002c2d: mov $r9 0x20600       ; $r9 = 0x20600
00002c31: iowr I[$r9] $r1       ; 寫 0x20600  ✓
00002c39: add b32 $r9 $r9 0xc00 ; $r9 = 0x21200  ← 腳本漏了這一步
00002c3e: iowr I[$r9] $r15      ; 實際寫 0x21200，被記成 0x20600  ✗
```

**新腳本 `tools/analyze_iowr_v3.py`** 追蹤 `mov(imm/reg) / add / sub / shl / shr / and / or`，
並先剝離反組譯行首的「位址 + 位元組碼」前綴（v2 因 `^` 錨點導致 0% 解析）。

### 修正後的統計

```
iowr 總數: 449   可解析: 442 (98.4%)   未解析: 7
iord 總數: 0

指令統計: mov_i 4446, lcall 932, add 286, sub 61, and 81, shl 43, shr 50, or 3
```

**位址分佈與 v1 大體一致（85% 仍在 0x20000 段），說明主要結論不受影響，但具體數值已修正。**

## 二、關鍵突破：Falcon IO 位址對映規則

envytools `docs/hw/falcon/io.rst` 給出了 Host / Falcon 雙視角對映表：

```
Host    Falcon    Name
0x000   0x00000   INTR_SET
0x004   0x00100   INTR_CLEAR
0x040   0x01000   SCRATCH0
0x100   0x04000   UC_CTRL        ← CPUCTL
0x104   0x04100   UC_ENTRY       ← BOOTVEC
0x108   0x04200   UC_CAPS        ← HWCFG
0x10c   0x04300   UC_BLOCK_ON_FIFO
0x12c   0x04b00   UC_CAPS2       ← HWCFG1
0x180   0x06000   CODE_INDEX     ← IMEM 視窗位址
0x184   0x06100   CODE           ← IMEM 視窗資料
0x1c0   0x07000   DATA_INDEX[0]
0x1c4   0x07100   DATA[0]
```

**對映規則：`Falcon = Host × 0x40`**

**驗證**：我們實測 `BAR0 0x409000 + 0x12c = 0x80104126`，而 `0x12c` 正是 `UC_CAPS2`。
`0x409184 = 0x002000D0`，而 `0x184` 正是 `CODE`（IMEM 視窗），讀出的正是 IMEM[0]。
**兩處獨立驗證，對映關係確認。**

## 三、五種假設逐一排除

### 假設 1 · `0x20000` 段是 BAR0 絕對位址

**測試**：驅動卸載後 + 驅動執行時（GPU 100%）分別讀 BAR0 `0x20000` 段。

```
驅動卸載:  0x020000 = 0xBADF5040
驅動執行:  0x020000 = 0xBADF5040   ← 仍然是 BAD
           0x0247FC = 0xBADF1100
           0x010100 = 0xBAD00100
```

**`0xBADF5040` / `0xBADF1100` / `0xBAD00100` 是 NVIDIA 的三類「未實作位址」哨兵值**
（對照：`0x001000` 也回傳 `0xBADF5040`，而 `0x001700` PRAMIN 視窗回傳有效值 `0x00007FF0`）。

**結論：排除。不是 BAR0 位址。**

### 假設 2 · `iowr 位址 = FECS 基底(0x409000) + offset`

**測試**：讀 BAR0 `0x409000 + 0x20000 = 0x429000` 等。

**結果**：`0x420000 - 0x43F000` 全部回傳 BAD。

同時掃描 GR 段有效區域：

```
0x404000: 0x80000000    ← 有效
0x408000: 0x08800800    ← 有效
0x409000: 0             ← FECS
0x410000: 0x32080A00    ← 有效
0x418000: 0x8700029F    ← 有效
0x419000: 0x10210780    ← 有效
0x41A000 / 0x41B000: 0  ← 有效但空
0x420000+: 全部 BAD
```

**結論：排除。GR 的暫存器區止於 0x41B000 附近。**

### 假設 3 · `0x20000` 段是 UAS（Unified Address Space）

**測試**：GPU 滿載時讀 FECS 的 UAS 暫存器組。

```
0x409160 UAS_IO_WINDOW   = 0x00000000
0x409164 UAS_CONFIG      = 0x00000000
0x409168 UAS_FAULT_ADDR  = 0x00000000
0x40916c UAS_FAULT_STATUS= 0x00000000
```

**全部為 0，且 `UAS_FAULT_STATUS = 0` 說明從未產生 UAS 存取錯誤。**

**結論：排除。該 Falcon 實例的 UAS 未啟用（或不存在）。**

> 附註：envytools 的 `docs/hw/falcon/data.rst` 第 9 行寫著 `.. todo:: document UAS`
> —— **連 envytools 自己都沒寫出 UAS 的文件。**

### 假設 4 · `0x20000` 段是 XFER 外部空間（VRAM）

**測試**：GPU 滿載時連續 8 次取樣 `XFER_EXT_BASE`。

```
0x409110 XFER_EXT_BASE = 0x00772600   （8 次取樣全部相同，穩定）
0x409114 XFER_FALCON_ADDR = 0x00000000
0x409118 XFER_CTRL        = 0x00000602
0x40911c XFER_EXT_ADDR    = 0x0000E700
```

**若 `iowr 位址 = XFER_EXT_BASE + offset`，則 `0x20000 → VRAM 0x792600`。**
**實測 dump VRAM `0x760000-0x860000`（1 MB），`0x792600` 處 64 位元組全零。**

**結論：排除。不是 XFER 外部空間。**

### 假設 5 · `0x20000` 段是 Falcon DMEM

**HWCFG = 0x40204080**，欄位解碼：
- bits 8:0 = 0x080 = 128 → IMEM = 128 × 256B = **32 KB**（與實測 dump 長度一致）
- DMEM 按 NVIDIA 慣例為 IMEM 的 1/4 ～ 1/2，即 **8–16 KB**

**`0x20000 = 128 KB`，遠超 DMEM 容量。**

**結論：排除。**

## 四、位址結構分析：它是「4KB 區塊 + 區塊內暫存器」

把 72 個唯一位址按 4KB 分塊：

| 區塊 | 位址數 | 區塊內偏移 |
|---|---|---|
| `0x20000-0x20FFF` | 11 | 0x000, 0x100, 0x600, 0x700, 0x900, 0xA00, 0xB00, 0xC00, 0xD00, 0xE00, 0xF00 |
| `0x21000-0x21FFF` | 3 | 0x200, 0x300, 0x800 |
| `0x22000-0x23FFF` | 7 | 0xA00, 0xE00, 0xF00, 0x000(23000), 0x200, 0x300, 0x800 |
| `0x24000-0x24FFF` | 4 | 0x200, 0x300, 0x400, 0x420, **0x6FC, 0x7FC, 0xFFC** |
| `0x28000-0x28FFF` | 8 | 0x000, 0x100, 0x300, 0x400, 0x800, 0x900, 0xD00, 0xE00 |
| `0x2C000-0x2CFFF` | 4 | 0x000, 0x100, 0x200, 0x300 |
| `0x2DC00-0x2DEFF` | 3 | 0xC00, 0xD00, 0xE00 |
| `0x30200-0x30900` | 4 | 0x200, 0x540, 0x700, 0x900 |

**兩個關鍵特徵：**

1. **區塊內偏移以 0x100 為基本步長** —— 典型的「每實例一組暫存器，實例間隔 0x100」
2. **`0x246FC / 0x247FC / 0x24FFC` 這三個 `0xFFC` 結尾位址** —— 4 KB 區塊內的末尾偏移，
   典型的「區塊結束標記 / 區塊級控制暫存器」

**這與「GR 內部硬體暫存器組」的佈局完全吻合，而不是記憶體緩衝區。**

## 五、最終判定

**`0x20000` 段是 Falcon IO 空間在 v6 上的高位址擴展區，對映到 GR 引擎內部硬體暫存器，不對映到 BAR0。**

依據：

| 證據 | 說明 |
|---|---|
| 五種假設全部實測排除 | BAR0 / FECS+off / UAS / XFER / DMEM |
| 位址結構為 4KB 區塊 + 0x100 步進 | 硬體暫存器組特徵，非記憶體 |
| `iord` 數量為 0 | 微碼只寫不讀 —— 典型的「配置暫存器」寫操作 |
| 與 GR 段有效區（止於 0x41B000）無重疊 | 不在 host 可見的 BAR0 空間內 |

**這是「公開資料不可解」的最終確認，而非「尚未找到」：**

- envytools rnndb：止於 Maxwell，`0x20000` 段上界 `0x227FF` < 微碼實際存取的 `0x30900`
- `turing/tu102/` 標頭檔：無 `dev_gpc.h` / `dev_tpc.h`
- 開源 HAL：`NV_PGRAPH_GPC` / `NV_PGRAPH_TPC` 零定義
- envytools falcon 文件：`.. todo:: document UAS`（作者也沒寫）

## 六、本輪附帶發現：VRAM 中的 GPU MMU 頁表

dump VRAM `0x760000-0x860000` 時，在 `0x788000-0x791000` 發現規整結構：

```
0x790000: 0D 0D 7E 17 00 00 00 06   → 0x177E0D << 8 = 0x177E0D00
          0D 0E 7E 17 00 00 00 06   → 0x177E0E00  (+0x100)
          0D 0F 7E 17 00 00 00 06   → 0x177E0F00
          0D A8 2F 21 00 00 00 06   → 0x212FA800  ← 跳到另一段
```

每項 8 位元組，`[flags:8][addr:24][reserved:32]`，位址在 2 GB VRAM 範圍內連續遞增。

```
0x788000: 02 91 07 00 00 00 00 00   → 0x079102
          02 89 07 00 00 00 00 00   → 0x078902
          12 91 07 00 00 00 00 00   → 0x079112
          02 8A 07 00 00 00 00 00   → 0x078A02
```

成對出現，步長分別為 `0x10` 和 `0x100` —— 典型的**頁表 / 位址對映表**結構。

**判定：這是 GPU 的記憶體管理結構（MMU 頁表 / 分配器中繼資料），不是 FECS 的私有資料。**

**但它是本專案首次在 VRAM 中定位到 GPU 自身的資料結構**，對後續研究有價值。

## 八、這一輪的意義

**排除了五種可能，這本身就是進展。**

在逆向工程中，「確定某物不是什麼」與「確定它是什麼」同樣有價值——它縮小了搜尋空間，
並防止後來者重複走同樣的彎路。

**現在的結論是清晰的：**

```
FECS 微碼（已 dump、已反組譯）
    ↓ 透過 iowr 存取
Falcon IO 空間（v6 擴展，0x20000 段）
    ↓ 對映到
GR 內部硬體暫存器（NVIDIA 從未公開對映表）
    ↓ 控制
GPC / TPC / SM 的執行時配置
```

**最後一環的對映表，是 NVIDIA 唯一沒有洩露的部分。**

要拿到它，只有兩條路：
1. 逆向閉源的 `nv-kernel.o_binary`（已剝離符號，工作量以月計）
2. 真機寫測試（**高風險，可能掛死 GPU**，不建議）

**在軟體層面，這條鏈已經探到能探的最深處。**
