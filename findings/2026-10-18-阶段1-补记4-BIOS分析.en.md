# 2026-10-18 · Stage 1 addendum 4: system BIOS dump and vBIOS location (route C, judged infeasible)

## Actions

1. check the ACPI tables: no `VFCT` (the usual ACPI carrier for a laptop GPU's vBIOS)
2. install `flashrom` + `acpica-tools`
3. probe the SPI Flash controller
4. read-only export of the BIOS region
5. locate the NVIDIA vBIOS inside the dump

## 1. ACPI table check

Available tables: `APIC BGRT DBG2 DBGP DMAR DSDT FACP FACS FPDT HPET LPIT MCFG MSDM NHLT PTDT
SSDT1-20 TPM2 UEFI WSMT`

**No `VFCT`** (Virtual Function Control Table). That table class is normally used to provide the system with a copy
of a discrete GPU's vBIOS; its absence means this route does not exist.

## 2. SPI Flash probe

```
Found chipset "Intel Tiger Lake U Premium".
FREG0: Flash Descriptor region (0x00000000-0x00000fff) is read-only.
FREG1: BIOS region (0x00800000-0x017fffff) is read-write.
FREG2: Management Engine region (0x00001000-0x007fffff) is read-only.
SPI Configuration is locked down.
Enabling hardware sequencing due to multiple flash chips detected.
```

- the whole Flash is 24,576 KB (24 MB)
- BIOS region: `0x00800000 – 0x017FFFFF` (16 MB)
- the ME region is read-only; the BIOS region is nominally writable but protected by PR0–PR3

## 3. Read-only export

```bash
flashrom -p internal:laptop=force_I_want_a_brick --ifd -i bios \
         -r /vol1/ganlin/bios/bios_readonly.bin
```

Result: `25165824` bytes (24 MB), MD5 `4d2c99e85e761e0a3b1b8dcada4cc950`
(`--ifd -i bios` did not take effect; the whole Flash was read, including Descriptor + ME + BIOS)

> Note: only the read-only `-r` option was used throughout; no erase or write was performed.

## 4. vBIOS location result

| Check | Result |
|---|---|
| standard PCI Option ROM (55AA + PCIR, VID=0x10DE) | **0 occurrences** |
| the string `NVIDIA` | **0 occurrences** |
| the string `90.17.64` (the VBIOS version reported by nvidia-smi) | **0 occurrences** |
| the string `TU117` | **0 occurrences** |
| `_FVH` (UEFI firmware volume signature) | only one 512 KB at `0x01400000` |
| `LZMA` / `Tiano` / `EFI_COMPRESS` | all zero |

The content starting at `0x00800000` is:

```
02 0F 3E 90 10 2D E0 44 90 EE E7 EF F0 A3 ED F0
```

**Not `_FVH`, no recognisable compression header — it is ciphertext.**

## 5. Verdict

**The BIOS body is protected and encrypted by Intel Boot Guard; a static dump cannot extract the vBIOS.**

Boot Guard's root of trust is a public key fused into the CPU; key BIOS regions (IBB) are stored signed and
encrypted, and are only decrypted into memory at runtime after the ROM stage verifies them. **Without the vendor's
private key, static analysis is impossible.**

This also corroborates something else: after unloading the driver, the PCI ROM BAR returns `EIO` (zero bytes),
meaning the GPU has no ROM of its own and the BIOS does not provide a plaintext Option ROM through the PCI
mechanism either — `nvidia-smi`'s reported `VBIOS Version: 90.17.64.00.14` is very likely a version number read by
the driver from some information structure inside the GPU, not a complete vBIOS image.

## Conclusion

**Route C is infeasible.** All three high-level paths are now bottomed out:

| Route | Means | Result |
|---|---|---|
| A | CUPTI metric enumeration | `rc=38`, zero metrics; unchanged after opening permissions |
| B | `NV2080_CTRL` ioctl | channel opened (ROOT_CLIENT succeeded), `GR_GET_INFO` status=31 |
| C | static analysis of system BIOS / vBIOS | Boot Guard encrypted; cannot be extracted |

## What these three routes jointly show

This machine's firmware and driver stack is defended **at three layers simultaneously**:

1. **hardware layer**: the GPU has no separate SPI Flash; the vBIOS is not supplied by the device itself
2. **firmware layer**: the system BIOS is signed and encrypted by Intel Boot Guard; not statically parseable
3. **driver layer**: user-space APIs (NVML / CUPTI / private ioctl) clip key capabilities or isolate at the object level

**This is not "high technical difficulty" — it is "sealed layer by layer by design".**

## Paths not yet excluded (for later reference)

| Path | Precondition | Feasibility |
|---|---|---|
| intercept GSP loading at runtime | build the `nvidia-open` kernel module + find Turing's Falcon load point | technically feasible, but **the target register addresses are unknown** (no PLM/CFG1 definitions in the open headers) |
| capture the decrypted vBIOS from memory | dump physical memory after BIOS POST but before the driver loads | needs a custom kernel module or kdump, and Boot Guard scrubs it |
| hardware-level measurement | logic analyser / oscilloscope on the TC clock domain | needs disassembly and specialist equipment |
