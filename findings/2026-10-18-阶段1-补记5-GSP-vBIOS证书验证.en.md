# 2026-10-18 · Stage 1 addendum 5: the vBIOS certificate verification chain in GSP firmware (decisive evidence)

## Finding

Inside `/lib/firmware/nvidia/580.142/gsp_tu10x.bin` (30 MB, Turing GSP firmware), a set of **vBIOS verification
error codes** was found, originating from the `FWSECLIC` (Firmware Security License) module:

```
vbios
vbios000
NV_UDE_ERR_VBIOS_VERIF_COMPLETED_AND_FAILED
NV_FWSECLIC_ERR_CODE_CMD_VBIOS_VERIFY_DEVID_FAIL
NV_FWSECLIC_ERR_CODE_CMD_VBIOS_VERIFY_CERT_NOT_FOUND
NV_FWSECLIC_ERR_CODE_CMD_VBIOS_VERIFY_CERT_PARSE_FAIL
NV_FWSECLIC_ERR_CODE_CMD_VBIOS_VERIFY_CERT_VERIFY_FAIL
NV_FWSECLIC_ERR_CODE_CMD_VBIOS_VERIFY_HAT_FAIL
NV_FWSECLIC_ERR_CODE_CMD_VBIOS_VERIFY_BIOS_SIG_FAIL
NV_FWSECLIC_ERR_CODE_CMD_VBIOS_VERIFY_HULK_INIT_FAIL
```

## What this evidence means

This is not speculation that "somewhere verification might happen" — it is a **ready-made error-code enumeration
inside the firmware**, and each entry corresponds to one verification stage:

| Error code | Verification stage |
|---|---|
| `VERIFY_DEVID_FAIL` | does the device ID match what the vBIOS declares |
| `VERIFY_CERT_NOT_FOUND` | is a signing certificate present |
| `VERIFY_CERT_PARSE_FAIL` | is the certificate format valid |
| `VERIFY_CERT_VERIFY_FAIL` | **does the certificate chain verify** |
| `VERIFY_BIOS_SIG_FAIL` | **does the vBIOS image signature match** |
| `VERIFY_HAT_FAIL` | hash tree / Hash-and-Trim verification |
| `VERIFY_HULK_INIT_FAIL` | secure initialization stage failed |
| `VERIF_COMPLETED_AND_FAILED` | the whole verification flow failed |

**Conclusion: before loading, the vBIOS must pass a full certificate chain + image signature + hash tree verification.**

## This directly explains three earlier observations

1. **Why modifying the vBIOS is impossible** — not "difficult", but the signature check will judge any change as
   `BIOS_SIG_FAIL`. Without NVIDIA's private key, a modified image cannot be accepted by the GSP.
2. **Why `cmpunlocker` must go through the Falcon vulnerability** — because what it bypasses is precisely the timing
   flaw "the loader copies data before verifying the signature", not an attempt to forge a signature.
3. **Why `nvidia-smi` reports a VBIOS version while the PCI ROM BAR reads nothing** — the vBIOS is held and verified
   on the GSP/firmware side and is not exposed to the system through the PCI Option ROM mechanism.

## The complete four-layer defence

```
┌─ ① hardware layer ──────────────────────────────────┐
│ the GPU has no separate SPI Flash                     │
│   after unloading the driver, PCI ROM BAR returns EIO (0 bytes) │
├─ ② firmware layer (system) ─────────────────────────┤
│ Intel Boot Guard: signing + encryption of key BIOS regions │
│ the 24 MB dump has no VFCT table, no _ROM method, no plaintext PCIR │
├─ ③ firmware layer (GPU) ────────────────────────────┤
│ GSP FWSECLIC: vBIOS certificate chain + image signature + hash tree │
│   ← newly found this round; the most direct layer      │
├─ ④ driver layer ────────────────────────────────────┤
│ NVML does not expose the TC count                     │
│ CUPTI metric enumeration rc=38                        │
│ private ioctl object-level isolation (placeholder handle 0xcaf0xxxx) │
└──────────────────────────────────────────────────────┘
```

**Four layers, four different technical means; each one alone is enough to seal off a path.**

## Final judgement on unlockability

| What would need changing | The blocking layer | Bypassable? |
|---|---|---|
| the vBIOS image (devinit / throttle configuration) | ③ GSP certificate verification | only via a loader timing flaw (Falcon class), requiring original research |
| the VGA module in the system BIOS | ② Boot Guard | needs Intel/Lenovo private keys, **impossible** |
| runtime registers (SS/PLM class) | ④ driver object model + ③ PLM privileges | needs Turing's register addresses first (**unknown**) |
| VRAM capacity | hardware (soldered packages) | **impossible** |

**Four paths: two physically impossible, two requiring information or a vulnerability that does not currently exist.**

## One untried avenue

The string `vbios000` hints that a handle/partition named `vbios000` may exist inside the firmware.
If that object could be queried over the mailbox after GSP startup, it might be possible to obtain the
**decrypted vBIOS image** for static analysis (note: obtaining the image still does not mean it can be modified —
see the table above).

This requires parsing the GSP's RPC protocol; the effort is substantial and it does not change the "cannot modify" conclusion.
