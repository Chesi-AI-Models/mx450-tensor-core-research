# 2026-10-18 · 阶段 2：GSP 固件逆向（系统性解封的第一步）

> 这是「正式投入」后的第一轮深度工作。
> 目标：从 GPU 固件内部找 Tensor Core 限速的控制点。

## 一、固件结构完全解析

`/lib/firmware/nvidia/580.142/gsp_tu10x.bin`（30 MB）是**双层 ELF**：

```
外层：ELF64 relocatable, UCB RISC-V, not stripped（实为无符号）
      ├── .fwimage        29 MB   ← 内嵌一个完整的 ELF
      ├── .fwversion      8 B
      └── .fwsignature[*] 3 × 4 KB  ← 签名段（CMPUnlocker 利用的正是这类段）
```

从 `.fwimage` 抽出内层 ELF（偏移 `0x40`）：

```
内层：ELF64 executable, UCB RISC-V, RVC, statically linked, stripped
      Entry point: 0x4009000
```

**内层节区按 GPU 架构分家**——这是关键：

| 节区 | 地址 | 大小 | 用途 |
|---|---|---|---|
| `.ga100_data` / `.ga100_text` | 0x4001000 / 0x4005000 | 0x1170 / 0x1414 | Ampere 分支 |
| `.tu10x_data` / `.tu10x_text` | 0x4003000 / 0x4007000 | 0x1170 / 0x1414 | **Turing 分支（本机走这条）** |
| `.bootstrap` | 0x4009000 | 0x74 | 入口 |
| `.tu10x_resident_text` | 0x400e000 | 0x3000 | Turing 常驻代码 |
| `.manifest` | 0x4012168 | 0xe98 | 配置清单 |
| `.acl` | 0x4012000 | 0x161 | 访问控制表 |

## 二、找到芯片分派逻辑（`.bootstrap`）

```asm
4009014: lw   t0, 0(t0)          # 读 PMC_BOOT_0
4009018: srl  t0, t0, 0x14       # >> 20 → chipset 字段
400901c: and  t0, t0, 511        # 取低 9 位
4009020: li   t1, 354            # 0x162 TU102
4009024: beq  t0, t1, 0x4009058
         ...
4009040: li   t1, 359            # 0x167 = TU117  ← 本机
4009044: beq  t0, t1, 0x4009058
         ...
4009058: jalr 0x4007000          # 跳入 .tu10x_text
```

**与实测完全吻合**：`NV_PMC_BOOT_0 = 0x167000a1`，`>> 20 = 0x167 = 359`。
**证明固件确实是按芯片 ID 分派，TU117 走 `.tu10x_text`。**

## 三、发现 GSP 的私有 CSR 机制

`.tu10x_text` 开头是连续 5 条非标准 CSR 写入：

```asm
csrw 0x7c8, t0    # 索引 / 选择子
csrw 0x7c9, s0    # 使能 / 状态
csrw 0x7ca, s1    # 基址
csrw 0x7cb, s2    # 长度 / 掩码
csrw 0x7cc, t1    # 属性 / 目标地址
```

配合出现的目标地址：`0xc0a04`、`0xc0600`、`0xc0e00`、`0x4005000`、`0x4000000`。

**这是 GSP 配置自身地址映射窗口的通道**。

> **⚠ 2026-10-18 21:45 修正（联网核查后）**
> 此前表述为「NVIDIA 私有 CSR」，不够准确。第三方对 GSP 固件的分析指出：
> GSP 运行的是 NVIDIA 自研微内核 **LibOS**，并用 **PMP（Physical Memory Protection）**
> 做分区隔离 —— 这是 RISC-V 的标准内存保护机制。
> 因此 `0x7c8–0x7cc` 更可能是 **NVIDIA 对 PMP 配置 CSR 的封装/扩展**，
> 即「把哪段物理地址开放给哪个 partition」。
> 参考：zerohour.day 对 `gsp-535.113.01.bin` 的分析
> （该文同时确认 Ampere 固件含 4 个 4KB RSA 签名段，Turing 的 GSP 同为 RISC-V）。

## 四、决定性负结果：Ampere 的解锁机制在 Turing 上不存在

把 CMPUnlocker 用到的 8 个 GA100 寄存器地址，逐一在 29 MB 固件里做小端搜索：

| 寄存器 | 地址 | 结果 |
|---|---|---|
| SS0 | `0x0082381C` | **未出现** |
| SS1 | `0x00823820` | **未出现** |
| FEAT_PLM | `0x00823804` | **未出现** |
| FBPA_PLM | `0x009A0148` | **未出现** |
| FBPA_CFG1 | `0x009A0204` | **未出现** |
| MMU_LMR | `0x00100CE0` | **未出现** |
| WPR_PLM | `0x001FA7C4` | **未出现** |
| WPR_CFG | `0x001FA7CC` | **未出现** |

**这不是「地址不同」，是「机制不存在」。**

CMPUnlocker 的四寄存器 PLM 打开 + SS0/SS1 限速解除，是 **Ampere（GA100）专属架构**。
Turing 的 GSP 固件里连这些地址都不引用，说明该世代没有这套 Platform Lock Manager 机制。

## 五、最后一个关键事实：Turing 的 SM 微码不在磁盘上

GSP 固件内只出现 FECS / GPCCS 的**错误字符串**（`FECS & GPCCS FALCONS HAVE…`、`UCODE RESET`），
**不包含它们的微码数据**。

文件系统里的微码只有 Kepler 世代的：

```
/lib/firmware/nvidia/gk20a/fecs_inst.bin     ← Kepler
/lib/firmware/nvidia/gk20a/gpccs_inst.bin    ← Kepler
```

**Turing 的 FECS/GPCCS 微码固化在 GPU 内部（ROM / 安全区），不通过文件系统提供。**

而 Tensor Core 位于 SM 内部，其调度与限速由 **FECS/GPCCS 微码 + 硬件配置** 控制 ——
**不在 GSP 固件里，也不在任何可读文件中。**

## 六、架构层面的结论

GPU 的软件栈分工是这样的：

```
┌─ GSP 固件（可读、已解析）──────────────────────┐
│ 管：GPU 全局初始化、调度、电力、错误处理       │
│ 不管：SM 内部单元（含 Tensor Core）的配置      │
├─ FECS / GPCCS 微码（固化在 GPU 内部，不可读）──┤
│ 管：SM 前端 / 计算管线的微码调度              │
│ Tensor Core 的行为在这里                       │
├─ 硬件熔丝 / 芯片布线 ──────────────────────────┤
│ 决定：SM 数量（14/16）、TC 是否可用            │
└────────────────────────────────────────────────┘
```

**关键判断：Tensor Core 的限速控制点，不在我们能够读写的任何一层。**

- GSP 固件里没有（已搜索证实）
- FECS/GPCCS 微码不可读（固化）
- 硬件熔丝不可改

## 七、这对「全面解锁」意味着什么

**软件路径到这里已经闭合。** 不是"难"，是控制点不在软件可及范围内：

| 尝试方向 | 结果 |
|---|---|
| 用户态 API（NVML / CUPTI / ioctl） | 三层均被裁剪/隔离 |
| 系统 BIOS（devinit） | Boot Guard 加密 |
| vBIOS 修改 | GSP 证书链验证 |
| GSP 固件修改 | 签名验证；且**不包含 TC 控制逻辑** |
| SM 微码修改 | **不可读、不可写** |
| 硬件熔丝 | **物理不可逆** |

## 八、如果仍要继续，只剩这三条（都不在软件范围）

1. **硬件层测量**：逻辑分析仪抓 SM 与 GPC 之间的总线，观察 HMMA 指令的实际执行路径
   —— 能"看见"，但改不了

3. **等待公开资料**：NVIDIA 从未公开 Turing 的 GSP/微码寄存器映射；若未来有安全研究公开，才可能推进

## 八点五、联网核查补充（同一轮，21:45）

三条外部信息与本轮发现互相印证：

1. **RSA 签名段数量吻合**：第三方分析 `gsp-535.113.01.bin` 得到「4 个 4KB RSA 签名段」，
   本机 `gsp_tu10x.bin` 为 **3 个 4096 字节 `.fwsignature` 段**（版本差异）。结构同源。
2. **PMP 机制**：GSP 微内核 LibOS 用 PMP 做分区隔离 → `.tu10x_text` 里的 `csrw 0x7c8–0x7cc`
   是 PMP 配置，不是"神秘私有寄存器"。这进一步说明写错该处会直接破坏 GSP 的内存隔离。
3. **NVIDIA 的公开表述**：RISC-V 被选中，部分原因正是"其隔离与内存保护特性让这类锁定更容易实现"。
   → 结论从"厂商疏忽"修正为"**刻意设计**"。
