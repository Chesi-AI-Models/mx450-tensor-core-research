# 2026-10-19 · Ownership of the 0x20000 segment: all three routes tried, judged "unsolvable from public material"

## 1. Route 2 failed: it is not a 14-iteration loop

`0x21800` appears 37 times in the disassembly, but distributed as follows:

```
000000ad  mov $r9 0x21800     ← function A
00000723  mov $r9 0x21800     ← function B
000009e9  mov $r9 0x21800     ← function C
00000b8b  mov $r9 0x21800     ← function D
00000e76  mov $r9 0x21800     ← function E
00000eed  mov $r9 0x21800
00000f0f  mov $r9 0x21800
00001ad7  mov $r9 0x21800
...
```

**Spread across more than ten different functions, and `mov $rX, 0xe` (14) has zero hits in the whole document.**

**Verdict: `0x21800` is a functional register shared by multiple functions, not a counter for "initialize in a loop
over the SM count".**

## 2. Route 1 failed: no definition in the HAL sources

```
gh search code "NV_PGRAPH_GPC"  → 0 results
gh search code "NV_PGRAPH_TPC"  → 0 results
```

**NVIDIA's `open-gpu-kernel-modules` (all Turing+ generations) contains no register macro definitions for GPC/TPC.**

This means GPC/TPC/SM-level register initialization logic lives inside the **closed-source HAL binary**
(`nv-kernel.o_binary`), not in the MIT/GPL-published open part.

## 3. Route 3 not verified (needs external material)

Comparing against the Kanxue AD102 FECS analysis requires reading the original article; whether its conclusions
(does it access `0x2000x` too) hold was outside this round's scope.

## 4. Final verdict

**The semantics of Turing's `0x20000` segment cannot be determined within the publicly obtainable material.**

Three obstacles:

| Obstacle | Status |
|---|---|
| envytools rnndb | coverage stops at Maxwell, and its recorded upper bound for the 0x20000 segment (0x227FF) is below the microcode's actual access range |
| NVIDIA open-source headers | the tu102 directory has no `dev_gpc.h` / `dev_tpc.h` |
| NVIDIA open-source HAL | zero definitions for `NV_PGRAPH_GPC` / `NV_PGRAPH_TPC`; the key logic is in the closed-source `.o_binary` |

**This is not "not found yet" — it is "NVIDIA never made this layer public".**

## 5. Directions that could continue (all need additional conditions)

| Direction | What it needs | Feasibility |
|---|---|---|
| disassemble the closed-source HAL | reverse `nv-kernel.o_binary` (IDA/Ghidra) | feasible but a large effort, and symbols are stripped |
| do write tests on the real machine | write to each address and observe the GPU's reaction | **high risk**, may hang the GPU |
| wait for third-party disclosure | a complete version of the AD102 reverse-engineering notes | not under our control |

**Note**: the second item (write tests) is the only one progressable on this machine, but it violates this project's
"read-only first" safety principle; moreover, given the `0x20000` segment is partly PTHERM/PFUSE/PUNITS,
a mistaken write could trigger thermal protection or fuse logic.
