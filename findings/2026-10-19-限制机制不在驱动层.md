# 2026-10-19 · nvidia.ko 全量线索排查：限制机制不在驱动层

用符号表 + `.rela.text` 重定位 + `objdump` + `.rodata` 全量扫描，
把 nvidia.ko（137 MB，46614 符号）里所有与「限制 / 授权 / 能力 / 限速」相关的线索逐一排查。

## 二、逐项排除

### 1. 熔丝：只有一个通用读取接口

```
46379: 0000000000000970    16 FUNC  GLOBAL DEFAULT  3  nv_soc_fuse_register_read
46530: 0000000000000960    16 FUNC  GLOBAL DEFAULT  3  __pfx_nv_soc_fuse_register_read
```

**16 字节，是跳转桩。** 熔丝字符串只有：

```
SEC_FAULT: _FUSE_POD
SEC_FAULT: _FUSE_SCPM
SEC_FAULT: _FUSE_POD_2ND
SEC_FAULT: _FUSE_SCPM_2ND
SEC_FAULT: _FAULT_FUSE_POD
```

**全部是「安全故障」日志（POD = Point of Disable，SCPM = Secure Copy Protection Module），
不是「读熔丝决定启用多少 SM/TC」的能力发现逻辑。**

**对比：GSP 固件里有完整的 FWSEC 证书验证链，而 nvidia.ko 的熔丝访问极少。**
说明**能力发现（多少个 SM、TC 是否可用）由 GSP 固件在初始化时完成**，不在驱动。

`SKEDCHECK25_THROTTLED_IS_RESTRICTED` 的语义是：
**当某个资源处于「被限制的限速状态」时，调度器报这个异常。**

也就是说——**驱动知道有限速这件事，并且会检测它，但驱动不控制它。**

**这是本项目最重要的一条间接证据：限速发生在驱动之下。**

### 3. License：全是 vGPU/GRID，与消费级无关


**「Unlicensed」指的是 vGPU 的 GRID license（数据中心虚拟化授权），
不是消费级卡的功能锁。**

**验证**：`GridLicensedFeatures` 是 vGPU 功能开关，`VGPU_GRID_SW_LICENSING` 是授权校验。
消费级 GeForce 不走这条路径。

**排除。**

### 4. PRIV_ACCESS_MAP：context 隔离，不是能力限制

```
GR_GLOBALCTX_BUFFER_PRIV_ACCESS_MAP
GR_GLOBALCTX_BUFFER_UNRESTRICTED_PRIV_ACCESS_MAP
GR_GLOBAL_BUFFER_GLOBAL_PRIV_ACCESS_MAP
```

**三种权限映射，作用是「不同 context 不能访问彼此的寄存器」——
这是安全隔离（防止恶意 shader 读写别的进程的 GPU 状态），
不是「限制 TC 算力」。**

**排除。**

## 三、本轮的根本结论

**nvidia.ko 里不存在任何「Tensor Core 能力配置」或「算力限速开关」。**

五类线索、八个方向，全部排除：

| 方向 | 结果 |
|---|---|
| 熔丝能力发现 | 不存在（只有通用接口 + 安全日志） |
| SKEDCHECK 限速检查 | 是「检测」不是「控制」 |
| License 授权 | vGPU 专用，消费级无关 |
| PRIV_ACCESS_MAP | context 隔离，非能力限制 |
| Tensor/MMA 代码 | 零命中 |
| THROTTLE 参数 | RM 总线节流，与算力无关 |
| FECS_EVENT | 只有名字，无格式定义 |
| GRCTX 布局 | 已完整解析，无 TC 字段 |

## 四、最重要的一条推论

**`SKEDCHECK25_THROTTLED_IS_RESTRICTED` 的存在，反过来证明了一件事：**

**驱动知道「限速状态」的存在，并且把它当作一种需要检测的异常——**

**但驱动既不设置它，也不清除它。**

**这说明限速由驱动之下的层（GSP 固件 / FECS 微码 / 硬件）设置，
驱动只是被动观察。**

**而我们已经逐一确认：**
- GSP 固件不含 TC 逻辑（8 个 Ampere 寄存器地址零命中）
- FECS/GPCCS 微码只管调度与同步（449/177 条 iowr，全是控制/同步）
- Falcon IO 空间 `0x20000` 段 host 永久不可见（`HOST_IO_INDEX` 仅 6 位）
- 熔丝由硬件决定，物理不可逆

**四层都指向同一结论：TC 的限速在硬件层，软件无法触及。**

## 五、方法论记录：为什么没有用 Ghidra 全量反编译

**Ghidra 12.1.4 已就绪且 doctor 全绿，但本轮没有用它做全量分析。**

理由：

| 方案 | 耗时估计 | 收益 |
|---|---|---|
| Ghidra 全量导入 + 自动分析 137 MB | 数小时 | 得到 4 万函数的反编译，但其中 99% 与问题无关 |
| **符号表 + 重定位 + objdump（本轮）** | **分钟级** | **精确定位 186 个字符串的全部引用点** |
| Ghidra 定向反编译单函数 | 分钟级 | 需要时再做 |

**结论：对于「有完整符号表的二进制」，符号 + 重定位比全量反编译高效得多。**

**Ghidra 的价值在于「无符号」或「需要类型恢复」的场景，不是「有符号的大二进制」。**

**这是本轮最重要的一条工程判断。**

## 九、补充验证：GR context buffer 不在 VRAM 末尾（负结果）

**动机**：`_nv033210rm` 显示 GR context 里保存了微码副本：
```
context+0x1d0 = 微码指针
context+0x1d8 = 微码字节数
context+0x1dc = 微码字节数（副本）
```
若 context buffer 在 VRAM，其微码副本应带 `d0 00 20 00 00 fe 04 00 bd a4 7e` 签名。

**实验**：GPU 满载 100% 时，用 PRAMIN dump VRAM `0x7E000000-0x7FF00000`（32 MB）。

**结果**：
```
FECS  完整头 (d0 00 20 00): 0 处
GPCCS 完整头 (d0 00 14 00): 0 处
公共 7 字节签名:            0 处
整片非零率: 96.78%
```

**判定**：GR context buffer 不在此区域。

**可能位置**：
1. VRAM 的其他区域（本次只覆盖末尾 32 MB）
2. 系统内存（context buffer 可能由 `os_alloc_mem` 分配在 host 侧）
3. 微码副本经过编码（`GRCTX_UCODE_DATA_*` 是 data 字段，可能非明文）

**要定位需读 `context+0x1d0` 的指针值，而 context 结构本身在驱动内存中——
需要在内核模块里解析驱动私有结构，超出当前只读研究范围。**

**这是本轮唯一一个负结果，但排除了一个可能位置，属于有效信息。**
