# 2026-10-19 · Full clue sweep of nvidia.ko: the restriction mechanism is not in the driver layer

## 1. Scope of this round

Using the symbol table + `.rela.text` relocations + `objdump` + a full `.rodata` scan, every clue in nvidia.ko
(137 MB, 46,614 symbols) related to "restriction / licensing / capability / throttling" was examined one by one.

| Clue class | Hits | Conclusion |
|---|---|---|
| fuse | 1 symbol + 5 security logs | no capability-discovery logic |
| SKEDCHECK | 29 | all exception checks, not configuration |
| License | 13 | all vGPU/GRID licensing |
| PRIV_ACCESS_MAP | 3 | context isolation, not capability restriction |
| GRCTX layout | 186 | fully parsed |
| FECS_EVENT | 1 (name only) | no format definition |
| Tensor / MMA | 0 valid | no related code |
| THROTTLE | 6 | all RM-internal throttle parameters |

## 2. Eliminating them one by one

### 1. Fuses: only one generic read interface

```
46379: 0000000000000970    16 FUNC  GLOBAL DEFAULT  3  nv_soc_fuse_register_read
46530: 0000000000000960    16 FUNC  GLOBAL DEFAULT  3  __pfx_nv_soc_fuse_register_read
```

**16 bytes — a jump stub.** The only fuse strings are:

```
SEC_FAULT: _FUSE_POD
SEC_FAULT: _FUSE_SCPM
SEC_FAULT: _FUSE_POD_2ND
SEC_FAULT: _FUSE_SCPM_2ND
SEC_FAULT: _FAULT_FUSE_POD
```

**They are all "security fault" logs (POD = Point of Disable, SCPM = Secure Copy Protection Module),
not capability-discovery logic that "reads fuses to decide how many SMs/TCs to enable".**

**Comparison: the GSP firmware contains a full FWSEC certificate verification chain, while nvidia.ko's fuse accesses
are minimal.**
This shows **capability discovery (how many SMs, whether TCs are available) is done by the GSP firmware at init
time**, not by the driver.

In other words — **the driver knows throttling exists and detects it, but does not control it.**

**This is the project's most important piece of indirect evidence: the throttling happens below the driver.**

### 4. PRIV_ACCESS_MAP: context isolation, not capability restriction

```
GR_GLOBALCTX_BUFFER_PRIV_ACCESS_MAP
GR_GLOBALCTX_BUFFER_UNRESTRICTED_PRIV_ACCESS_MAP
GR_GLOBAL_BUFFER_GLOBAL_PRIV_ACCESS_MAP
```

**Three privilege maps whose purpose is "different contexts cannot access each other's registers" —
this is security isolation (preventing a malicious shader from reading/writing another process's GPU state),
not "restricting TC compute".**

**Eliminated.**

## 3. The fundamental conclusion of this round

**nvidia.ko contains no "Tensor Core capability configuration" or "compute throttling switch" whatsoever.**

Five clue classes, eight directions, all eliminated:

| Direction | Result |
|---|---|
| fuse capability discovery | does not exist (only a generic interface + security logs) |
| SKEDCHECK throttle check | detection, not control |
| License authorisation | vGPU-only, irrelevant to consumer |
| PRIV_ACCESS_MAP | context isolation, not capability restriction |
| Tensor/MMA code | zero hits |
| THROTTLE parameters | RM bus throttling, unrelated to compute |
| FECS_EVENT | name only, no format definition |
| GRCTX layout | fully parsed, no TC fields |

## 4. The single most important inference

**The very existence of `SKEDCHECK25_THROTTLED_IS_RESTRICTED` proves something in reverse:**

**The driver knows the "throttled state" exists and treats it as an exception to be detected —**

**but the driver neither sets it nor clears it.**

**This shows the throttling is set by a layer below the driver (GSP firmware / FECS microcode / hardware),
and the driver merely observes it passively.**

**And we have confirmed one by one:**
- the GSP firmware contains no TC logic (8 Ampere register addresses zero-hit)
- the FECS/GPCCS microcode only handles scheduling and synchronisation (449/177 iowr, all control/sync)
- the Falcon IO space `0x20000` segment is permanently invisible to the host (`HOST_IO_INDEX` only 6 bits)
- fuses are decided by hardware, physically irreversible

**All four layers point to the same conclusion: TC throttling is at the hardware layer, unreachable by software.**

## 5. Methodology note: why Ghidra was not used for a full decompile

**Ghidra 12.1.4 is ready and the doctor check is all green, but it was not used for full analysis this round.**

Reasons:

| Approach | Time estimate | Payoff |
|---|---|---|
| full Ghidra import + auto-analysis of 137 MB | hours | decompile 40k functions, 99% of them irrelevant |
| **symbol table + relocations + objdump (this round)** | **minutes** | **precisely locate all reference points of 186 strings** |
| targeted Ghidra decompile of a single function | minutes | do it when needed |

**Conclusion: for a binary with a complete symbol table, symbols + relocations are far more efficient than a full
decompile.**

**Ghidra's value lies in "symbol-less" or "type recovery needed" scenarios, not "large binaries with symbols".**

**This is the most important engineering judgement of this round.**

## 9. Supplementary verification: the GR context buffer is not at the end of VRAM (negative result)

**Motivation**: `_nv033210rm` shows the GR context stores a copy of the microcode:
```
context+0x1d0 = microcode pointer
context+0x1d8 = microcode byte count
context+0x1dc = microcode byte count (copy)
```
if the context buffer were in VRAM, its microcode copy should carry the signature
`d0 00 20 00 00 fe 04 00 bd a4 7e`.

**Experiment**: with the GPU at 100% load, dump VRAM `0x7E000000-0x7FF00000` (32 MB) via PRAMIN.

**Result**:
```
FECS  full header (d0 00 20 00): 0 occurrences
GPCCS full header (d0 00 14 00): 0 occurrences
common 7-byte signature:          0 occurrences
overall non-zero ratio: 96.78%
```

**Verdict**: the GR context buffer is not in this region.

**Possible locations**:
1. other regions of VRAM (this covered only the last 32 MB)
2. system memory (the context buffer may be allocated host-side via `os_alloc_mem`)
3. the microcode copy is encoded (`GRCTX_UCODE_DATA_*` are data fields, possibly not plaintext)

**To locate it one would need to read the pointer value at `context+0x1d0`, and the context structure itself lives in
driver memory — that requires parsing driver-private structures inside a kernel module, beyond the current
read-only research scope.**

**This is the round's only negative result, but it eliminates one possible location, which is valid information.**
