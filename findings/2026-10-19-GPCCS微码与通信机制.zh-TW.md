# 🔴🔴 2026-10-19 · GPCCS 微碼完整 dump + FECS/GPCCS 通訊機制發現

## 一、找到 GPCCS 的 Falcon 實例

此前探測 `0x41A000` 時讀到全 0，是因為**讀錯了偏移**——讀了基底本身而非 `+0x100`。
改為掃描「每 0x1000 讀 `+0x108`（HWCFG）」後，兩個 Falcon 同時現形：

```
0x409000  HWCFG=0x40204080  IMEM=32KB  CPUCTL=0x10  HWCFG1=0x80104126  sec=2 core=6
0x41A000  HWCFG=0x40102840  IMEM=16KB  CPUCTL=0x10  HWCFG1=0x80104126  sec=2 core=6
```

**HWCFG 解碼：**
- `0x40204080` → IMEM_SIZE 欄位 `0x080` = 128 → 128 × 256 B = **32 KB**（FECS）
- `0x40102840` → IMEM_SIZE 欄位 `0x040` = 64 → 64 × 256 B = **16 KB**（GPCCS）

**兩者 `HWCFG1 = 0x80104126` 完全一致**：`core_rev=6`（fuc6）、`security_model=2`（LIGHT SECURE）。

### 正確性驗證：三份微碼逐位元組對照

```
gk20a FECS  (參考): d0 00 10 00 | 00 fe 04 00 bd a4 7e | 2f 3a 00 f8 02
MX450 FECS        : d0 00 20 00 | 00 fe 04 00 bd a4 7e | a0 6c 00 f8 02
MX450 GPCCS       : d0 00 14 00 | 00 fe 04 00 bd a4 7e | 24 2f 00 f8 02
                     ↑ 堆疊頂端  ↑ 7 位元組簽章完全一致    ↑ lcall 目標
```

- 堆疊頂端值不同：`0x1000`(Kepler) / `0x2000`(FECS, 8KB DMEM) / `0x1400`(GPCCS, 5KB DMEM)
- **`00 fe 04 00 bd a4 7e` 七位元組完全一致** —— 這是 Falcon 微碼的固定入口模式
- `lcall` 目標不同：main 分別在 `0x3a2f` / `0x6ca0` / `0x2f24`

**三份獨立樣本的入口結構同構，確認 dump 正確。**

## 三、GPCCS 反組譯

### 與 FECS 的指令統計對比

| 指標 | FECS | GPCCS |
|---|---|---|
| 反組譯行數 | 11401 | 6059 |
| `iowr`（寫） | 449 | 177 |

## 四、重大發現：FECS 與 GPCCS 的位址集是包含關係

### GPCCS 的 38 個唯一位址，全部落在 FECS 的 72 個位址內

高頻位址對比：

| 位址 | FECS 次數 | GPCCS 次數 | 性質 |
|---|---|---|---|
| `0x21800` | 33 | 14 | 共享 |
| `0x21200` | 31 | 16 | 共享 |
| `0x23200` | 29 | 17 | 共享 |
| `0x22A00` | 28 | 19 | 共享 |
| `0x23800` | 27 | 12 | 共享 |
| `0x20A00` | 27 | **0** | **FECS 獨有** |
| `0x20000` | 26 | 9 | 共享 |
| `0x23300` | 20 | 13 | 共享 |
| `0x21300` | 20 | 13 | 共享 |
| `0x10C00` | 11 | 10 | 共享 |
| **`0x247FC`** | **4** | **4** | **完全相同** |
| **`0x246FC`** | **2** | **2** | **完全相同** |
| **`0x24FFC`** | **1** | **1** | **完全相同** |

**三個「頁尾」位址在兩個微碼中的存取次數完全相同**——這不可能是巧合，必然是雙方約定的通訊暫存器。

### GPCCS 獨有位址

`0x033F00`（1 次）—— 唯一超出 FECS 位址集的位址。

### FECS 獨有位址段

`0x28000-0x28E00`（多數）、`0x2C000-0x2C300`、`0x30200-0x30900` ——
這些是 FECS 獨有的管理區，GPCCS 完全不碰。

**推斷：`0x28000+` 是 GPC/TPC 級的全域配置，由 FECS 獨佔；`0x20000-0x24FFF` 是雙方共享的控制／同步區。**

## 五、mailbox 協定：微碼自己算出了位址關係

### 證據 1 · 位址加法

```asm
000018ee: mov $r15 0x8000        ; bit15
000018f2: mov $r9 0x23300        ; 基底
000018f6: iowr I[$r9] $r15       ; 寫 0x23300 = 0x8000
000018f9: add b32 $r9 $r9 0x14fc ; $r9 = 0x23300 + 0x14FC = 0x247FC
000018fe: iowr I[$r9] $r10       ; 寫 0x247FC = 參數
```

**`0x23300 + 0x14FC = 0x247FC` —— 微碼自己在執行時算出這個位址。**

這是「`0x247FC` 與 `0x23300` 屬於同一暫存器組」的直接證據，不是我們的猜測。

### 證據 2 · 中斷遮罩模式

```asm
0000190f: clear b32 $r15          ; $r15 = 0
00001911: mov $r9 0x246fc
00001915: iowr I[$r9] $r15        ; 寫 0x246FC = 0x00000000

00001953: mov $r15 -0x1           ; $r15 = 0xFFFFFFFF
00001955: mov $r9 0x246fc
00001959: iowr I[$r9] $r15        ; 寫 0x246FC = 0xFFFFFFFF
```

**只寫 `0` 和 `0xFFFFFFFF` 兩個值——這是典型的「中斷啟用／遮罩」或「遮罩全開／全關」模式。**

### 證據 3 · INDEX/DATA 配對

| 位址 | 差值 | 角色 |
|---|---|---|
| `0x246FC` | — | 控制 / 遮罩 |
| `0x247FC` | `+0x100` | 資料 / 參數 |
| `0x24FFC` | `+0x800` | 另一控制 |

**`+0x100` 的間距與 envytools 文件中 `DATA_INDEX`/`DATA` 的間距模式完全一致**
（`I[0x07000 + i*0x200]` → `I[0x07100 + i*0x200]`）。

### 綜合推斷

```
FECS（發起者，只寫）
   ↓ 寫 0x246FC（遮罩）/ 0x247FC（參數）/ 0x23300（事件位）
GR 共享控制區（0x20000-0x24FFF）
   ↓
GPCCS（執行者，會讀會寫）
   ↓ 輪詢狀態，執行後回寫
SM / GPC 硬體
```

**`0x246FC` = 遮罩，`0x247FC` = 資料，`0x23300` = 事件／中斷位。**

## 六、這對「Tensor Core 限速」意味著什麼

### 好消息

**現在手裡有兩個微碼的完整反組譯，且知道它們的分工與通訊位址。**

- FECS 管全域（`0x28000+` 獨佔）
- GPCCS 管 GPC 內的 SM（共享區 + 輪詢）
- 兩者透過 `0x246FC/0x247FC/0x24FFC` 通訊

### 壞消息

**這些位址全部是「控制／同步」性質，不是「SM 內部配置」性質。**

依據：
1. 寫入值以位元遮罩為主（`0x8000`, `0x2000`, `0`, `0xFFFFFFFF`）
2. `iord` 在 GPCCS 裡出現 51 次，說明是輪詢等待而非配置讀取
3. 沒有出現「按 SM 索引迴圈」的模式（此前已證否 14 次迴圈）
4. `0x20000` 段在 BAR0 中不存在（五種假設已排除），說明它是 GR 內部匯流排位址

**結論：TC 的配置不在 FECS/GPCCS 微碼裡，而是由硬體（熔絲 + SM 內部邏輯）決定。**

**微碼能做的是「排程」和「開關」，不是「配置算力」。**

這與之前的判斷一致：
- GSP 韌體管全域，不管 SM 內部
- FECS/GPCCS 管排程與同步，不管 SM 內部單元配置
- SM 無微碼（純硬體）
- TC 的可用性由熔絲／佈線決定
