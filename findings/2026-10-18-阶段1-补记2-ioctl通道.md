# 2026-10-18 · 阶段 1 补记 2：NV2080 ioctl 通道打通（80%）与卡点

## 结论摘要

**从「完全不通」推进到「ioctl 通道打通、root client 分配成功」，**
但在 `NV20_SUBDEVICE_0` 之后的 `GR_GET_INFO` 处返回 `NV_STATUS 31`，未能取到 TC 计数。

工具已完整保留在 `tools/read_tc_count.c`，注释标注了每一个已修复的坑，后人可从此处继续。

## 一、修复的三个真实 bug

### Bug 1 · ioctl 命令号不该加 NV_IOCTL_BASE

最初按常见写法用 `_IOWR('F', NV_IOCTL_BASE + NV_ESC_RM_ALLOC, ...)`，
即 `200 + 0x2B = 243`，**始终返回 EINVAL**。

**靠 strace 抓 `nvidia-smi` 的真实调用才发现真相**：

```
ioctl(9, _IOC(_IOC_READ|_IOC_WRITE, 0x46, 0x2b, 0x30), ...) = 0   ← RM_ALLOC, 48B
ioctl(9, _IOC(_IOC_READ|_IOC_WRITE, 0x46, 0x2a, 0x20), ...) = 0   ← RM_CONTROL, 32B
```

`0x46` = `'F'`，`nr` 就是 **`0x2b` 本身**，不叠加 base。
改用 `NV_ESC_RM_ALLOC` 原值后，**ROOT_CLIENT 立即分配成功**（`hClient = 0xc1d00063`）。

> 方法论记录：**私有 ioctl 的编号不要靠猜，strace 一个能工作的官方工具最快。**

### Bug 2 · NV0080_ALLOC_PARAMETERS 的 flags 宽度

自建结构里把 `flags` 声明成 `NvU64`（8 字节），官方定义是 **`NvV32`（4 字节）**：

```c
typedef struct NV0080_ALLOC_PARAMETERS {
    NvU32    deviceId;
    NvHandle hClientShare;
    NvHandle hTargetClient;
    NvHandle hTargetDevice;
    NvV32    flags;                                   /* ← 4 字节，不是 8 */
    NV_DECLARE_ALIGNED(NvU64 vaSpaceSize, 8);
    NV_DECLARE_ALIGNED(NvU64 vaStartInternal, 8);
    NV_DECLARE_ALIGNED(NvU64 vaLimitInternal, 8);
    NvV32    vaMode;
} NV0080_ALLOC_PARAMETERS;
```

多出的 4 字节让后面所有字段整体错位。结构总大小恰好都是 56，
**所以 sizeof 校验能过，但字段读错** —— 这是最难查的一类 bug。

### Bug 3 · 缺少打开设备节点

`nvidia-smi` 在 RM_ALLOC 前会先 `open("/dev/nvidia0")`。
补上该步骤后，DEVICE_0 / SUBDEVICE_0 不再报 status=64，而是返回句柄。

## 二、当前卡点

```
[1] ROOT_CLIENT (0x41)   hClient    = 0xc1d00063
[2] DEVICE_0 (0x80)      hDevice    = 0xcaf00000
[3] SUBDEVICE_0 (0x2080) hSubdevice = 0xcaf00001
[4] GR_GET_INFO
    index=0x00 NUM_SMS              status=31
    index=0x23 TENSOR_CORE_COUNT    status=31
```

- `0xc1d0xxxx` 形态是有效 client handle；`0xcaf0xxxx` 形态**疑似驱动返回的占位/无效对象**
- `NV_STATUS 31 (0x1F)` 在 `nvstatus.h` 中无直接字面定义（该文件用宏生成枚举）

**判断**：device/subdevice 的对象链没有真正建立，因此 control 调用被拒。
剩余工作是把 `0xcaf0xxxx` 的语义与 control 权限搞清楚，属于驱动内部对象模型范畴。

## 三、为什么在此收敛

| 因素 | 说明 |
|---|---|
| 边际收益下降 | TC 计数只是「驱动怎么看这块硅片」的旁证，不改变 0.60 TFLOPS 的实测事实 |
| 成本 | 需要逆向驱动的对象句柄编码与 control 权限校验，估计还需数轮调试 |
| 已有证据充分 | HMMA 指令存在 + 执行不报错 + 吞吐仅为理论 5–10% + cuBLAS 同现象，四条互证 |
| 工具已留档 | 三个 bug 的修法都写进注释，任何人可从此处接续 |

**这不是失败，是把路走到了「还差最后一段」并标好了路标。**

## 四、如果继续，建议路径

1. **对比法**：写一个最小程序 strace 自己，与 `nvidia-smi` 的 ioctl 序列逐条比对，
   找出缺失的前置调用（strace 里看到 `nvidia-smi` 在 RM_ALLOC 前还调了 `0xd2`、`0xd6`、`0xc8` 三个 ioctl）
2. **更省力的替代**：直接链接 `libnvidia-ml.so`，用 NVML 的 `nvmlDeviceGetFieldValues`
   试探是否可读 GR_INFO 类字段
3. **彻底换路**：用 CUPTI 采集张量管线活跃计数器，直接观察 TC 是否被物理激活
   （信息量比 TC 计数更大，且不依赖私有 ioctl）
