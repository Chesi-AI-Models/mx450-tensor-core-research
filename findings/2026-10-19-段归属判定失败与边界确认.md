# 2026-10-19 · 0x20000 段归属：三条路线全部尝试，判定为「公开资料不可解」

## 一、路线 2 失败：不是 14 次循环

`0x21800` 在反汇编中出现 37 次，但分布如下：

```
000000ad  mov $r9 0x21800     ← 函数 A
00000723  mov $r9 0x21800     ← 函数 B
000009e9  mov $r9 0x21800     ← 函数 C
00000b8b  mov $r9 0x21800     ← 函数 D
00000e76  mov $r9 0x21800     ← 函数 E
00000eed  mov $r9 0x21800
00000f0f  mov $r9 0x21800
00001ad7  mov $r9 0x21800
...
```

**分散在十余个不同函数中，且 `mov $rX, 0xe`（14）在全文中零命中。**

**判定：`0x21800` 是多个函数共用的功能寄存器，不是「按 SM 数循环初始化」的计数器。**

## 二、路线 1 失败：HAL 源码无定义

```
gh search code "NV_PGRAPH_GPC"  → 0 结果
gh search code "NV_PGRAPH_TPC"  → 0 结果
```

**NVIDIA 的 `open-gpu-kernel-modules`（Turing+ 全世代）中不存在 GPC/TPC 的寄存器宏定义。**

说明：GPC/TPC/SM 级的寄存器初始化逻辑位于**闭源 HAL 二进制**（`nv-kernel.o_binary`）内，
不在 MIT/GPL 发布的开源部分。

## 三、路线 3 未验证（需外部资料）

对照看雪 AD102 FECS 分析需翻阅原文，其结论（是否同样访问 `0x2000x`）未在本次核查范围内。

## 四、最终判定

**Turing 的 `0x20000` 段语义，在当前可获得的公开资料范围内无法确定。**

三重障碍：

| 障碍 | 状态 |
|---|---|
| envytools rnndb | 覆盖止于 Maxwell，且记录的 0x20000 段上界（0x227FF）小于微码实际访问范围 |
| NVIDIA 开源头文件 | tu102 目录无 `dev_gpc.h` / `dev_tpc.h` |
| NVIDIA 开源 HAL | `NV_PGRAPH_GPC` / `NV_PGRAPH_TPC` 零定义，关键逻辑在闭源 `.o_binary` |

**这不是"还没找到"，是"这一层信息 NVIDIA 没有公开"。**

## 五、可以继续的方向（都需要额外条件）

| 方向 | 需要什么 | 可行性 |
|---|---|---|
| 反汇编闭源 HAL | `nv-kernel.o_binary` 逆向（IDA/Ghidra） | 可行但工作量大，且已剥离符号 |
| 在真机上做写测试 | 逐个地址写入并观察 GPU 反应 | **高风险**，可能挂死 GPU |
| 等第三方公开 | AD102 逆向笔记的完整版 | 不受控 |

**注意**：第二项（写测试）是唯一能在本机推进的，但违背了本项目"只读优先"的安全原则，
且 `0x20000` 段确认为 PTHERM/PFUSE/PUNITS 一部分的情况下，误写可能触发温度保护或熔丝逻辑。

## 七、结论

**今晚把"能看见"这条线走到了公开资料的尽头。**

- 微码拿到了 → 反汇编了 → 寄存器访问统计了
- 但「0x20000 段每个地址是什么」这一层，NVIDIA 从未公开
- 继续需要：逆向闭源 HAL 二进制（工作量大），或高风险写测试

**下一次推进的前提，是拿到 `nv-kernel.o_binary` 的符号或第三方 Turing 寄存器映射。**

**在此之前，硬闯没有意义。**
