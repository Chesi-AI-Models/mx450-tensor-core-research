# P2 stage four: NV_MEMORY enum confirmed, the cache_type contradiction resolved

## 1. Recalling the contradiction

The disassembly showed that in `os_map_kernel_space` the `cache_type == 0` branch tail-calls `ioremap_cache`,
while from memory I believed `NV_MEMORY_UNCACHED = 0`. The two did not agree, so calling was paused.

## 2. Source-code evidence

`gh search code "NV_MEMORY_UNCACHED" --repo NVIDIA/open-gpu-kernel-modules` located:

```
src/nvidia/inc/kernel/os/nv_memory_type.h
kernel-open/common/inc/os/nv_memory_type.h
```

The complete enum (a 41-line file, quoted verbatim):

```c
#define NV_MEMORY_NONCONTIGUOUS      0
#define NV_MEMORY_CONTIGUOUS         1
#define NV_MEMORY_CACHED             0
#define NV_MEMORY_UNCACHED           1
#define NV_MEMORY_WRITECOMBINED      2
#define NV_MEMORY_WRITEBACK          5
#define NV_MEMORY_DEFAULT            6
#define NV_MEMORY_UNCACHED_WEAK      7
```

**Key: `NV_MEMORY_CACHED = 0`, `NV_MEMORY_UNCACHED = 1`.**

## 3. Three-way cross-validation

| edx value | Enum constant | Disassembly branch behaviour | Consistent? |
|---|---|---|---|
| **0** | `NV_MEMORY_CACHED` | tail-calls `ioremap_cache` | ✅ exact match |
| **2** | `NV_MEMORY_WRITECOMBINED` | `je 0xffffffffc2c13c33` | ✅ |
| **6** | `NV_MEMORY_DEFAULT` | `je 0xffffffffc2c13c4e` | ✅ |
| other | — | log and return NULL | ✅ matches the source's default branch |

**Conclusion: the disassembly analysis was accurate; the earlier error was remembering 0 as UNCACHED.**

## 4. Function entry offset confirmed

```
ffffffffc2c13bb0  t __pfx_os_map_kernel_space   ← 16-byte CET prefix
ffffffffc2c13bc0  t os_map_kernel_space         ← real entry (+0x10)
```

The dump starts with the bytes `0f 1f 40 d6` (a multi-byte NOP used by GCC for alignment), not `endbr64`
(`f3 0f 1e fa`) — meaning endbr64 sits inside the `__pfx_` region and the real function body begins at the
NOP alignment.

**`0xffffffffc2c13bc0` is confirmed as the function body, not a thunk.**

## 5. Final confirmed prototype

```c
void *os_map_kernel_space(void *phys_addr,   /* rdi */
                          NvU64 size,        /* rsi */
                          NvU32 cache_type); /* edx: 0=CACHED 1=UNCACHED 2=WC 6=DEFAULT */
```

Behaviour:
1. `phys_addr == NULL && cache_type == 0` → returns some global object (`mov -0x11191531(%rip),%rax`)
2. `phys_addr != NULL`:
   - checks the IF flag and `preempt_count()` (**must not be called from interrupt/atomic context**)
   - dispatches on `cache_type`: 0 → `ioremap_cache`; 2 → WC path; 6 → DEFAULT path
   - default: `log(4, ...)` and return NULL

**Note**: the 4-parameter version `osMapKernelSpace(addr, size, cache_type, protect)` is its upper-layer wrapper;
`protect` is handled further up and does not enter this function.

## 7. Can it be called now?

**Technically the preconditions are met** (address, signature, enum, behaviour all confirmed). But:

| Risk | Note |
|---|---|
| it really operates on GPU address space | not read-only; it establishes a mapping at the ioremap layer |
| residual uncertainty in parameter semantics | `size` alignment requirements and whether `phys_addr` must be page-aligned are unverified |
| cannot be rehearsed in QEMU | the VM has no NVIDIA module |
| consequences of failure | may return NULL (harmless), or establish a bad mapping that breaks later accesses |

**Recommendation**: for the first call use the most conservative parameters — `cache_type = NV_MEMORY_UNCACHED (1)`
(the standard choice for register access), a page-aligned address, `size = PAGE_SIZE`, and immediately release with
`os_unmap_kernel_space`.
