# 🔴🔴 2026-10-19 · GPCCS microcode fully dumped + discovery of the FECS/GPCCS communication mechanism

## 1. Locating GPCCS's Falcon instance

The earlier probe of `0x41A000` read all zeros because **the offset was wrong** — it read the base address itself
rather than `+0x100`. After switching to scanning "read `+0x108` (HWCFG) every 0x1000", both Falcons appeared at once:

```
0x409000  HWCFG=0x40204080  IMEM=32KB  CPUCTL=0x10  HWCFG1=0x80104126  sec=2 core=6
0x41A000  HWCFG=0x40102840  IMEM=16KB  CPUCTL=0x10  HWCFG1=0x80104126  sec=2 core=6
```

**HWCFG decoding:**
- `0x40204080` → IMEM_SIZE field `0x080` = 128 → 128 × 256 B = **32 KB** (FECS)
- `0x40102840` → IMEM_SIZE field `0x040` = 64 → 64 × 256 B = **16 KB** (GPCCS)

**Both have `HWCFG1 = 0x80104126` identically**: `core_rev=6` (fuc6), `security_model=2` (LIGHT SECURE).

### Correctness check: three microcodes compared byte by byte

```
gk20a FECS  (reference): d0 00 10 00 | 00 fe 04 00 bd a4 7e | 2f 3a 00 f8 02
MX450 FECS            : d0 00 20 00 | 00 fe 04 00 bd a4 7e | a0 6c 00 f8 02
MX450 GPCCS           : d0 00 14 00 | 00 fe 04 00 bd a4 7e | 24 2f 00 f8 02
                        ↑ stack top  ↑ 7-byte signature identical  ↑ lcall target
```

- stack top values differ: `0x1000` (Kepler) / `0x2000` (FECS, 8 KB DMEM) / `0x1400` (GPCCS, 5 KB DMEM)
- **the seven bytes `00 fe 04 00 bd a4 7e` are identical** — this is the fixed entry pattern of Falcon microcode
- `lcall` targets differ: main is at `0x3a2f` / `0x6ca0` / `0x2f24` respectively

**Three independent samples share an isomorphic entry structure, confirming the dump is correct.**

```

**6,059 lines, 273 KB.**

0000000a: lcall 0x2f24        ; main

```

### Instruction statistics compared with FECS

| Metric | FECS | GPCCS |
|---|---|---|
| disassembly lines | 11,401 | 6,059 |
| `iowr` (write) | 449 | 177 |
| **`iord` (read)** | **0** | **51** |
| `lcall` | 932 | 461 |
| unique iowr addresses | 72 | 38 |

**Key difference: FECS only writes, GPCCS has 51 reads.**

This shows FECS is the "command initiator" (configure and go) while GPCCS is the "command executor" (needs to poll
status and wait for completion).

## 4. Major discovery: FECS's and GPCCS's address sets are in a containment relation

### All 38 unique GPCCS addresses fall inside FECS's 72

High-frequency address comparison:

| Address | FECS count | GPCCS count | Nature |
|---|---|---|---|
| `0x21800` | 33 | 14 | shared |
| `0x21200` | 31 | 16 | shared |
| `0x23200` | 29 | 17 | shared |
| `0x22A00` | 28 | 19 | shared |
| `0x23800` | 27 | 12 | shared |
| `0x20A00` | 27 | **0** | **FECS only** |
| `0x20000` | 26 | 9 | shared |
| `0x23300` | 20 | 13 | shared |
| `0x21300` | 20 | 13 | shared |
| `0x10C00` | 11 | 10 | shared |
| **`0x247FC`** | **4** | **4** | **identical** |
| **`0x246FC`** | **2** | **2** | **identical** |
| **`0x24FFC`** | **1** | **1** | **identical** |

**The three "page-tail" addresses have exactly the same access counts in both microcodes — that cannot be
coincidence; they must be communication registers agreed between the two sides.**

### GPCCS-only address

`0x033F00` (1 access) — the only address outside FECS's address set.

### FECS-only address ranges

`0x28000-0x28E00` (mostly), `0x2C000-0x2C300`, `0x30200-0x30900` —
these are FECS-exclusive management regions that GPCCS never touches.

**Inference: `0x28000+` is GPC/TPC-level global configuration held exclusively by FECS; `0x20000-0x24FFF` is the
shared control/synchronisation region.**

## 5. The mailbox protocol: the microcode itself computes the address relationships

### Evidence 1 · address addition

```asm
000018ee: mov $r15 0x8000        ; bit15
000018f2: mov $r9 0x23300        ; base
000018f6: iowr I[$r9] $r15       ; write 0x23300 = 0x8000
000018f9: add b32 $r9 $r9 0x14fc ; $r9 = 0x23300 + 0x14FC = 0x247FC
000018fe: iowr I[$r9] $r10       ; write 0x247FC = parameter
```

**`0x23300 + 0x14FC = 0x247FC` — the microcode computes this address itself at runtime.**

This is direct evidence that "`0x247FC` and `0x23300` belong to the same register group", not our speculation.

### Evidence 2 · interrupt mask pattern

```asm
0000190f: clear b32 $r15          ; $r15 = 0
00001911: mov $r9 0x246fc
00001915: iowr I[$r9] $r15        ; write 0x246FC = 0x00000000

00001953: mov $r15 -0x1           ; $r15 = 0xFFFFFFFF
00001955: mov $r9 0x246fc
00001959: iowr I[$r9] $r15        ; write 0x246FC = 0xFFFFFFFF
```

**Only two values are ever written, `0` and `0xFFFFFFFF` — the classic "interrupt enable/mask" or "mask all on/all
off" pattern.**

### Evidence 3 · INDEX/DATA pairing

| Address | Delta | Role |
|---|---|---|
| `0x246FC` | — | control / mask |
| `0x247FC` | `+0x100` | data / parameter |
| `0x24FFC` | `+0x800` | another control |

**The `+0x100` spacing is exactly the pattern envytools documents for `DATA_INDEX`/`DATA`**
(`I[0x07000 + i*0x200]` → `I[0x07100 + i*0x200]`).

### Overall inference

```
FECS (initiator, write-only)
   ↓ writes 0x246FC (mask) / 0x247FC (parameter) / 0x23300 (event bit)
GR shared control region (0x20000-0x24FFF)
   ↓
GPCCS (executor, reads and writes)
   ↓ polls status, writes back after executing
SM / GPC hardware
```

**`0x246FC` = mask, `0x247FC` = data, `0x23300` = event/interrupt bit.**

## 6. What this means for "Tensor Core throttling"

### Good news

**We now have complete disassemblies of both microcodes, and know their division of labour and their communication
addresses.**

- FECS manages the global picture (`0x28000+`, exclusive)
- GPCCS manages the SMs inside a GPC (shared region + polling)
- the two communicate via `0x246FC/0x247FC/0x24FFC`

### Bad news

**All these addresses are "control/synchronisation" in nature, not "SM internal configuration".**

Basis:
1. the written values are mostly bit masks (`0x8000`, `0x2000`, `0`, `0xFFFFFFFF`)
2. `iord` appears 51 times in GPCCS, indicating polling for completion rather than configuration reads
3. no "loop indexed by SM number" pattern appears (the 14-iteration loop was already disproven)
4. the `0x20000` segment does not exist in BAR0 (five hypotheses eliminated), showing it is a GR-internal bus address

**Conclusion: TC configuration is not in the FECS/GPCCS microcode; it is determined by hardware (fuses + SM internal
logic).**

**What the microcode can do is "schedule" and "switch", not "configure compute".**

This is consistent with earlier judgements:
- GSP firmware manages the global picture, not SM internals
- FECS/GPCCS manage scheduling and synchronisation, not SM-internal unit configuration
- the SM has no microcode (pure hardware)
- TC availability is decided by fuses/wiring
