# 🔴🔴🔴 2026-10-19 · Falcon IO 地址空间完整模型（架构级发现）

**简体中文** | [繁體中文](2026-10-19-Falcon-IO地址空间完整模型.zh-TW.md) | [English](2026-10-19-Falcon-IO地址空间完整模型.en.md)

## 一、核心文档（envytools `docs/hw/falcon/io.rst` 第 24-40 行，原样引用）

```
The addresses are different between falcon and host. From falcon POV, the IO space
is word-addressable 0x40000-byte space. However, most registers are duplicated
64 times: bits 2-7 of the address are ignored. The few registers that don't
ignore these bits are called "indexed" registers. From host POV, the falcon IO
space is a 0x1000-byte window in BAR0. Its base address is engine-dependent.
First 0xf00 bytes of this window are tied to the falcon IO space, while last 0x100
bytes contain several host-only registers. On G98:GF119, host mmio address
falcon_base + X is directed to falcon IO space address X << 6 | HOST_IO_INDEX << 2.
On GF119+, some engines stopped using the indexed accesses. On those, host mmio
address falcon_base + X is directed to falcon IO space address X.

HOST_IO_INDEX is specified in the host-only MMIO register falcon_base + 0xffc:

MMIO 0xffc: HOST_IO_INDEX
  bits 0-5: selects bits 2-7 of the falcon IO space when accessed from host.

Unaligned accesses to the IO space are unsupported, both from host and falcon.
Low 2 bits of addresses should be 0 at all times.
```

## 二、由此建立的完整模型

### Falcon 侧

| 项 | 值 |
|---|---|
| IO 空间总大小 | **0x40000 字节（256 KB）** |
| 地址范围 | `0x00000 - 0x3FFFF` |
| 对齐要求 | 低 2 位必须为 0（4 字节对齐） |
| 寄存器复制 | 大多数寄存器复制 64 份，`bits 2-7` 被忽略 |
| 例外 | "indexed" 寄存器不忽略 `bits 2-7`，用它们做索引 |

### Host 侧

| 项 | 值 |
|---|---|
| 可见窗口 | **0x1000 字节（4 KB）**，位于 `falcon_base + 0x000` |
| 窗口内划分 | `0x000-0xEFF` → Falcon IO 空间；`0xF00-0xFFF` → host-only 寄存器 |
| `HOST_IO_INDEX` | `falcon_base + 0xFFC`，`bits 0-5` 选择 Falcon IO 的 `bits 2-7` |
| 老式映射（G98:GF119） | `falcon_addr = (host_offset << 6) \| (HOST_IO_INDEX << 2)` |
| 新式映射（GF119+ 部分引擎） | `falcon_addr = host_offset` |

### 关键结论

**`HOST_IO_INDEX` 的 6 个 bit 只能选择 `bits 2-7`，即「第几个副本」。**

**它无法选择 `bits 8+`——而 `bits 8+` 才是「哪个寄存器」。**

**因此 host 最多只能访问 Falcon IO 空间的最低 4 KB（`0x0000-0x0FFF`）。**

**`0x20000` 段（`bits 17:8` 非零）对 host 永久不可见。**

## 三、这解释了此前所有的矛盾

| 现象 | 解释 |
|---|---|
| 微码 iowr `0x20000` 段 376 次（85%） | 合法的 Falcon IO 地址，在 256 KB 空间内 |
| BAR0 `0x020000` 读回 `0xBADF5040` | host 窗口只有 4 KB，`0x20000` 远超窗口 |
| `HOST_IO_INDEX` 无法帮上忙 | 只能选 `bits 2-7`，选不到 `bits 17:8` |
| `0x409818` 在 BAR0 里有效 | **不是** Falcon IO 地址，而是外部 BAR0 地址（见下节） |
| 五种假设全部失败 | 因为前提错了——它不是 BAR0 地址，也不是 UAS/XFER/DMEM |

## 四、GPCCS 微码揭示的两套地址机制

### 机制 A · 直接 iowr（Falcon IO 空间）

```asm
00002f28: mov $r9 0x23200
00002f2c: iowr I[$r9] $r15        ; bit31=0 → Falcon IO 空间
```

**地址 `0x00000-0x3FFFF`，访问 Falcon 控制的引擎内部寄存器。**

### 机制 B · 带 bit31 的外部访问（BAR0）

```asm
; 0x201 子程序：构造带标志的地址
00000201: mov $r9 0x3fffffc       ; 26 位地址掩码
00000209: and $r10 $r9            ; 地址只保留低 26 位
0000020f: mov $r9 0x80000000      ; bit 31
00000214: shl b32 $r12 0x1a       ; bit26 = 读/写方向
00000217: or  $r10 $r9            ; 设置 bit31
0000021a: or  $r10 $r11           ; 合并参数
0000021d: or  $r11 $r10 $r12      ; 合并方向位
00000220: mov $r10 0x1ca00        ; 命令队列地址
00000224: lcall 0x1d8             ; 提交命令
```

**`iowr I[0x80000000 | (addr & 0x3FFFFFC)]` → 访问 BAR0 绝对地址 `addr`。**

**GPCCS 用它访问 FECS 的寄存器：**

```asm
00000276: mov $r10 0x409818       ; FECS 段内的 BAR0 地址
0000027c: lcall 0x337             ; → 0x2a1 → 0x201 → 打包 bit31
00000282: mov $r10 0x409c1c
0000028a: lcall 0x337
0000028e: mov $r10 0x409c18
00000294: lcall 0x26a             ; 读
0000029b: bra b32 $r10 0x1 e 0x28e ; 循环轮询！
```

**这是 GPCCS 等待 FECS 的握手循环。**

### 机制 B 的验证

**BAR0 实测（GPU 满载）：**

```
0x409800 = 0x00000004
0x409808 = 0x00000001
0x409810 = 0x00042790   ← 非零
0x409818 = 0x00000000
0x409830 = 0x03030000   ← 非零
0x409838 = 0x00001F97   ← 非零
0x409C00 = 0x00000002
```

**这些是真实寄存器（不是 BAD），证明机制 B 访问的确实是 BAR0 地址空间。**

**而 GPCCS 轮询的 `0x409818` / `0x409C18` / `0x409C1C` 当前值均为 0——**
**说明握手处于「空闲/已完成」状态（GPU 在跑 GEMM，但不需要 context switch）。**

```

```

**这是本项目对 Turing GR 引擎架构最完整的一次刻画。**

## 六、这对「Tensor Core 限速」的最终意义

### 已经确定的事

1. **TC 硬件存在**（SASS 可编译执行 HMMA，实测 0.60 TFLOPS）
2. **TC 被限速到理论值的 5%**（理论 6-12 TFLOPS）
3. **控制点不在任何 host 可读写的层**：
   - GSP 固件：已完整反汇编，不含 TC 逻辑
   - vBIOS：受 FWSEC 证书链保护
   - 系统 BIOS：Boot Guard 加密
   - **FECS/GPCCS 微码：已完整反汇编，只管调度与同步**
   - **Falcon IO 空间 `0x20000` 段：host 永久不可见**
   - SM 微码：不存在（纯硬件）
   - 硬件熔丝：物理不可逆

### 新增的一条硬边界

**即使知道 `0x20000` 段是 GR 内部寄存器，host 也永远读不到它——**
**这是 `HOST_IO_INDEX` 只有 6 位（只能选 `bits 2-7`）决定的硬件设计。**

**要读它，只有两条路：**
1. **修改微码**，让它把 `0x20000` 段的值搬到 host 可见的地方
   → 但微码受 **FWSEC 签名验证**，改一个字节即拒绝加载
2. **物理层探测**（逻辑分析仪抓 Falcon 的 IO 总线）
   → 超出软件研究范畴

**第一条路被签名挡住，第二条路需要拆机。**
