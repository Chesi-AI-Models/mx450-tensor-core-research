## 一、找到 GPCCS 的 Falcon 实例

此前探测 `0x41A000` 时读到全 0，是因为**读错了偏移**——读了基址本身而非 `+0x100`。
改为扫描「每 0x1000 读 `+0x108`（HWCFG）」后，两个 Falcon 同时现形：

```
0x409000  HWCFG=0x40204080  IMEM=32KB  CPUCTL=0x10  HWCFG1=0x80104126  sec=2 core=6
0x41A000  HWCFG=0x40102840  IMEM=16KB  CPUCTL=0x10  HWCFG1=0x80104126  sec=2 core=6
```

**HWCFG 解码：**
- `0x40204080` → IMEM_SIZE 字段 `0x080` = 128 → 128 × 256 B = **32 KB**（FECS）
- `0x40102840` → IMEM_SIZE 字段 `0x040` = 64 → 64 × 256 B = **16 KB**（GPCCS）

**两者 `HWCFG1 = 0x80104126` 完全一致**：`core_rev=6`（fuc6）、`security_model=2`（LIGHT SECURE）。

### 正确性验证：三份微码逐字节对照

```
gk20a FECS  (参考): d0 00 10 00 | 00 fe 04 00 bd a4 7e | 2f 3a 00 f8 02
MX450 FECS        : d0 00 20 00 | 00 fe 04 00 bd a4 7e | a0 6c 00 f8 02
MX450 GPCCS       : d0 00 14 00 | 00 fe 04 00 bd a4 7e | 24 2f 00 f8 02
                     ↑ 栈顶      ↑ 7 字节签名完全一致    ↑ lcall 目标
```

- 栈顶值不同：`0x1000`(Kepler) / `0x2000`(FECS, 8KB DMEM) / `0x1400`(GPCCS, 5KB DMEM)
- **`00 fe 04 00 bd a4 7e` 七字节完全一致** —— 这是 Falcon 微码的固定入口模式
- `lcall` 目标不同：main 分别在 `0x3a2f` / `0x6ca0` / `0x2f24`

**三份独立样本的入口结构同构，确认 dump 正确。**

## 三、GPCCS 反汇编

```bash
envydis -m falcon -V fuc6 -i -n gpccs_imem.bin > gpccs_plain.asm
```

**6059 行，273 KB。**

```
00000000: mov $r0 0x1400      ; 栈顶
00000005: mov $sp $r0
00000008: clear b32 $r10
0000000a: lcall 0x2f24        ; main
0000000e: exit
```

### 与 FECS 的指令统计对比

| 指标 | FECS | GPCCS |
|---|---|---|
| 反汇编行数 | 11401 | 6059 |
| `iowr`（写） | 449 | 177 |
| **`iord`（读）** | **0** | **51** |
| `lcall` | 932 | 461 |
| 唯一 iowr 地址 | 72 | 38 |

**关键差异：FECS 只写不读，GPCCS 有 51 条读。**

说明 FECS 是「命令发起者」（配置完就走），GPCCS 是「命令执行者」（需要轮询状态、等待完成）。

## 四、重大发现：FECS 与 GPCCS 的地址集是包含关系

### GPCCS 的 38 个唯一地址，全部落在 FECS 的 72 个地址内

高频地址对比：

| 地址 | FECS 次数 | GPCCS 次数 | 性质 |
|---|---|---|---|
| `0x21800` | 33 | 14 | 共享 |
| `0x21200` | 31 | 16 | 共享 |
| `0x23200` | 29 | 17 | 共享 |
| `0x22A00` | 28 | 19 | 共享 |
| `0x23800` | 27 | 12 | 共享 |
| `0x20A00` | 27 | **0** | **FECS 独有** |
| `0x20000` | 26 | 9 | 共享 |
| `0x23300` | 20 | 13 | 共享 |
| `0x21300` | 20 | 13 | 共享 |
| `0x10C00` | 11 | 10 | 共享 |
| **`0x247FC`** | **4** | **4** | **完全相同** |
| **`0x246FC`** | **2** | **2** | **完全相同** |
| **`0x24FFC`** | **1** | **1** | **完全相同** |

**三个「页尾」地址在两个微码中的访问次数完全相同**——这不可能是巧合，必然是双方约定的通信寄存器。

### GPCCS 独有地址

`0x033F00`（1 次）—— 唯一超出 FECS 地址集的地址。

### FECS 独有地址段

`0x28000-0x28E00`（多数）、`0x2C000-0x2C300`、`0x30200-0x30900` ——
这些是 FECS 独有的管理区，GPCCS 完全不碰。

**推断：`0x28000+` 是 GPC/TPC 级的全局配置，由 FECS 独占；`0x20000-0x24FFF` 是双方共享的控制/同步区。**

## 五、mailbox 协议：微码自己算出了地址关系

### 证据 1 · 地址加法

```asm
000018ee: mov $r15 0x8000        ; bit15
000018f2: mov $r9 0x23300        ; 基址
000018f6: iowr I[$r9] $r15       ; 写 0x23300 = 0x8000
000018f9: add b32 $r9 $r9 0x14fc ; $r9 = 0x23300 + 0x14FC = 0x247FC
000018fe: iowr I[$r9] $r10       ; 写 0x247FC = 参数
```

**`0x23300 + 0x14FC = 0x247FC` —— 微码自己在运行时算出这个地址。**

这是「`0x247FC` 与 `0x23300` 属于同一寄存器组」的直接证据，不是我们的猜测。

### 证据 2 · 中断屏蔽模式

```asm
0000190f: clear b32 $r15          ; $r15 = 0
00001911: mov $r9 0x246fc
00001915: iowr I[$r9] $r15        ; 写 0x246FC = 0x00000000

00001953: mov $r15 -0x1           ; $r15 = 0xFFFFFFFF
00001955: mov $r9 0x246fc
00001959: iowr I[$r9] $r15        ; 写 0x246FC = 0xFFFFFFFF
```

**只写 `0` 和 `0xFFFFFFFF` 两个值——这是典型的「中断使能/屏蔽」或「掩码全开/全关」模式。**

### 证据 3 · INDEX/DATA 配对

| 地址 | 差值 | 角色 |
|---|---|---|
| `0x246FC` | — | 控制 / 掩码 |
| `0x247FC` | `+0x100` | 数据 / 参数 |
| `0x24FFC` | `+0x800` | 另一控制 |

**`+0x100` 的间距与 envytools 文档中 `DATA_INDEX`/`DATA` 的间距模式完全一致**
（`I[0x07000 + i*0x200]` → `I[0x07100 + i*0x200]`）。

### 综合推断

```
FECS（发起者，只写）
   ↓ 写 0x246FC（掩码）/ 0x247FC（参数）/ 0x23300（事件位）
GR 共享控制区（0x20000-0x24FFF）
   ↓
GPCCS（执行者，会读会写）
   ↓ 轮询状态，执行后回写
SM / GPC 硬件
```

**`0x246FC` = 掩码，`0x247FC` = 数据，`0x23300` = 事件/中断位。**

## 六、这对「Tensor Core 限速」意味着什么

### 好消息

**现在手里有两个微码的完整反汇编，且知道它们的分工与通信地址。**

- FECS 管全局（`0x28000+` 独占）
- GPCCS 管 GPC 内的 SM（共享区 + 轮询）
- 两者通过 `0x246FC/0x247FC/0x24FFC` 通信

### 坏消息

**这些地址全部是「控制/同步」性质，不是「SM 内部配置」性质。**

依据：
1. 写入值以位掩码为主（`0x8000`, `0x2000`, `0`, `0xFFFFFFFF`）
2. `iord` 在 GPCCS 里出现 51 次，说明是轮询等待而非配置读取
3. 没有出现「按 SM 索引循环」的模式（此前已证否 14 次循环）
4. `0x20000` 段在 BAR0 中不存在（五种假设已排除），说明它是 GR 内部总线地址

**结论：TC 的配置不在 FECS/GPCCS 微码里，而是由硬件（熔丝 + SM 内部逻辑）决定。**

**微码能做的是「调度」和「开关」，不是「配置算力」。**

这与之前的判断一致：
- GSP 固件管全局，不管 SM 内部
- FECS/GPCCS 管调度与同步，不管 SM 内部单元配置
- SM 无微码（纯硬件）
- TC 的可用性由熔丝/布线决定
