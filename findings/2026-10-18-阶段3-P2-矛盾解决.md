# P2 第四阶段：NV_MEMORY 枚举确认，cache_type 矛盾解决

## 一、矛盾回顾

反汇编显示 `os_map_kernel_space` 中 `cache_type == 0` 分支尾调用 `ioremap_cache`，
但我此前按记忆认为 `NV_MEMORY_UNCACHED = 0`，二者不符，故暂停调用。

## 二、源码实证

`gh search code "NV_MEMORY_UNCACHED" --repo NVIDIA/open-gpu-kernel-modules` 定位到：

```
src/nvidia/inc/kernel/os/nv_memory_type.h
kernel-open/common/inc/os/nv_memory_type.h
```

完整枚举（41 行文件，原样引用）：

```c
#define NV_MEMORY_NONCONTIGUOUS      0
#define NV_MEMORY_CONTIGUOUS         1
#define NV_MEMORY_CACHED             0
#define NV_MEMORY_UNCACHED           1
#define NV_MEMORY_WRITECOMBINED      2
#define NV_MEMORY_WRITEBACK          5
#define NV_MEMORY_DEFAULT            6
#define NV_MEMORY_UNCACHED_WEAK      7
```

**关键：`NV_MEMORY_CACHED = 0`，`NV_MEMORY_UNCACHED = 1`。**

## 三、三方交叉验证

| edx 值 | 枚举常量 | 反汇编分支行为 | 一致性 |
|---|---|---|---|
| **0** | `NV_MEMORY_CACHED` | 尾调用 `ioremap_cache` | ✅ 完全吻合 |
| **2** | `NV_MEMORY_WRITECOMBINED` | `je 0xffffffffc2c13c33` | ✅ |
| **6** | `NV_MEMORY_DEFAULT` | `je 0xffffffffc2c13c4e` | ✅ |
| 其他 | — | 记录日志、返回 NULL | ✅ 与源码 default 分支一致 |

**结论：反汇编分析准确无误；此前的错误在于把 0 记成了 UNCACHED。**

## 四、函数入口偏移确认

```
ffffffffc2c13bb0  t __pfx_os_map_kernel_space   ← 16 字节 CET 前缀
ffffffffc2c13bc0  t os_map_kernel_space         ← 真入口（+0x10）
```

dump 起始字节为 `0f 1f 40 d6`（多字节 NOP，GCC 对齐用），而非 `endbr64`
（`f3 0f 1e fa`）——说明 endbr64 位于 `__pfx_` 区域内，真函数体从 NOP 对齐开始。

**`0xffffffffc2c13bc0` 确认为函数本体，不是 thunk。**

## 五、最终确认的函数原型

```c
void *os_map_kernel_space(void *phys_addr,   /* rdi */
                          NvU64 size,        /* rsi */
                          NvU32 cache_type); /* edx: 0=CACHED 1=UNCACHED 2=WC 6=DEFAULT */
```

行为：
1. `phys_addr == NULL && cache_type == 0` → 返回某全局对象（`mov -0x11191531(%rip),%rax`）
2. `phys_addr != NULL`：
   - 检查 IF 标志与 `preempt_count()`（**不允许在中断/原子上下文调用**）
   - 按 `cache_type` 分派：0 → `ioremap_cache`；2 → WC 路径；6 → DEFAULT 路径
   - 默认：`log(4, ...)` 并返回 NULL

**注**：4 参数版本 `osMapKernelSpace(addr, size, cache_type, protect)` 是其上层封装，
`protect` 在更上层处理，不进入该函数。

## 七、当前可否调用

**技术上已具备调用条件**（地址、签名、枚举、行为全部确认）。但：

| 风险项 | 说明 |
|---|---|
| 真实操作 GPU 地址空间 | 不是只读，会在 ioremap 层建立映射 |
| 参数语义仍有残余不确定 | `size` 的对齐要求、`phys_addr` 是否必须页对齐未验证 |
| 无法在 QEMU 预演 | 虚拟机无 NVIDIA 模块 |
| 失败后果 | 可能返回 NULL（无害），也可能建立错误映射导致后续访问异常 |

**建议**：首次调用选择最保守的参数——`cache_type = NV_MEMORY_UNCACHED (1)`
（寄存器访问的标准选择）、页对齐地址、`size = PAGE_SIZE`，并立即 `os_unmap_kernel_space` 释放。
