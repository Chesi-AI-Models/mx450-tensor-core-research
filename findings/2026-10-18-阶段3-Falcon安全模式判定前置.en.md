# Stage 3 · Prerequisites for determining the Falcon security mode

## 1. Exact information obtained

### Generic Falcon registers (`dev_falcon_v4.h`)

```
NV_PFALCON_FALCON_HWCFG     0x00000108   /* R--4R */
NV_PFALCON_FALCON_HWCFG2    0x000000f4   /* R--4R */
  HWCFG2.RISCV              bits 10:10
```

### SECURITY_MODEL field (`dev_falcon_v4.h`)

```
NV_PFALCON_FALCON_HWCFG1_SECURITY_MODEL   bits 5:4
  _NONE   = 0x0   (NS, non-secure)
  _LIGHT  = 0x2   (LS, light secure)
  _HEAVY  = 0x3   (HS, heavy secure)
  _INIT   = 0x3   (initial value)
```

**Reading bits 5:4 of HWCFG1 immediately settles which security mode FECS/GPCCS is in.**

### FECS control register region (nouveau `macros.fuc`)

```
NV_PGRAPH_FECS_INTR_ACK   0x409004
NV_PGRAPH_FECS_INTR       0x409008
NV_PGRAPH_FECS_ACCESS     0x409048
NV_PGRAPH_FECS_FIFO_DATA  0x409064
NV_PGRAPH_FECS_FIFO_CMD   0x409068
NV_PGRAPH_FECS_CAPS       0x409108
NV_PGRAPH_FECS_SIGNAL     0x409400
NV_PGRAPH_FECS_RED_SWITCH 0x409614
```

## 2. Where this got stuck

**The Falcon instance base address is undetermined.**

The contradiction:
- If FECS's Falcon base were `0x409000`, then `HWCFG` should be at `0x409000 + 0x108 = 0x409108`
- But `0x409108` is already defined as `NV_PGRAPH_FECS_CAPS`
- **The two conflict → `0x409000` is not the Falcon base**

This means `0x409xxx` is **the FECS control façade as seen from the GR engine**, while the Falcon core registers
inside FECS (HWCFG / CPUCTL / IMEMC etc.) live at a different base.

## 3. Candidate bases (pending measurement)

In envytools' GR documentation, Falcon often sits in its own `0x…` segment. Possible candidates:

| Candidate | Basis | How to verify |
|---|---|---|
| a GR falcon segment other than `0x409000` | nouveau does not state it directly | scan BAR0 for the HWCFG signature value |
| `0x800000`+ segment | not public for Turing | same as above |
| recover the FECS base constant from the driver via `/proc/kallsyms` | driver source has macros like `NV_PFALCON_FECS` | grep the driver binary/source |

**Most effective route**: `gh search code "FALCON_BASE" --repo NVIDIA/open-gpu-kernel-modules`,
or read `src/common/inc/swref/published/turing/tu102/dev_gr.h` directly
to see TU102's GR submodule base table.

## 4. Why this step is worth doing

**SECURITY_MODEL decides everything downstream:**

| Value read | Meaning | What follows |
|---|---|---|
| 0x0 (NS) | non-secure | **IMEM reads may work**; microcode could be obtained |
| 0x2 (LS) | light secure | partial state visible; still hopeful |
| 0x3 (HS) | heavy secure | **completely invisible to the host; this path ends** |

**One register read decides whether the whole route still has meaning. Minimal cost, maximal information.**
