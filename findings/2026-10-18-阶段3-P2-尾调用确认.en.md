### Check 2 · **the earlier parameter-count inference was wrong: it is actually 4 parameters**

The real call in `src/nvidia/arch/nvalloc/unix/src/osapi.c`:

```c
reg_mapping = osMapKernelSpace(nv->regs->cpu_address,   /* physical address */
                               os_page_size,             /* size */
                               NV_MEMORY_UNCACHED,       /* cache_type */
                               NV_PROTECT_READABLE);     /* protect */
```

**Four parameters.** Yet in my disassembly of `os_map_kernel_space` I only saw `rdi`/`rsi`/`edx`
(no use of `ecx`), which means:

- `osMapKernelSpace` (4 parameters) is the public API layer
- `os_map_kernel_space` (3 parameters) is the underlying kernel implementation
- I was reading the latter, so **the signature must be read as 3 parameters; `protect` is handled one layer up**

## 2. Tail-call target confirmed

In `os_map_kernel_space`, the `cache_type == 0` branch tail-calls `0xffffffffb04a4730`:

```
$ grep -E "^ffffffffb04a47" /proc/kallsyms
ffffffffb04a4700 T ioremap_encrypted
ffffffffb04a4720 T __pfx_ioremap_cache
ffffffffb04a4730 T ioremap_cache          ← the target
ffffffffb04a4750 T __pfx_ioremap_prot
ffffffffb04a4760 T ioremap_prot
```

**Conclusion: `os_map_kernel_space` is a thin wrapper over the kernel's `ioremap` family.**
This matches NVIDIA's open-source code structure exactly.

## 3. ⚠ Unresolved contradiction (must be clarified before calling)

The disassembly shows **`cache_type == 0` → `ioremap_cache`**.

But the NVIDIA convention is `NV_MEMORY_UNCACHED = 0`, in which case it should call `ioremap_uc` / `ioremap_nocache`.

**One of the two must be wrong.** Possible causes:

| Hypothesis | Explanation | How to verify |
|---|---|---|
| A. the enum value is not UNCACHED=0 | in this version `NV_MEMORY_*` differs from what I recall | read the real enum from 580.142's `nvtypes.h` |
| B. the read start offset is off | 0x...bc0 may be a thunk rather than the real entry | compare `__pfx_` (+0x10) against the body |
| C. `ioremap_cache` semantics differ | the function's behaviour changed in 6.x kernels | check kernel source `arch/x86/mm/ioremap.c` |
| D. this branch is not a cache_type dispatch | I misread what edx is for | verify instruction semantics one by one |

**Do not call this function until clarified** — mapping GPU memory with the wrong cache attribute can cause
coherency errors, data corruption, or even a GPU hang.

## 5. The `nv_al_*` family does not exist

`grep -oE "nv_al_[a-z_]+" /proc/kallsyms` → **zero results**.

This means names like `nv_al_add_mapping` are incorrect, or have been inlined/renamed.
Address-space management goes through the `os_*` abstraction layer, not `nv_al_*`.
