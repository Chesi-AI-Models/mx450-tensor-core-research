# 2026-10-18 · 阶段 1 补记 4：系统 BIOS dump 与 vBIOS 定位（C 路线，判定不可行）

## 动作

1. 检查 ACPI 表：无 `VFCT`（笔记本 GPU vBIOS 常见的 ACPI 载体）
2. 安装 `flashrom` + `acpica-tools`
3. 探测 SPI Flash 控制器
4. 只读导出 BIOS 区域
5. 在 dump 中定位 NVIDIA vBIOS

## 1. ACPI 表检查

可用表：`APIC BGRT DBG2 DBGP DMAR DSDT FACP FACS FPDT HPET LPIT MCFG MSDM NHLT PTDT
SSDT1-20 TPM2 UEFI WSMT`

**没有 `VFCT`**（Virtual Function Control Table）。该类表通常用于向系统提供
独立显卡的 vBIOS 副本；缺失意味着这条路不存在。

## 2. SPI Flash 探测

```
Found chipset "Intel Tiger Lake U Premium".
FREG0: Flash Descriptor region (0x00000000-0x00000fff) is read-only.
FREG1: BIOS region (0x00800000-0x017fffff) is read-write.
FREG2: Management Engine region (0x00001000-0x007fffff) is read-only.
SPI Configuration is locked down.
Enabling hardware sequencing due to multiple flash chips detected.
```

- 整片 Flash 24576 KB（24 MB）
- BIOS 区域：`0x00800000 – 0x017FFFFF`（16 MB）
- ME 区域只读，BIOS 区域标称可写但受 PR0–PR3 保护

## 3. 只读导出

```bash
flashrom -p internal:laptop=force_I_want_a_brick --ifd -i bios \
         -r /vol1/ganlin/bios/bios_readonly.bin
```

结果：`25165824` 字节（24 MB），MD5 `4d2c99e85e761e0a3b1b8dcada4cc950`
（`--ifd -i bios` 未生效，实际读出整片 Flash，含 Descriptor + ME + BIOS）

> 注：全程仅使用 `-r` 只读参数，未执行任何擦除/写入。

## 4. vBIOS 定位结果

| 检测项 | 结果 |
|---|---|
| 标准 PCI Option ROM（55AA + PCIR，VID=0x10DE） | **0 个** |
| 字符串 `NVIDIA` | **0 处** |
| 字符串 `90.17.64`（nvidia-smi 报告的 VBIOS 版本） | **0 处** |
| 字符串 `TU117` | **0 处** |
| `_FVH`（UEFI 固件卷签名） | 仅 `0x01400000` 一处 512 KB |
| `LZMA` / `Tiano` / `EFI_COMPRESS` | 全为 0 |

`0x00800000` 起始内容为：

```
02 0F 3E 90 10 2D E0 44 90 EE E7 EF F0 A3 ED F0
```

**非 `_FVH`、无可识别压缩头 —— 是密文。**

## 5. 判定

**BIOS 主体受 Intel Boot Guard 保护并加密，静态 dump 无法提取 vBIOS。**

Boot Guard 的信任链起点在 CPU 熔丝内的公钥，BIOS 关键区域（IBB）以签名+加密方式存储，
只有经过 ROM 阶段验证后才在运行时解密到内存。**没有厂商私钥，静态解析不可能。**

同时印证了另一件事：驱动卸载后 PCI ROM BAR 返回 `EIO`（零字节），
说明 GPU 自身没有 ROM，BIOS 也没有通过 PCI 机制提供明文 Option ROM ——
`nvidia-smi` 报告的 `VBIOS Version: 90.17.64.00.14` 很可能是驱动从 GPU 内部
某个信息结构读取的版本号，而非完整 vBIOS 镜像。

## 结论

**C 路线不可行。** 三条高层路径至此全部探底：

| 路线 | 手段 | 结果 |
|---|---|---|
| A | CUPTI metric 枚举 | `rc=38`，零 metric；开权限后不变 |
| B | `NV2080_CTRL` ioctl | 通道打通（ROOT_CLIENT 成功），`GR_GET_INFO` status=31 |
| C | 系统 BIOS / vBIOS 静态分析 | Boot Guard 加密，无法提取 |

## 这三条路共同说明什么

这台机器的固件与驱动栈在**三个层次上同时设防**：

1. **硬件层**：GPU 无独立 SPI Flash，vBIOS 不由自身提供
2. **固件层**：系统 BIOS 受 Intel Boot Guard 签名加密，无法静态解析
3. **驱动层**：用户态 API（NVML / CUPTI / 私有 ioctl）对关键能力做了裁剪或对象级隔离

**这不是「技术难度高」，是「设计上逐层封死」。**

## 还没被排除的路径（供后续参考）

| 路径 | 前提 | 可行性 |
|---|---|---|
| 运行时拦截 GSP 加载 | 编译 `nvidia-open` 内核模块 + 找 Turing 的 Falcon 加载点 | 技术可行，但**目标寄存器地址未知**（开源头文件中无 PLM/CFG1 定义） |
| 从内存中抓取已解密的 vBIOS | 在 BIOS POST 后、驱动加载前 dump 物理内存 | 需要自定义内核模块或 kdump，且 Boot Guard 会清理 |
| 硬件层测量 | 逻辑分析仪/示波器观察 TC 时钟域 | 需要拆机与专业设备 |
