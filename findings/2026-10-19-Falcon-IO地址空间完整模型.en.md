# 🔴🔴🔴 2026-10-19 · Complete model of the Falcon IO address space (architecture-level discovery)

## 1. The core document (envytools `docs/hw/falcon/io.rst`, lines 24–40, quoted verbatim)

```
The addresses are different between falcon and host. From falcon POV, the IO space
is word-addressable 0x40000-byte space. However, most registers are duplicated
64 times: bits 2-7 of the address are ignored. The few registers that don't
ignore these bits are called "indexed" registers. From host POV, the falcon IO
space is a 0x1000-byte window in BAR0. Its base address is engine-dependent.
First 0xf00 bytes of this window are tied to the falcon IO space, while last 0x100
bytes contain several host-only registers. On G98:GF119, host mmio address
falcon_base + X is directed to falcon IO space address X << 6 | HOST_IO_INDEX << 2.
On GF119+, some engines stopped using the indexed accesses. On those, host mmio
address falcon_base + X is directed to falcon IO space address X.

HOST_IO_INDEX is specified in the host-only MMIO register falcon_base + 0xffc:

MMIO 0xffc: HOST_IO_INDEX
  bits 0-5: selects bits 2-7 of the falcon IO space when accessed from host.

Unaligned accesses to the IO space are unsupported, both from host and falcon.
Low 2 bits of addresses should be 0 at all times.
```

## 2. The complete model built from it

### Falcon side

| Item | Value |
|---|---|
| total IO space size | **0x40000 bytes (256 KB)** |
| address range | `0x00000 - 0x3FFFF` |
| alignment requirement | low 2 bits must be 0 (4-byte aligned) |
| register duplication | most registers are duplicated 64 times; `bits 2-7` are ignored |
| exception | "indexed" registers do not ignore `bits 2-7`; they use them as an index |

### Host side

| Item | Value |
|---|---|
| visible window | **0x1000 bytes (4 KB)**, at `falcon_base + 0x000` |
| window layout | `0x000-0xEFF` → Falcon IO space; `0xF00-0xFFF` → host-only registers |
| `HOST_IO_INDEX` | `falcon_base + 0xFFC`; `bits 0-5` select Falcon IO `bits 2-7` |
| old mapping (G98:GF119) | `falcon_addr = (host_offset << 6) \| (HOST_IO_INDEX << 2)` |
| new mapping (GF119+ some engines) | `falcon_addr = host_offset` |

### Key conclusion

**The 6 bits of `HOST_IO_INDEX` can only select `bits 2-7`, i.e. "which copy".**

**They cannot select `bits 8+` — and `bits 8+` is what says "which register".**

**Therefore the host can access at most the lowest 4 KB of the Falcon IO space (`0x0000-0x0FFF`).**

**The `0x20000` segment (where `bits 17:8` are non-zero) is permanently invisible to the host.**

## 3. This explains every earlier contradiction

| Observation | Explanation |
|---|---|
| microcode does `iowr` to the `0x20000` segment 376 times (85%) | a legal Falcon IO address, inside the 256 KB space |
| BAR0 `0x020000` reads back `0xBADF5040` | the host window is only 4 KB; `0x20000` is far beyond it |
| `HOST_IO_INDEX` cannot help | it can only select `bits 2-7`, never `bits 17:8` |
| `0x409818` is valid in BAR0 | **not** a Falcon IO address but an external BAR0 address (see next section) |
| all five hypotheses failed | because the premise was wrong — it is neither a BAR0 address nor UAS/XFER/DMEM |

## 4. The two address mechanisms revealed by GPCCS microcode

### Mechanism A · direct iowr (Falcon IO space)

```asm
00002f28: mov $r9 0x23200
00002f2c: iowr I[$r9] $r15        ; bit31=0 → Falcon IO space
```

**Addresses `0x00000-0x3FFFF`, accessing engine-internal registers controlled by the Falcon.**

### Mechanism B · external access with bit31 set (BAR0)

```asm
; subroutine 0x201: build a flag-tagged address
00000201: mov $r9 0x3fffffc       ; 26-bit address mask
00000209: and $r10 $r9            ; keep only the low 26 bits of the address
0000020f: mov $r9 0x80000000      ; bit 31
00000214: shl b32 $r12 0x1a       ; bit26 = read/write direction
00000217: or  $r10 $r9            ; set bit31
0000021a: or  $r10 $r11           ; merge parameters
0000021d: or  $r11 $r10 $r12      ; merge the direction bit
00000220: mov $r10 0x1ca00        ; command queue address
00000224: lcall 0x1d8             ; submit the command
```

**`iowr I[0x80000000 | (addr & 0x3FFFFFC)]` → accesses the BAR0 absolute address `addr`.**

**GPCCS uses it to reach FECS's registers:**

```asm
00000276: mov $r10 0x409818       ; a BAR0 address inside the FECS segment
0000027c: lcall 0x337             ; → 0x2a1 → 0x201 → pack bit31
00000282: mov $r10 0x409c1c
0000028a: lcall 0x337
0000028e: mov $r10 0x409c18
00000294: lcall 0x26a             ; read
0000029b: bra b32 $r10 0x1 e 0x28e ; poll in a loop!
```

**This is the handshake loop where GPCCS waits for FECS.**

### Verifying mechanism B

**BAR0 measurement (GPU at full load):**

```
0x409800 = 0x00000004
0x409808 = 0x00000001
0x409810 = 0x00042790   ← non-zero
0x409818 = 0x00000000
0x409830 = 0x03030000   ← non-zero
0x409838 = 0x00001F97   ← non-zero
0x409C00 = 0x00000002
```

**These are real registers (not BAD), proving that mechanism B really does access the BAR0 address space.**

**And the values GPCCS polls — `0x409818` / `0x409C18` / `0x409C1C` — are currently all 0,
showing the handshake is in an "idle/completed" state (the GPU is running GEMM but needs no context switch).**

## 6. What this ultimately means for "Tensor Core throttling"

### What is settled

1. **TC hardware is present** (SASS can compile and execute HMMA; measured 0.60 TFLOPS)
2. **TCs are throttled to 5% of theoretical** (theoretical 6–12 TFLOPS)
3. **the control point is not in any host-readable/writable layer**:
   - GSP firmware: fully disassembled, contains no TC logic
   - vBIOS: protected by the FWSEC certificate chain
   - system BIOS: Boot Guard encrypted
   - **FECS/GPCCS microcode: fully disassembled — it only handles scheduling and synchronisation**
   - **Falcon IO space `0x20000` segment: permanently invisible to the host**
   - SM microcode: does not exist (pure hardware)
   - hardware fuses: physically irreversible

### One newly established hard boundary

**Even knowing that the `0x20000` segment is a GR-internal register block, the host can never read it —
this is a hardware design decision forced by `HOST_IO_INDEX` being only 6 bits wide (able to select only `bits 2-7`).**

**To read it there are only two routes:**
1. **modify the microcode** so it copies the `0x20000` segment somewhere host-visible
   → but the microcode is **FWSEC-signature verified**; a single changed byte blocks loading
2. **physical-layer probing** (logic analyser on the Falcon IO bus)
   → outside the scope of software research

**The first route is blocked by the signature, the second requires disassembly.**
