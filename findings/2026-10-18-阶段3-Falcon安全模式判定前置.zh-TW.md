# 階段 3 · Falcon 安全模式判定的前置條件

## 一、已獲得的確切資訊

### Falcon 通用暫存器（`dev_falcon_v4.h`）

```
NV_PFALCON_FALCON_HWCFG     0x00000108   /* R--4R */
NV_PFALCON_FALCON_HWCFG2    0x000000f4   /* R--4R */
  HWCFG2.RISCV              bits 10:10
```

### SECURITY_MODEL 欄位（`dev_falcon_v4.h`）

```
NV_PFALCON_FALCON_HWCFG1_SECURITY_MODEL   bits 5:4
  _NONE   = 0x0   (NS, 非安全)
  _LIGHT  = 0x2   (LS, 輕安全)
  _HEAVY  = 0x3   (HS, 重安全)
  _INIT   = 0x3   (初始值)
```

**只要讀到 HWCFG1 的 bits 5:4，就能立刻判定 FECS/GPCCS 處於哪個安全模式。**

### FECS 控制暫存器區（nouveau `macros.fuc`）

```
NV_PGRAPH_FECS_INTR_ACK   0x409004
NV_PGRAPH_FECS_INTR       0x409008
NV_PGRAPH_FECS_ACCESS     0x409048
NV_PGRAPH_FECS_FIFO_DATA  0x409064
NV_PGRAPH_FECS_FIFO_CMD   0x409068
NV_PGRAPH_FECS_CAPS       0x409108
NV_PGRAPH_FECS_SIGNAL     0x409400
NV_PGRAPH_FECS_RED_SWITCH 0x409614
```

## 二、卡住的地方

**Falcon 實例基底未確定。**

矛盾點：
- 若 FECS 的 Falcon 基底 = `0x409000`，則 `HWCFG` 應在 `0x409000 + 0x108 = 0x409108`
- 但 `0x409108` 已被定義為 `NV_PGRAPH_FECS_CAPS`
- **兩者衝突 → `0x409000` 不是 Falcon 基底**

說明 `0x409xxx` 是 **GR 引擎視角的 FECS 控制門面**，而 FECS 內部的 Falcon 核心暫存器
（HWCFG / CPUCTL / IMEMC 等）位於另一段基底。

## 三、候選基底（待實測驗證）

envytools 的 GR 相關文件中，Falcon 常位於獨立的 `0x…` 段。可能候選：

| 候選 | 依據 | 驗證方法 |
|---|---|---|
| `0x409000` 之外的 GR falcon 段 | nouveau 未直接給出 | 掃描 BAR0 找 HWCFG 特徵值 |
| `0x800000`+ 段 | Turing 未公開 | 同上 |
| 從 `/proc/kallsyms` 找驅動裡的 FECS base 常數 | 驅動原始碼裡有 `NV_PFALCON_FECS` 之類 macro | grep 驅動二進位／原始碼 |

**最有效方式**：用 `gh search code "FALCON_BASE" --repo NVIDIA/open-gpu-kernel-modules`
或直接讀 `src/common/inc/swref/published/turing/tu102/` 下的 `dev_gr.h`，
看 TU102 的 GR 子模組基底表。

## 四、為什麼這一步值得做

**SECURITY_MODEL 決定後續所有可能性**：

| 讀到的值 | 含義 | 後續 |
|---|---|---|
| 0x0 (NS) | 非安全模式 | **可以嘗試讀 IMEM**，可能拿到微碼 |
| 0x2 (LS) | 輕安全模式 | 部分狀態可見，仍有希望 |
| 0x3 (HS) | 重安全模式 | **host 完全不可見，此路終結** |

**一次暫存器讀取，就能決定整條路是否還有意義。成本極低，資訊量極大。**
