# Stage 3 · PRAMIN channel opened, but VRAM contents unreadable

## 1. Completed: the module successfully operates PRAMIN while the driver runs

`kernel/mx450_p3.c` implementation (strictly following nova-core's three rules):

1. the window must be 64 KB aligned (`BASE_ADDR` stores VRAM address bits[39:16])
2. **read back and verify** after every window change
3. restore the original window value when done

**This rules out the "VRAM is powered down" hypothesis** — 40 MiB of live data exists, yet it is still unreadable.

## 3. Possible causes (ranked by likelihood)

### Hypothesis 1 · PRAMIN needs PFB-side enablement (most likely)

PRAMIN is implemented by **PBUS**, but accessing VRAM requires **PFB (Framebuffer)** to be in an accessible state.
The driver may have set certain PFB control bits during init, while our window only moved the PBUS-side address.

**Verification direction**: check `dev_fb.h` / `dev_bus.h` for an aperture enable bit.

### Hypothesis 2 · a delay or extra trigger is needed after setting the window

nova-core's code does `read` immediately after `write` to verify — we did that, and verification passed.
But the hardware may still need several cycles before the window contents actually switch.

**Verification direction**: add `mdelay(1)` after setting the window, then read.

### Hypothesis 3 · ioremap attribute issue

BAR0 is mapped with `ioremap()` (UC-minus). The PRAMIN region may need a different attribute
(e.g. `ioremap_wc`), otherwise reads get optimized by the CPU or return bogus values.

**Verification direction**: compare against `ioremap_wc` or `ioremap_nocache`.

### Hypothesis 4 · on Turing, PRAMIN requires GSP authorization

Since Turing, the GSP has taken over a great deal of initialization. If the GSP placed PRAMIN inside some protected
domain, direct host-side access would be denied (returning 0 rather than an error).

**Verification direction**: hard; requires GSP-side information.

### Hypothesis 5 · the window value does not mean what we think

The original window `0x00007FF0` has BASE_ADDR = 0x7FF0 → VRAM 0x7FF00000.
If VRAM is exactly 2 GB, that points at the final 1 MB. **But why does the driver park it there?**
Perhaps this register's semantics changed on Turing.

## 4. Current state and next steps

**Proven**:
- ✅ the PRAMIN register set exists (0x1700 + 0x700000)
- ✅ ioremap and window-register read/write are possible while the driver runs
- ✅ window movement, readback verification, and restore all work
- ❌ but VRAM contents cannot be read through the window

**Next steps (ordered by cost)**:

1. **add a delay and retry**: `mdelay(1)` after `set_window`, to rule out timing (10 minutes)
2. **change the ioremap attribute**: compare `ioremap_wc` / `ioremap_nocache` (10 minutes)
3. **look for the PFB enable bit**: find the aperture control register in `dev_fb.h` (1–2 hours)
4. **read PMC_BOOT_42 etc. to confirm chip state**: verify the GPU is in a normal working state
