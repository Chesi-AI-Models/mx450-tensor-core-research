# 2026-10-18 · 階段 1 首輪：Turing 暫存器調查

> 環境：LYLNAS / fnOS (Debian 12) / kernel 6.18.18 / 驅動 580.142 / MX450 `10de:1f97`

## 一、本輪動作

1. `gh` 檢索 `NVIDIA/open-gpu-kernel-modules`（Turing+ 開源核心模組）
2. 拉取 `src/common/inc/swref/published/turing/tu102/` 下的暫存器標頭檔
3. 逐個檢索 fuse / FBPA / GSP / PLM / TENSOR 相關定義

## 二、拉取的檔案

| 檔案 | 行數 | 內容 |
|---|---|---|
| `dev_fuse.h` | 35 | 熔絲暫存器（僅 2 個） |
| `dev_fbpa.h` | 29 | FBPA（僅 ECC 計數） |
| `dev_gsp.h` | 68 | GSP Falcon mailbox / queue / EMEM |

留檔於 `refs/nvidia-swref/`。

## 三、關鍵發現

### 發現 1 · `dev_fuse.h` 裡沒有任何 Tensor Core 相關熔絲

全文只有兩條：

```c
#define NV_FUSE_OPT_SECURE_GSP_DEBUG_DIS   0x0002174C  /* RW-4R */
#define NV_FUSE_OPT_NVDEC_DISABLE          0x00021378  /* RW-4R */
```

- 權限標記 `RW-4R` = 讀/寫、32 位 —— **熔絲暫存器在驅動層是可存取的**，不是完全黑箱
- **但沒有 TC 能力位**。如果 TC 是被 OTP 熔斷，理論上應有一條類似 `NV_FUSE_OPT_TENSOR_DISABLE` 的定義

**推論**：TU117 的 TC 限速**很可能不透過 fuse 實作**。這削弱了「A 類（物理熔斷）」假設，
但同時也沒有給出「B 類（暫存器可改）」的位址。

### 發現 2 · Turing 的 FBPA 標頭檔裡沒有 CFG1

`cmpunlocker` 在 GA100 上改的是：

```
FBPA_CFG1 (0x009A0204) = 0x02779000   # 64GB HBM2e 幾何
```

而 `tu102/dev_fbpa.h` 全文只有：

```c
#define NV_PFB_FBPA_0_ECC_DED_COUNT(i)  (0x00900488+(i)*4)  /* RW-4A */
```

- 位址前綴 `0x00900xxx` 與 GA100 的 `0x009A0xxx` 不同段
- **沒有 CFG1 / PLM 定義**

**推論**：顯示記憶體幾何配置不在開源標頭檔的公開範圍內。對 MX450 而言這無關緊要
（顯示記憶體是物理焊死的 2GB），但它說明**「按 CMPUnlocker 的位址表直接照搬」在 Turing 上不成立**。

### 發現 3 · Turing 目錄下檢索不到 PLM

`gh search code "PLM" --repo NVIDIA/open-gpu-kernel-modules` 在 Turing 路徑下**零命中**。

CMPUnlocker 的核心是打開 4 個 PLM 暫存器（`FEAT_PLM` / `FBPA_PLM` / `WPR_PLM` / `WPR_CFG`），
而 Turing 的開源程式碼裡沒有這套東西。

**推論**：要嘛 Turing 用別的機制做權限隔離，要嘛這部分完全在閉源 GSP 微碼裡。兩種情況下，
**CMPUnlocker 的注入目標位址在 Turing 上都不可用**。

### 發現 4 · `dev_gsp.h` 暴露了 Falcon 通訊介面

```c
#define NV_PGSP                         0x113fff:0x110000
#define NV_PGSP_FALCON_MAILBOX0         0x110040   /* RW-4R */
#define NV_PGSP_FALCON_MAILBOX1         0x110044   /* RW-4R */
#define NV_PGSP_QUEUE_HEAD(i)           (0x110c00+(i)*8)
#define NV_PGSP_QUEUE_TAIL(i)           (0x110c04+(i)*8)
#define NV_PGSP_EMEMC(i)                (0x110ac0+(i)*8)
#define NV_PGSP_EMEMD(i)                (0x110ac4+(i)*8)
```

**這是本輪最有價值的收穫。** Turing 是 NVIDIA 第一個引入 GSP 的世代，
GSP 韌體透過這組 mailbox/queue 與 host 通訊，並且有直接存取 EMEM（外部記憶體）的通道。

`cmpunlocker` 的原理就是**在 GSP-RM 啟動之前**竄改其簽章段，從而劫持執行流。
MX450 上同樣存在 `PGSP` 這組介面 —— **注入入口在物理上是存在的**。

### 發現 5 · 驅動有查詢 TC 數量的控制命令（未使用）

```c
#define NV0080_CTRL_GR_INFO_INDEX_TENSOR_CORE_COUNT   (0x00000023)
// "This index is used to return the number of Tensor Cores"
```

說明 GR 引擎知道這塊晶片有多少 TC。若能把該值讀出來：

- 報 56（14 SM × 4）→ TC 被硬體承認，只是限速 → **B 類假設成立**
- 報 0 → TC 在驅動層就被判定為不可用 → **接近 A/D 類**

讀取需要走 `NV2080_CTRL` ioctl（NVML 私有介面），本輪未實作。
**這是下一輪優先級最高的動作** —— 它是判定鎖性質的直接證據。

## 四、本輪結論

| 假設 | 本輪證據 | 判斷 |
|---|---|---|
| A. OTP eFuse 熔斷 | fuse 標頭檔無 TC 位 | **減弱**（但可能未公開） |
| B. 暫存器級 throttle | 未找到 Turing 的 SS/PLM 定義 | **待驗證**（需 TC 計數） |
| C. devinit 表配置 | 需 dump 系統 BIOS | 未開始 |
| D. 硬體設計低速率 | NVIDIA 論壇稱「throttled throughput」 | **仍可能** |

**淨收穫**：確認 CMPUnlocker 的暫存器位址表**不能照搬**（Turing 命名空間不同），
但確認了 **GSP Falcon 注入通道存在**（`NV_PGSP`），這為後續提供了唯一可行的入口。

## 五、下一輪計畫

1. **讀取 TC 數量**（`NV2080_CTRL_GR_INFO_INDEX_TENSOR_CORE_COUNT`）
   → 直接判定 B 類是否成立
2. 若 B 成立：在 Turing 命名空間中定位 SM 級 throttle 暫存器
3. 若 B 不成立：轉向 dump 系統 BIOS，解析 devinit 表
4. 同時補：`dev_ltc.h`（L2）、`dev_sec_pri.h`（SEC2）的完整審查
