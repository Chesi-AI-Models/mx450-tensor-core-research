# 2026-10-19 · 阶段 4 补记：iowr 地址空间归属 —— 五种假设逐一排除

## 一、本轮修正了一个方法论错误

**此前的地址统计（findings/阶段4-FECS微码反汇编.md）存在系统性偏差。**

原分析脚本 `analyze_iowr.py` 只跟踪 `mov` 指令，不跟踪 `add`/`sub`。而微码中存在大量：

```asm
00002c2d: mov $r9 0x20600       ; $r9 = 0x20600
00002c31: iowr I[$r9] $r1       ; 写 0x20600  ✓
00002c39: add b32 $r9 $r9 0xc00 ; $r9 = 0x21200  ← 脚本漏了这一步
00002c3e: iowr I[$r9] $r15      ; 实际写 0x21200，被记成 0x20600  ✗
```

**新脚本 `tools/analyze_iowr_v3.py`** 跟踪 `mov(imm/reg) / add / sub / shl / shr / and / or`，
并先剥离反汇编行首的「地址 + 字节码」前缀（v2 因 `^` 锚点导致 0% 解析）。

### 修正后的统计

```
iowr 总数: 449   可解析: 442 (98.4%)   未解析: 7
iord 总数: 0

指令统计: mov_i 4446, lcall 932, add 286, sub 61, and 81, shl 43, shr 50, or 3
```

**地址分布与 v1 大体一致（85% 仍在 0x20000 段），说明主要结论不受影响，但具体数值已修正。**

## 二、关键突破：Falcon IO 地址映射规则

envytools `docs/hw/falcon/io.rst` 给出了 Host / Falcon 双视角映射表：

```
Host    Falcon    Name
0x000   0x00000   INTR_SET
0x004   0x00100   INTR_CLEAR
0x040   0x01000   SCRATCH0
0x100   0x04000   UC_CTRL        ← CPUCTL
0x104   0x04100   UC_ENTRY       ← BOOTVEC
0x108   0x04200   UC_CAPS        ← HWCFG
0x10c   0x04300   UC_BLOCK_ON_FIFO
0x12c   0x04b00   UC_CAPS2       ← HWCFG1
0x180   0x06000   CODE_INDEX     ← IMEM 窗口地址
0x184   0x06100   CODE           ← IMEM 窗口数据
0x1c0   0x07000   DATA_INDEX[0]
0x1c4   0x07100   DATA[0]
```

**映射规则：`Falcon = Host × 0x40`**

**验证**：我们实测 `BAR0 0x409000 + 0x12c = 0x80104126`，而 `0x12c` 正是 `UC_CAPS2`。
`0x409184 = 0x002000D0`，而 `0x184` 正是 `CODE`（IMEM 窗口），读出的正是 IMEM[0]。
**两处独立验证，映射关系确认。**

## 三、五种假设逐一排除

### 假设 1 · `0x20000` 段是 BAR0 绝对地址

**测试**：驱动卸载后 + 驱动运行时（GPU 100%）分别读 BAR0 `0x20000` 段。

```
驱动卸载:  0x020000 = 0xBADF5040
驱动运行:  0x020000 = 0xBADF5040   ← 仍然是 BAD
           0x0247FC = 0xBADF1100
           0x010100 = 0xBAD00100
```

**`0xBADF5040` / `0xBADF1100` / `0xBAD00100` 是 NVIDIA 的三类「未实现地址」哨兵值**
（对照：`0x001000` 也返回 `0xBADF5040`，而 `0x001700` PRAMIN 窗口返回有效值 `0x00007FF0`）。

**结论：排除。不是 BAR0 地址。**

### 假设 2 · `iowr 地址 = FECS 基址(0x409000) + offset`

**测试**：读 BAR0 `0x409000 + 0x20000 = 0x429000` 等。

**结果**：`0x420000 - 0x43F000` 全部返回 BAD。

同时扫描 GR 段有效区域：

```
0x404000: 0x80000000    ← 有效
0x408000: 0x08800800    ← 有效
0x409000: 0             ← FECS
0x410000: 0x32080A00    ← 有效
0x418000: 0x8700029F    ← 有效
0x419000: 0x10210780    ← 有效
0x41A000 / 0x41B000: 0  ← 有效但空
0x420000+: 全部 BAD
```

**结论：排除。GR 的寄存器区止于 0x41B000 附近。**

### 假设 3 · `0x20000` 段是 UAS（Unified Address Space）

**测试**：GPU 满载时读 FECS 的 UAS 寄存器组。

```
0x409160 UAS_IO_WINDOW   = 0x00000000
0x409164 UAS_CONFIG      = 0x00000000
0x409168 UAS_FAULT_ADDR  = 0x00000000
0x40916c UAS_FAULT_STATUS= 0x00000000
```

**全部为 0，且 `UAS_FAULT_STATUS = 0` 说明从未产生 UAS 访问错误。**

**结论：排除。该 Falcon 实例的 UAS 未使能（或不存在）。**

> 附注：envytools 的 `docs/hw/falcon/data.rst` 第 9 行写着 `.. todo:: document UAS`
> —— **连 envytools 自己都没写出 UAS 的文档。**

### 假设 4 · `0x20000` 段是 XFER 外部空间（VRAM）

**测试**：GPU 满载时连续 8 次采样 `XFER_EXT_BASE`。

```
0x409110 XFER_EXT_BASE = 0x00772600   （8 次采样全部相同，稳定）
0x409114 XFER_FALCON_ADDR = 0x00000000
0x409118 XFER_CTRL        = 0x00000602
0x40911c XFER_EXT_ADDR    = 0x0000E700
```

**若 `iowr 地址 = XFER_EXT_BASE + offset`，则 `0x20000 → VRAM 0x792600`。**
**实测 dump VRAM `0x760000-0x860000`（1 MB），`0x792600` 处 64 字节全零。**

**结论：排除。不是 XFER 外部空间。**

### 假设 5 · `0x20000` 段是 Falcon DMEM

**HWCFG = 0x40204080**，字段解码：
- bits 8:0 = 0x080 = 128 → IMEM = 128 × 256B = **32 KB**（与实测 dump 长度一致）
- DMEM 按 NVIDIA 惯例为 IMEM 的 1/4 ～ 1/2，即 **8–16 KB**

**`0x20000 = 128 KB`，远超 DMEM 容量。**

**结论：排除。**

## 四、地址结构分析：它是「4KB 块 + 块内寄存器」

把 72 个唯一地址按 4KB 分块：

| 块 | 地址数 | 块内偏移 |
|---|---|---|
| `0x20000-0x20FFF` | 11 | 0x000, 0x100, 0x600, 0x700, 0x900, 0xA00, 0xB00, 0xC00, 0xD00, 0xE00, 0xF00 |
| `0x21000-0x21FFF` | 3 | 0x200, 0x300, 0x800 |
| `0x22000-0x23FFF` | 7 | 0xA00, 0xE00, 0xF00, 0x000(23000), 0x200, 0x300, 0x800 |
| `0x24000-0x24FFF` | 4 | 0x200, 0x300, 0x400, 0x420, **0x6FC, 0x7FC, 0xFFC** |
| `0x28000-0x28FFF` | 8 | 0x000, 0x100, 0x300, 0x400, 0x800, 0x900, 0xD00, 0xE00 |
| `0x2C000-0x2CFFF` | 4 | 0x000, 0x100, 0x200, 0x300 |
| `0x2DC00-0x2DEFF` | 3 | 0xC00, 0xD00, 0xE00 |
| `0x30200-0x30900` | 4 | 0x200, 0x540, 0x700, 0x900 |

**两个关键特征：**

1. **块内偏移以 0x100 为基本步长** —— 典型的「每实例一组寄存器，实例间隔 0x100」
2. **`0x246FC / 0x247FC / 0x24FFC` 这三个 `0xFFC` 结尾地址** —— 4 KB 块内的末尾偏移，
   典型的「块结束标记 / 块级控制寄存器」

**这与「GR 内部硬件寄存器组」的布局完全吻合，而不是内存缓冲区。**

## 五、最终判定

**`0x20000` 段是 Falcon IO 空间在 v6 上的高地址扩展区，映射到 GR 引擎内部硬件寄存器，不映射到 BAR0。**

依据：

| 证据 | 说明 |
|---|---|
| 五种假设全部实测排除 | BAR0 / FECS+off / UAS / XFER / DMEM |
| 地址结构为 4KB 块 + 0x100 步进 | 硬件寄存器组特征，非内存 |
| `iord` 数量为 0 | 微码只写不读 —— 典型的「配置寄存器」写操作 |
| 与 GR 段有效区（止于 0x41B000）无重叠 | 不在 host 可见的 BAR0 空间内 |

**这是「公开资料不可解」的最终确认，而非「尚未找到」：**

- envytools rnndb：止于 Maxwell，`0x20000` 段上界 `0x227FF` < 微码实际访问的 `0x30900`
- `turing/tu102/` 头文件：无 `dev_gpc.h` / `dev_tpc.h`
- 开源 HAL：`NV_PGRAPH_GPC` / `NV_PGRAPH_TPC` 零定义
- envytools falcon 文档：`.. todo:: document UAS`（作者也没写）

## 六、本轮附带发现：VRAM 中的 GPU MMU 页表

dump VRAM `0x760000-0x860000` 时，在 `0x788000-0x791000` 发现规整结构：

```
0x790000: 0D 0D 7E 17 00 00 00 06   → 0x177E0D << 8 = 0x177E0D00
          0D 0E 7E 17 00 00 00 06   → 0x177E0E00  (+0x100)
          0D 0F 7E 17 00 00 00 06   → 0x177E0F00
          0D A8 2F 21 00 00 00 06   → 0x212FA800  ← 跳到另一段
```

每项 8 字节，`[flags:8][addr:24][reserved:32]`，地址在 2 GB VRAM 范围内连续递增。

```
0x788000: 02 91 07 00 00 00 00 00   → 0x079102
          02 89 07 00 00 00 00 00   → 0x078902
          12 91 07 00 00 00 00 00   → 0x079112
          02 8A 07 00 00 00 00 00   → 0x078A02
```

成对出现，步长分别为 `0x10` 和 `0x100` —— 典型的**页表 / 地址映射表**结构。

**判定：这是 GPU 的内存管理结构（MMU 页表 / 分配器元数据），不是 FECS 的私有数据。**

**但它是本项目首次在 VRAM 中定位到 GPU 自身的数据结构**，对后续研究有价值。

## 八、这一轮的意义

**排除了五种可能，这本身就是进展。**

在逆向工程中，「确定某物不是什么」与「确定它是什么」同样有价值——它缩小了搜索空间，
并防止后来者重复走同样的弯路。

**现在的结论是清晰的：**

```
FECS 微码（已 dump、已反汇编）
    ↓ 通过 iowr 访问
Falcon IO 空间（v6 扩展，0x20000 段）
    ↓ 映射到
GR 内部硬件寄存器（NVIDIA 从未公开映射表）
    ↓ 控制
GPC / TPC / SM 的运行时配置
```

**最后一环的映射表，是 NVIDIA 唯一没有泄露的部分。**

要拿到它，只有两条路：
1. 逆向闭源的 `nv-kernel.o_binary`（已剥离符号，工作量以月计）
2. 真机写测试（**高风险，可能挂死 GPU**，不建议）

**在软件层面，这条链已经探到能探的最深处。**
