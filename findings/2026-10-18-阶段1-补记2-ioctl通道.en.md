# 2026-10-18 · Stage 1 addendum 2: NV2080 ioctl channel opened (80%) and where it stopped

## Conclusion summary

**Progressed from "completely blocked" to "ioctl channel open, root client allocated successfully"**,
but `GR_GET_INFO` after `NV20_SUBDEVICE_0` returns `NV_STATUS 31`, so the TC count could not be obtained.

The tool is fully preserved in `tools/read_tc_count.c`, with every fixed pitfall annotated in comments, so whoever
continues can start from there.

## 1. Three real bugs fixed

### Bug 1 · the ioctl command number must not add NV_IOCTL_BASE

Initially, following the common pattern, `_IOWR('F', NV_IOCTL_BASE + NV_ESC_RM_ALLOC, ...)` was used,
i.e. `200 + 0x2B = 243`, which **always returned EINVAL**.

**The truth only surfaced by strace-ing a real `nvidia-smi` call**:

```
ioctl(9, _IOC(_IOC_READ|_IOC_WRITE, 0x46, 0x2b, 0x30), ...) = 0   ← RM_ALLOC, 48B
ioctl(9, _IOC(_IOC_READ|_IOC_WRITE, 0x46, 0x2a, 0x20), ...) = 0   ← RM_CONTROL, 32B
```

`0x46` = `'F'`, and `nr` is **`0x2b` itself** — no base added.
After switching to the raw `NV_ESC_RM_ALLOC` value, **ROOT_CLIENT was allocated immediately** (`hClient = 0xc1d00063`).

> Methodology note: **never guess private ioctl numbers — strace a working official tool, it is the fastest route.**

### Bug 2 · the width of `NV0080_ALLOC_PARAMETERS.flags`

In the hand-built struct `flags` was declared as `NvU64` (8 bytes), while the official definition is **`NvV32` (4 bytes)**:

```c
typedef struct NV0080_ALLOC_PARAMETERS {
    NvU32    deviceId;
    NvHandle hClientShare;
    NvHandle hTargetClient;
    NvHandle hTargetDevice;
    NvV32    flags;                                   /* ← 4 bytes, not 8 */
    NV_DECLARE_ALIGNED(NvU64 vaSpaceSize, 8);
    NV_DECLARE_ALIGNED(NvU64 vaStartInternal, 8);
    NV_DECLARE_ALIGNED(NvU64 vaLimitInternal, 8);
    NvV32    vaMode;
} NV0080_ALLOC_PARAMETERS;
```

The extra 4 bytes shift every following field. The total struct size happens to be 56 either way,
**so the `sizeof` check passes while the fields are read incorrectly** — the hardest class of bug to find.

### Bug 3 · the device node was never opened

`nvidia-smi` calls `open("/dev/nvidia0")` before RM_ALLOC.
After adding that step, DEVICE_0 / SUBDEVICE_0 no longer returned status=64 and instead returned handles.

## 2. Where it currently stops

```
[1] ROOT_CLIENT (0x41)   hClient    = 0xc1d00063
[2] DEVICE_0 (0x80)      hDevice    = 0xcaf00000
[3] SUBDEVICE_0 (0x2080) hSubdevice = 0xcaf00001
[4] GR_GET_INFO
    index=0x00 NUM_SMS              status=31
    index=0x23 TENSOR_CORE_COUNT    status=31
```

- the `0xc1d0xxxx` form is a valid client handle; the `0xcaf0xxxx` form **looks like a placeholder/invalid object
  returned by the driver**
- `NV_STATUS 31 (0x1F)` has no direct literal definition in `nvstatus.h` (that file generates the enum via macros)

**Judgement**: the device/subdevice object chain was never really established, so the control call is rejected.
The remaining work is to pin down the semantics of `0xcaf0xxxx` and the control permissions — that belongs to the
driver's internal object model.

## 3. Why it was converged here

| Factor | Note |
|---|---|
| diminishing returns | the TC count is only corroboration for "how the driver sees this silicon"; it does not change the measured 0.60 TFLOPS |
| cost | requires reversing the driver's object-handle encoding and control permission checks; probably several more debugging rounds |
| existing evidence is sufficient | HMMA instructions exist + execute without fault + throughput only 5–10% of theoretical + cuBLAS shows the same behaviour — four mutually supporting facts |
| the tool is archived | all three bug fixes are in the comments; anyone can continue from here |

**This is not a failure; it is walking the road to "only the last stretch remains" and marking the wayposts.**

## 4. Suggested path if continuing

1. **comparison method**: write a minimal program, strace yourself, and compare instruction-by-instruction against
   `nvidia-smi`'s ioctl sequence to find the missing prerequisite calls (strace shows `nvidia-smi` also calls
   three more ioctls `0xd2`, `0xd6`, `0xc8` before RM_ALLOC)
2. **a cheaper alternative**: link `libnvidia-ml.so` directly and use NVML's `nvmlDeviceGetFieldValues`
   to probe whether GR_INFO-class fields are readable
3. **change route entirely**: use CUPTI to collect tensor-pipeline activity counters and directly observe whether
   TCs are physically activated (more informative than the TC count, and independent of private ioctls)
