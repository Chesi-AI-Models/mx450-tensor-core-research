# 2026-10-19 · 0x20000 段歸屬：三條路線全部嘗試，判定為「公開資料不可解」

## 一、路線 2 失敗：不是 14 次迴圈

`0x21800` 在反組譯中出現 37 次，但分佈如下：

```
000000ad  mov $r9 0x21800     ← 函式 A
00000723  mov $r9 0x21800     ← 函式 B
000009e9  mov $r9 0x21800     ← 函式 C
00000b8b  mov $r9 0x21800     ← 函式 D
00000e76  mov $r9 0x21800     ← 函式 E
00000eed  mov $r9 0x21800
00000f0f  mov $r9 0x21800
00001ad7  mov $r9 0x21800
...
```

**分散在十餘個不同函式中，且 `mov $rX, 0xe`（14）在全文中零命中。**

**判定：`0x21800` 是多個函式共用的功能暫存器，不是「按 SM 數迴圈初始化」的計數器。**

## 二、路線 1 失敗：HAL 原始碼無定義

```
gh search code "NV_PGRAPH_GPC"  → 0 結果
gh search code "NV_PGRAPH_TPC"  → 0 結果
```

**NVIDIA 的 `open-gpu-kernel-modules`（Turing+ 全世代）中不存在 GPC/TPC 的暫存器巨集定義。**

說明：GPC/TPC/SM 級的暫存器初始化邏輯位於**閉源 HAL 二進位**（`nv-kernel.o_binary`）內，
不在 MIT/GPL 發布的開源部分。

## 三、路線 3 未驗證（需外部資料）

對照看雪 AD102 FECS 分析需翻閱原文，其結論（是否同樣存取 `0x2000x`）未在本次核查範圍內。

## 四、最終判定

**Turing 的 `0x20000` 段語意，在目前可獲得的公開資料範圍內無法確定。**

三重障礙：

| 障礙 | 狀態 |
|---|---|
| envytools rnndb | 覆蓋止於 Maxwell，且記錄的 0x20000 段上界（0x227FF）小於微碼實際存取範圍 |
| NVIDIA 開源標頭檔 | tu102 目錄無 `dev_gpc.h` / `dev_tpc.h` |
| NVIDIA 開源 HAL | `NV_PGRAPH_GPC` / `NV_PGRAPH_TPC` 零定義，關鍵邏輯在閉源 `.o_binary` |

**這不是「還沒找到」，是「這一層資訊 NVIDIA 沒有公開」。**

## 五、可以繼續的方向（都需要額外條件）

| 方向 | 需要什麼 | 可行性 |
|---|---|---|
| 反組譯閉源 HAL | `nv-kernel.o_binary` 逆向（IDA/Ghidra） | 可行但工作量大，且已剝離符號 |
| 在真機上做寫測試 | 逐個位址寫入並觀察 GPU 反應 | **高風險**，可能掛死 GPU |
| 等第三方公開 | AD102 逆向筆記的完整版 | 不受控 |

**注意**：第二項（寫測試）是唯一能在本機推進的，但違背了本專案「唯讀優先」的安全原則，
且 `0x20000` 段確認為 PTHERM/PFUSE/PUNITS 一部分的情況下，誤寫可能觸發溫度保護或熔絲邏輯。
