# 2026-10-18 · 階段 1 補記 2：NV2080 ioctl 通道打通（80%）與卡點

## 結論摘要

**從「完全不通」推進到「ioctl 通道打通、root client 分配成功」**，
但在 `NV20_SUBDEVICE_0` 之後的 `GR_GET_INFO` 處回傳 `NV_STATUS 31`，未能取得 TC 計數。

工具已完整保留在 `tools/read_tc_count.c`，註解標註了每一個已修復的坑，後人可從此處接續。

## 一、修復的三個真實 bug

### Bug 1 · ioctl 命令號不該加 NV_IOCTL_BASE

最初按常見寫法用 `_IOWR('F', NV_IOCTL_BASE + NV_ESC_RM_ALLOC, ...)`，
即 `200 + 0x2B = 243`，**始終回傳 EINVAL**。

**靠 strace 抓 `nvidia-smi` 的真實呼叫才發現真相**：

```
ioctl(9, _IOC(_IOC_READ|_IOC_WRITE, 0x46, 0x2b, 0x30), ...) = 0   ← RM_ALLOC, 48B
ioctl(9, _IOC(_IOC_READ|_IOC_WRITE, 0x46, 0x2a, 0x20), ...) = 0   ← RM_CONTROL, 32B
```

`0x46` = `'F'`，`nr` 就是 **`0x2b` 本身**，不疊加 base。
改用 `NV_ESC_RM_ALLOC` 原值後，**ROOT_CLIENT 立即分配成功**（`hClient = 0xc1d00063`）。

> 方法論記錄：**私有 ioctl 的編號不要靠猜，strace 一個能工作的官方工具最快。**

### Bug 2 · NV0080_ALLOC_PARAMETERS 的 flags 寬度

自建結構裡把 `flags` 宣告成 `NvU64`（8 位元組），官方定義是 **`NvV32`（4 位元組）**：

```c
typedef struct NV0080_ALLOC_PARAMETERS {
    NvU32    deviceId;
    NvHandle hClientShare;
    NvHandle hTargetClient;
    NvHandle hTargetDevice;
    NvV32    flags;                                   /* ← 4 位元組，不是 8 */
    NV_DECLARE_ALIGNED(NvU64 vaSpaceSize, 8);
    NV_DECLARE_ALIGNED(NvU64 vaStartInternal, 8);
    NV_DECLARE_ALIGNED(NvU64 vaLimitInternal, 8);
    NvV32    vaMode;
} NV0080_ALLOC_PARAMETERS;
```

多出的 4 位元組讓後面所有欄位整體錯位。結構總大小恰好都是 56，
**所以 sizeof 校驗能過，但欄位讀錯** —— 這是最難查的一類 bug。

### Bug 3 · 缺少開啟裝置節點

`nvidia-smi` 在 RM_ALLOC 前會先 `open("/dev/nvidia0")`。
補上該步驟後，DEVICE_0 / SUBDEVICE_0 不再報 status=64，而是回傳句柄。

## 二、目前卡點

```
[1] ROOT_CLIENT (0x41)   hClient    = 0xc1d00063
[2] DEVICE_0 (0x80)      hDevice    = 0xcaf00000
[3] SUBDEVICE_0 (0x2080) hSubdevice = 0xcaf00001
[4] GR_GET_INFO
    index=0x00 NUM_SMS              status=31
    index=0x23 TENSOR_CORE_COUNT    status=31
```

- `0xc1d0xxxx` 形態是有效 client handle；`0xcaf0xxxx` 形態**疑似驅動回傳的佔位／無效物件**
- `NV_STATUS 31 (0x1F)` 在 `nvstatus.h` 中無直接字面定義（該檔案用巨集生成列舉）

**判斷**：device/subdevice 的物件鏈沒有真正建立，因此 control 呼叫被拒。
剩餘工作是把 `0xcaf0xxxx` 的語意與 control 權限搞清楚，屬於驅動內部物件模型範疇。

## 三、為什麼在此收斂

| 因素 | 說明 |
|---|---|
| 邊際收益下降 | TC 計數只是「驅動怎麼看這塊矽晶片」的旁證，不改變 0.60 TFLOPS 的實測事實 |
| 成本 | 需要逆向驅動的物件句柄編碼與 control 權限校驗，估計還需數輪除錯 |
| 已有證據充分 | HMMA 指令存在 + 執行不報錯 + 吞吐僅為理論 5–10% + cuBLAS 同現象，四條互證 |
| 工具已留檔 | 三個 bug 的修法都寫進註解，任何人可從此處接續 |

**這不是失敗，是把路走到了「還差最後一段」並標好了路標。**

## 四、如果繼續，建議路徑

1. **對比法**：寫一個最小程式 strace 自己，與 `nvidia-smi` 的 ioctl 序列逐條比對，
   找出缺失的前置呼叫（strace 裡看到 `nvidia-smi` 在 RM_ALLOC 前還調了 `0xd2`、`0xd6`、`0xc8` 三個 ioctl）
2. **更省力的替代**：直接連結 `libnvidia-ml.so`，用 NVML 的 `nvmlDeviceGetFieldValues`
   試探是否可讀 GR_INFO 類欄位
3. **徹底換路**：用 CUPTI 擷取張量管線活躍計數器，直接觀察 TC 是否被物理活化
   （資訊量比 TC 計數更大，且不依賴私有 ioctl）
