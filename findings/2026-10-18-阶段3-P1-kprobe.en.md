# 2026-10-18 · Stage 3 · P1: kprobe bypass (partial success + approach corrected)

## Goal

Work around the fact that `kallsyms_lookup_name` has not been exported since Linux 5.7, and use it to look up
internal symbol addresses in NVIDIA's kernel module.

## Implementation

`kernel/mx450_p1.c`:

```c
struct kprobe kp = { .symbol_name = "kallsyms_lookup_name" };
register_kprobe(&kp);
kln_addr = (unsigned long)kp.addr;      /* obtain the real address */
unregister_kprobe(&kp);
kln = (kln_t)kln_addr;                  /* cast and call */
kln("os_map_kernel_space");              /* look up the target symbol */
```

## Result 1 · QEMU isolated environment: complete success

```
kernel: 6.18.18.c1126-trim
mx450_p1: kallsyms_lookup_name resolved @ 0xffffffffb37e9404
mx450_p1: os_map_kernel_space = (not present)
mx450_p1: nv_al_add_mapping   = (not present)
mx450_p1: probe complete
rc=0
```

- **The kprobe technique works on the fnOS 6.18 kernel**
- The `kallsyms_lookup_name` address was obtained successfully and could be called
- The nvidia symbols being "not present" is expected (the nvidia module is not loaded in the VM)

## Result 2 · Host machine: kernel oops

```
Segmentation fault (rc=139)
mx450_p1: kallsyms_lookup_name resolved @ 0xffffffffa65e9404
 mx450_p1_init+0x92/0xff0 [mx450_p1]
```

**The address was obtained, but calling `kallsyms_lookup_name` crashed (+0x92).**

### Difference analysis

| Environment | Symbol table size | Result |
|---|---|---|
| QEMU (no nvidia) | small | ✅ success |
| Host (with nvidia, 46,294 symbols) | large | ❌ oops |

**Likely cause**: while traversing a large symbol table, `kallsyms_lookup_name` may depend on
`kallsyms_lock` / RCU protection, making a direct call from module-init context unsafe; or the function's
internal implementation changed in 6.18.

### System state

- **Host did not reboot** (uptime 2 days 22 hours)
- `nvidia-smi` normal (MX450, 57 °C, 1395 MHz)
- `nvidia` / `nvidia_uvm` / `nvidia_drm` modules normal
- Leftover: `mx450_p1` and `mx450_probe` at 12 KB each, marked `in use`; both `rmmod` and `rmmod -f`
  failed — **only a reboot clears them**

## Key correction: `kallsyms_lookup_name` is not needed at all

While investigating it turned out that **`/proc/kallsyms` is fully readable by root** — the symbol addresses
were sitting right there.

```bash
# measured locally (no module required)
$ grep -E "os_map_kernel_space|nv_al_add_mapping" /proc/kallsyms
ffffffffc2c13bb0 t __pfx_os_map_kernel_space	[nvidia]
```

**So the correct approach is:**

1. Read `/proc/kallsyms` from user space to get the target symbol address
2. Pass the address in via a module parameter (`module_param`)
3. The module casts and calls that address directly — **never touching `kallsyms_lookup_name` at all**

**Benefits:**
- Avoids the function that caused the oops
- The address source is transparent and auditable (the `[nvidia]` attribution is visible)
- You can confirm the symbol exists with `cat /proc/kallsyms` before deciding to load a module

## P1 conclusion

| Item | Status |
|---|---|
| kprobe technical feasibility | ✅ validated (QEMU) |
| calling `kallsyms_lookup_name` on the host | ❌ oops, unusable |
| **obtaining symbol addresses** | ✅ **switched to `/proc/kallsyms`, measured working** |
| P1 goal (obtain nvidia symbol addresses) | ✅ **substantively achieved** (addresses are already in `/proc/kallsyms`) |

**P1 verdict: done, but the approach was corrected from "dynamic kprobe resolution" to "read kallsyms in user space + pass in as a parameter".**

## Lessons

1. **QEMU and host behaviour can differ** — the symbol-table size difference made the same code succeed on one side and crash on the other
2. **A crashed kernel module cannot be unloaded** — two tests left two 12 KB zombie modules each, clearable only by reboot
3. **Look for the simplest route first** — time was spent writing a kprobe when `/proc/kallsyms` was directly readable
4. **Validate in an isolated environment before porting, but passing isolated validation ≠ safe on the host**

## Next step (P2)

1. User-space script: extract the addresses of `os_map_kernel_space` / `nv_al_add_mapping` etc. from `/proc/kallsyms`
2. The module receives the address via `module_param`, then does a **read-only validation** first (print memory
   contents near the symbol to confirm the address is valid)
3. Once confirmed valid, study the function signature and attempt to establish a GPU memory mapping
