# 2026-10-18 · 阶段 1 补记 5：GSP 固件的 vBIOS 证书验证链（决定性证据）

## 发现

在 `/lib/firmware/nvidia/580.142/gsp_tu10x.bin`（30 MB，Turing GSP 固件）中，
检索到一组 **vBIOS 验证错误码**，来自 `FWSECLIC`（Firmware Security License）模块：

```
vbios
vbios000
NV_UDE_ERR_VBIOS_VERIF_COMPLETED_AND_FAILED
NV_FWSECLIC_ERR_CODE_CMD_VBIOS_VERIFY_DEVID_FAIL
NV_FWSECLIC_ERR_CODE_CMD_VBIOS_VERIFY_CERT_NOT_FOUND
NV_FWSECLIC_ERR_CODE_CMD_VBIOS_VERIFY_CERT_PARSE_FAIL
NV_FWSECLIC_ERR_CODE_CMD_VBIOS_VERIFY_CERT_VERIFY_FAIL
NV_FWSECLIC_ERR_CODE_CMD_VBIOS_VERIFY_HAT_FAIL
NV_FWSECLIC_ERR_CODE_CMD_VBIOS_VERIFY_BIOS_SIG_FAIL
NV_FWSECLIC_ERR_CODE_CMD_VBIOS_VERIFY_HULK_INIT_FAIL
```

## 这条证据说明什么

这不是"某处可能校验"的推测，而是**固件里现成的错误码枚举** —— 每一条都对应一个校验环节：

| 错误码 | 校验环节 |
|---|---|
| `VERIFY_DEVID_FAIL` | 设备 ID 与 vBIOS 声明是否一致 |
| `VERIFY_CERT_NOT_FOUND` | 是否携带签名证书 |
| `VERIFY_CERT_PARSE_FAIL` | 证书格式是否合法 |
| `VERIFY_CERT_VERIFY_FAIL` | **证书链是否可验通** |
| `VERIFY_BIOS_SIG_FAIL` | **vBIOS 镜像签名是否匹配** |
| `VERIFY_HAT_FAIL` | 哈希树 / Hash-and-Trim 校验 |
| `VERIFY_HULK_INIT_FAIL` | 安全初始化阶段失败 |
| `VERIF_COMPLETED_AND_FAILED` | 整个验证流程失败 |

**结论：vBIOS 在加载前要过完整的证书链 + 镜像签名 + 哈希树验证。**

## 这直接解释了三个此前的实测现象

1. **为什么改 vBIOS 不可能** —— 不是"难"，是签名校验会把任何改动判为 `BIOS_SIG_FAIL`。
   没有 NVIDIA 私钥，改出来的镜像无法被 GSP 接受。
2. **为什么 `cmpunlocker` 必须走 Falcon 漏洞** —— 因为它绕过的正是"加载器在验签之前先拷贝数据"
   这个时序缺陷，而不是尝试伪造签名。
3. **为什么 `nvidia-smi` 能报 VBIOS 版本而 PCI ROM BAR 读不到** —— vBIOS 由 GSP/固件侧持有并验证，
   不通过 PCI Option ROM 机制向系统暴露。

## 至此，完整的四层防线

```
┌─ ① 硬件层 ───────────────────────────────────────────┐
│ GPU 无独立 SPI Flash                                  │
│   卸载驱动后 PCI ROM BAR 返回 EIO（0 字节）            │
├─ ② 固件层（系统）───────────────────────────────────┤
│ Intel Boot Guard：BIOS 关键区域签名 + 加密            │
│ 24 MB dump 中无 VFCT 表、无 _ROM 方法、无明文 PCIR     │
├─ ③ 固件层（GPU）────────────────────────────────────┤
│ GSP FWSECLIC：vBIOS 证书链 + 镜像签名 + 哈希树验证    │
│   ← 本轮新发现，是最直接的一条                        │
├─ ④ 驱动层 ───────────────────────────────────────────┤
│ NVML 不暴露 TC 计数                                    │
│ CUPTI metric 枚举 rc=38                                │
│ 私有 ioctl 对象级隔离（占位句柄 0xcaf0xxxx）           │
└──────────────────────────────────────────────────────┘
```

**四层，四个不同的技术手段，每一层单独就足以封死一条路径。**

## 对解锁可能性的最终判断

| 要改的东西 | 拦路的那一层 | 可否绕过 |
|---|---|---|
| vBIOS 镜像（devinit / 限速配置） | ③ GSP 证书验证 | 仅可能通过加载器时序漏洞（Falcon 类），需自研 |
| 系统 BIOS 中的 VGA 模块 | ② Boot Guard | 需要 Intel/联想私钥，**不可能** |
| 运行时寄存器（SS/PLM 类） | ④ 驱动对象模型 + ③ PLM 权限 | 需先知道 Turing 的寄存器地址（**未知**） |
| 显存容量 | 硬件（颗粒焊死） | **不可能** |

**四条路径，两条物理不可能，两条需要目前不存在的信息/漏洞。**

## 尚未尝试的一条

若能在 GSP 启动后通过 mailbox 查询该对象，或许能取到**已解密的 vBIOS 镜像**用于静态分析

这需要解析 GSP 的 RPC 协议，工作量较大，且不改变「改不了」的结论。
