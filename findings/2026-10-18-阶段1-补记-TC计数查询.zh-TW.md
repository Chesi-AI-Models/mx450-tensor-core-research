# 2026-10-18 · 階段 1 補記：TC 計數查詢嘗試（未成功）

## 目標

讀取 `NV2080_CTRL_GR_INFO_INDEX_TENSOR_CORE_COUNT (0x23)`，
判定驅動是否承認這塊晶片存在 Tensor Core。

- 回傳 56（14 SM × 4）→ TC 被硬體承認，只是限速 → **B 類假設成立**
- 回傳 0 → 驅動層即判定不可用 → 接近 A/D 類

## 執行結果

```
開啟 /dev/nvidiactl OK (fd=3)
[1] 分配 ROOT_CLIENT
  ALLOC class=0x41 失敗: [Errno 22] Invalid argument (status=0)
```

**第一步 alloc 即被拒，`EINVAL`。**

## 失敗原因分析

1. **無編譯器。** NAS 上 `which gcc` → not found（只有 `/usr/bin/make`），
   無法編譯官方範例（`nvidia-3d-init.c`），只能用 ctypes 手工建構結構體。
2. **結構與驅動期望不匹配。** 驅動在 `escape.c` 裡用
   `_RM_ESC_IOCTL_ENTRY(cmd, type)` 嚴格校驗 `size == sizeof(type)`。
   通用 Turing 結構在 580 驅動的實際封裝方式（對齊/padding）若與 ctypes 推算差一個位元組即回傳 EINVAL。
3. **RM 初始化時序。** 現代驅動（470+）對 `/dev/nvidiactl` 的 RM 通道有額外前置要求，
   直接 alloc root client 不一定被接受。

## 結論

**這是工具鏈問題，不是原理問題。** 該診斷手段在目前環境不可用，需要：

- 方案 A：給 NAS 裝 `build-essential`（`apt install gcc make linux-headers-$(uname -r)`），
  然後編譯基於官方 headers 的 C 工具 —— 最可靠
- 方案 B：改用 `nvidia-push` 函式庫的 `rmApiControl`（與 `nvidia-3d-init.c` 同路徑）
- 方案 C：放棄該指標，改用 CUPTI 擷取 `sm__pipe_tensor_cycles_active` 類計數器，
  直接觀察張量管線是否被活化 —— **資訊量更大，且不依賴私有 ioctl**

## 影響評估

**不阻塞主線。** 已有證據足以支撐「TC 存在但被限速」的判斷：

1. `ptxas -arch=sm_75` 對 `mma.m16n8k8` 產生真 HMMA 指令（opcode 指紋與 FFMA 版完全不同）
2. 執行不報錯（若 TC 完全缺失，HMMA 應觸發非法指令）
3. 吞吐恆為 0.60 TFLOPS，低於純 FFMA 的 3.06 —— 說明走了一條**比軟體模擬還慢**的路徑
4. `cuBLAS` 請求 `TENSOR_OP` 演算法後同樣只有 0.32 TFLOPS

TC 計數只是一個「驅動怎麼看這塊矽晶片」的旁證，不改變上述四條實測事實。
