## 五、发现：Falcon / RISC-V 的分派逻辑

```asm
655b1a: mov  0x640(%r13),%eax     ; 读架构标识字段
655b21: sub  $0x2,%eax
655b24: cmp  $0x1,%eax
655b27: jbe  657c32               ; 值 ∈ {2,3} → 走 RISC-V 微码路径
655b2d: movq $0x0,0x40(%rbp)      ; 否则 → 走 Falcon 微码路径
655b35: mov  $0x0,%rsi            ; ← 重定位占位：GRCTX_UCODE_DATA_FECS
```

**这直接印证了本项目的实测结论：**

| 架构 | 微码类型 | 依据 |
|---|---|---|
| Turing (TU117) | **Falcon fuc6** | 我们 dump 的 32KB/16KB 都是 fuc6 指令 |
| Ampere+ | **RISC-V** | 代码里 `arch ∈ {2,3}` 分支加载 RISCV ucode |

**`0x640(%r13)` 是架构枚举字段，`{2,3}` 对应 RISC-V 世代。**

## 七、实测验证：`0x40A600` 是 GPC 级状态寄存器

GPU 满载时读 BAR0：

```
0x40a600 = 0x1F801FC2   ← GPC0
0x40a604 = 0x1F801000
0x40a608 = 0x1F801000
0x40a60c = 0x1F801000
0x40a610 = 0x1F801FC2   ← GPC1（与 GPC0 完全相同）
0x40a614 = 0x1F801000
0x40a618 = 0x1F801000
0x40a61c = 0x1F801000
0x40a620 - 0x40a66c = 0x00000000   ← 剩余 5 组全零
```

**结构解读：**

- 数组按**最大 GPC 数 7** 分配（对应 GA102 等大芯片）
- **TU117 只有 2 个 GPC**，所以只有前 2 组有数据
- 每组 4 个寄存器，步长 `0x10`
- 组内第 0 个是状态（`0x1F801FC2`），第 1-3 个是配置（`0x1F801000`）

**这是 GPC 级状态寄存器，不是 Tensor Core 配置。**

## 八、这一轮的根本结论

### 已经确认的

| # | 结论 | 证据 |
|---|---|---|
| 1 | nvidia.ko 符号表完整（46614 条） | `readelf -s`，与 kallsyms 地址精确对应 |
| 2 | GR context 布局由 `_nv033210rm` 构造 | 186 个 GRCTX 字符串全部定位到该函数 |
| 3 | **Turing 用 Falcon 微码，Ampere+ 用 RISC-V** | `0x640(%r13) ∈ {2,3}` 分支 |
| 4 | **`0x20000` 段在 host 侧无任何地址表** | `.rodata` 全量扫描，仅找到数值表 |
| 5 | `0x400000` 段有 18 张真实地址表 | 含 `0x409C18`（FECS↔GPCCS 握手） |
| 6 | `0x40A600` 是 GPC 级状态，7 组按最大 GPC 分配 | BAR0 实测，前 2 组有效 |

### 最终判断（与之前一致，但现在有闭源 HAL 的证据）

**`0x20000` 段是 Falcon IO 空间，不是 host 可见的 GR 寄存器。**

三重证据：

1. **`.rodata` 里没有 `0x20000` 段的地址表**（只有等比数列等数值表）
2. **GR context 的寄存器清单只包含 `0x400000` 段**（18 张表，全部在该段）
3. **微码用 `bit31=0` 的 `iowr` 访问 `0x20000` 段，用 `bit31=1` 访问 `0x400000` 段**（GPCCS 的 `0x201` 子程序）

**三条独立证据指向同一结论：NVIDIA 自己的驱动都不把 `0x20000` 段当作 host 可访问的寄存器。**
