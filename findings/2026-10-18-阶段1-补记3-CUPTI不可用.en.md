# 2026-10-18 · Stage 1 addendum 3: the CUPTI route (option A) ruled out

## Goal

Use CUPTI to enumerate the performance counters the GPU exposes, look for `sm__pipe_tensor*`-class metrics, and
directly observe whether the tensor pipeline is physically activated. That is closer to the hardware truth than the
TC count.

## Environment

- CUPTI library: `/vol1/ganlin/venv/lib/python3.11/site-packages/nvidia/cuda_cupti/lib/libcupti.so.12`
- headers complete (`cupti.h` / `cupti_metrics.h` / `cupti_events.h` etc.)
- exported symbols confirmed present: `cuptiDeviceEnumMetrics` / `cuptiDeviceGetNumMetrics` /
  `cuptiMetricGetIdFromName` / `cuptiMetricEnumEvents`
- tool: `tools/enum_cupti_metrics.py` (calls CUPTI via ctypes, no compilation needed)

## Attempt 1 · direct enumeration

```
cuInit -> 0
cuDeviceGet -> 0  device = 0
cuCtxCreate -> 0
cuptiDeviceEnumMetrics -> rc = 38
collected 0 metrics in total
```

All CUDA-side initialization succeeded; **only metric enumeration was refused**.

## Attempt 2 · retry after opening profiling permissions

GeForce restricts profiler permissions by default, so a module option was written and the driver reloaded:

```
/etc/modprobe.d/nvidia-profiling.conf:
  options nvidia NVreg_RestrictProfilingToAdminUsers=0

modprobe -r nvidia_uvm nvidia_drm nvidia_modeset nvidia
modprobe nvidia / nvidia_modeset / nvidia_drm / nvidia_uvm
nvidia-smi -L  ->  GPU 0: NVIDIA GeForce MX450 (normal)
```

Re-running the enumeration:

```
cuptiDeviceEnumMetrics -> rc = 38
collected 0 metrics in total
```

**Conclusion: this is not a permissions problem.**

## Verdict

`CUPTI 38` cannot be mapped to a literal enum entry in the local headers (that header is generated by conditional
compilation). With the permissions factor eliminated, the most likely explanations are:

- this CUPTI version (12.1.105) does not support metric enumeration on this GPU, or
- `cuptiDeviceEnumMetrics` requires a prior profiler-config initialization that is unavailable on GeForce

**Either way, route A is unusable in this environment.**

## Final status of the three diagnostic routes

| Route | Means | Result | Nature of the blocker |
|---|---|---|---|
| B-1 | `NV2080_CTRL` ioctl read of the TC count | channel opened (ROOT_CLIENT succeeded), GR_GET_INFO status=31 | driver object model not established |
| A | CUPTI metric enumeration | `rc=38`, zero metrics (even after opening permissions) | library + permission, double restriction |
| C | system BIOS devinit analysis | not started | needs a BIOS dump |

**Both high-level diagnostic paths are sealed, but both are "toolchain limitations", not a denial at the level of principle.**

## Impact on the core conclusion

**None.** The following four pieces of evidence are mutually independent; any one of them supports "TCs exist but
are throttled":

1. `ptxas -arch=sm_75` emits real HMMA instructions for `mma.m16n8k8` (opcode fingerprint completely different
   from the FFMA version)
2. the instruction executes without fault (if TCs were entirely absent it should raise an illegal instruction)
3. throughput is a constant 0.60 TFLOPS, **below pure FFMA's 3.06** — a path even less efficient than a software
   unrolled version
4. `cuBLAS` returns 0.32 TFLOPS after requesting the `TENSOR_OP` algorithm, 6.4× slower than FP32

**To go further one must cross beyond user space:**

1. **write a kernel module to mmap BAR0 directly** — this is exactly the route CMPUnlocker takes
   (its patch modifies the `nvidia-open` kernel module directly, bypassing all user-space APIs)
2. **dump the system BIOS and analyze the devinit tables** — the only high-level path not yet tried
3. physical measurement (oscilloscope / power meter) — unrelated to this project's goal
