# 2026-10-18 · Stage 1 addendum: TC count query attempt (unsuccessful)

## Goal

Read `NV2080_CTRL_GR_INFO_INDEX_TENSOR_CORE_COUNT (0x23)` to determine whether the driver
acknowledges that this chip has Tensor Cores.

- Returns 56 (14 SM × 4) → TC is acknowledged by hardware and merely throttled → **hypothesis B holds**
- Returns 0 → the driver layer already considers it unavailable → closer to class A/D

**The very first alloc was rejected with `EINVAL`.**

## Failure analysis

1. **No compiler.** On the NAS `which gcc` → not found (only `/usr/bin/make`), so the official example
   (`nvidia-3d-init.c`) could not be built; the struct had to be hand-assembled with ctypes.
2. **Struct layout does not match what the driver expects.** The driver uses
   `_RM_ESC_IOCTL_ENTRY(cmd, type)` in `escape.c` to strictly check `size == sizeof(type)`.
   If ctypes' computed packing (alignment/padding) differs by even one byte from the 580 driver's
   actual layout, EINVAL is returned.
3. **RM initialization ordering.** Modern drivers (470+) impose additional prerequisites on the RM
   channel of `/dev/nvidiactl`; allocating a root client directly is not necessarily accepted.

## Conclusion

**This is a toolchain problem, not a principle problem.** The diagnostic is unavailable in the current
environment and requires:

- Option A: install `build-essential` on the NAS (`apt install gcc make linux-headers-$(uname -r)`),
  then build a C tool against the official headers — most reliable
- Option B: use `nvidia-push`'s `rmApiControl` (the same path as `nvidia-3d-init.c`)
- Option C: drop this metric and instead use CUPTI to collect counters such as
  `sm__pipe_tensor_cycles_active`, directly observing whether the tensor pipeline is activated —
  **more informative, and free of private ioctl dependencies**

## Impact assessment

**This does not block the main line.** The evidence already suffices to support "TCs exist but are throttled":

1. `ptxas -arch=sm_75` emits real HMMA instructions for `mma.m16n8k8` (opcode fingerprint completely
   different from the FFMA version)
2. Execution does not fault (if TCs were entirely absent, HMMA should raise an illegal instruction)
3. Throughput is a constant 0.60 TFLOPS, below pure FFMA's 3.06 — meaning it takes a path that is
   **even slower than software emulation**
4. `cuBLAS` returns only 0.32 TFLOPS after requesting the `TENSOR_OP` algorithm

The TC count is merely corroborating evidence for "how the driver sees this silicon"; it does not change
the four measured facts above.
