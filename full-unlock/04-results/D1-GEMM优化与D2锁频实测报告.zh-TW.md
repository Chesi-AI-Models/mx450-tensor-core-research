## 一、結論摘要

| 指標 | 結果 |
|---|---|
| 自研 FFMA GEMM 最好成績 | **2.4872 TFLOPS**（C7 `64×128×BK8 T8×8 PAD0 單緩衝`） |
| 相對 cuBLAS fp32 mm（同行程測） | **1.17x**（cuBLAS 2.13 TFLOPS） |
| 相對 cuBLAS fp16 mm | **8.1x**（cuBLAS fp16 僅 0.32 TFLOPS） |
| 時脈折算效率 | **80–81%**（對比：純 FP32 FFMA 可到 99.0%） |
| `nvidia-smi -lgc` 鎖頻 | **被接受（rc=0）但完全無效** |
| 熱降頻標誌 | **Not Active**（不是散熱壓的） |

**★ 最重要的修正：「3.06 TFLOPS」這個分母是錯的。**
它來自 1665 MHz 假設，但本機 SM 時脈實測在 **1290–1830 MHz** 之間漂移
（`clocks.max.sm = 2100`）。因此：

- 物理峰值 = `2 × 64 × 14 × clk` = 1290MHz→2.31 / 1395→2.50 / 1665→2.98 / 1830→3.28 / 2100→3.76 TFLOPS
- **絕對 TFLOPS 跨輪次不可比**，只有「相對同輪時脈折算峰值」的百分比可比
- 教訓與 T2-1 的「MB/GB 單位混用」同類：**分母沒校準，所有百分比都是假的**

### 2.2 關鍵機制驗證

**① float2 ≠ 2 個 half（踩坑）**
CUDA 的 `float2` 是 2 個 **float** = 8 位元組。要表示 2 個 half（4 位元組）必須用
`unsigned int`。用錯立刻觸發 `misaligned address`，而這是**黏性錯誤**，會打死整個
context，導致後續所有 kernel 報 716/700。→ 必須寫**靜態對齊預檢**，不能靠跑崩來驗證。

**② padding 會破壞 16B 對齊（連網查證 + 實測一致）**
A tile `[BM][BK+PAD]`，要 float4（16B）寫共享記憶體，需 `(BK+PAD)×2 % 16 == 0`，
即 `BK+PAD` 必須是 8 的倍數。BK=8 時 PAD=6 → 行首偏移 12B，靜態預檢直接攔下。
可選 PAD ∈ {0, 8, 16}。**PAD=0 時行跨度正好 16B，天然零 bank 衝突**（實測 C7 用 PAD=0）。

**③ 減少內層指令數不等於變快**
v6 把內層從 `16×LDS.U16 + 16×cvt` 改成 `4×LDS.128`，指令數降到 1/4，
但**整體慢了 8%**。原因是 smem 存 float 讓位元組量翻倍、且轉置寫入是 8 次純量 STS。
→ 「指令數」不是唯一維度，**smem 位元組流量**同樣關鍵。

**④ 純 FFMA 天花板可信（99.0%）**
`2.4747 TFLOPS @ 1395 MHz`，分母 `2×64×14×1.395 = 2.4998` → 99.0%。
說明公式與 FMA 管線都能跑滿，GEMM 的 80.9% 差的是**訪存停頓**，不是算力。

### 3.1 為什麼 -lgc 無效（推斷 + 已有證據支撐）

- 命令被驅動**接受並回顯設定成功**，但時脈紋絲不動 → 不是權限問題、不是語法問題
- **熱降頻標誌全是 0** → 不是散熱壓的（溫度 80–86°C，但沒觸發 throttle flag）
- 本專案已實測確認：**開源模組強制啟用 GSP**（`NVreg_EnableGpuFirmware=0` 被忽略）
- GSP-RM 韌體接管了時脈／電源域 → `nvidia-smi` 的 lgc 走的是老的 PMU 路徑，被旁路

**→ 想真正超頻，只有兩條路：**
1. **換閉源模組** + `NVreg_EnableGpuFirmware=0`，讓時脈管理回到驅動側（open-gpu-kernel-modules
   issue #965 有成功案例，代價是某些場景效能降 50%）—— 尚未做
2. 改 vBIOS/PPTable —— **本機無 vBIOS**（ROM BAR 分配失敗，已實測），此路不通
